# Дизайн: единая фабрика спавна игрока + ростер + компонентные мозги

Дата: 2026-07-19
Статус: спека (утверждена к планированию)

## Контекст

Сейчас в проекте **7 почти одинаковых мест спавна игрока** (по ~30 строк копипаста
каждое: `CharacterBody3D` + `PlayerVisual` + `PlayerMotor` + `CollisionShape3D` +
группа + слои коллизий + `set_script(ai)` + ссылки `ball`/`home_goal`/…):

- `player_home` — в `match_manager._ready` (особый случай: узел сцены `$PlayerHome`,
  а не `.new()`);
- `_setup_keeper`, `_setup_away_player`, `_make_dummy_opponent`, `_setup_teammate`
  (в `match_manager.gd`);
- `_make_wall_body`, `_make_mate_body` (в `free_kick_controller.gd`).

И **46 обращений по имени** (`player_home`/`player_teammate`/`player_away`), все в
`match_manager.gd`. Проблемные потребители: `_reset_ball` (репозиционирует ровно 3
именованных игрока), `_sync_ai_controllers`, логика `player_away.target_node`,
`_give_ai_to_player_home`.

Это породило целый **класс багов**: каждое заспавненное «на лету» тело (стенка
штрафного, цели навеса) оказывалось «второсортным» — часть кода проверяла игроков по
имени, а не по группе/роли, поэтому спавны вели себя иначе, чем штатные игроки
(другая сила/направление паса, отсутствие анимации, накопление тел между розыгрышами).
Чинилось реактивно, точечно, по одному сайту.

### Дорожная карта (драйвер архитектуры)

Дальше планируются: **угловые, ауты, удары от ворот** (сет-писы по образцу штрафного),
затем **11×11 с двумя разными командами** (и возможные 7×7 / 5×5), с **заменами** и
**сменой тактики по ходу игры**. Более далёкие цели: карьера тренера, карьера игрока,
локальный сплит-скрин, сетевой мультиплеер (LAN-матч против друга или кооп против ИИ),
мультиплеер внутри карьеры.

Именованные синглтоны при 22 игроках (11 на команду, вратарь среди них) разваливаются
полностью, а сет-писам
постоянно нужно спавнить/репозиционировать подмножества игроков **по роли**.

## Принцип (единственное, что закладываем «на будущее»)

Триаж дорожной карты показывает, что все будущие режимы указывают на один и тот же
load-bearing принцип (ретрофит которого дорогой):

> **Разделить ДАННЫЕ игрока** (сериализуемые, переживают матч — «член заявки») **и
> ТЕЛО** (`CharacterBody3D`, заспавненное в конкретный матч). **Фабрика делает тело из
> данных и является единственным швом создания.**

Это то же разделение, что уже пронизывает проект (gameplay/presentation; чистая
математика `class_name X extends Object` vs узлы). Оно ложится в стиль кодовой базы.

| Будущее | Требование именно к слою «ростер/фабрика» (и только) |
|---|---|
| 11/7/5, разные конфиги | Ростер — список переменной длины; спавн N по конфигу |
| Замены, смена тактики | Состав изменяемый в рантайме; различие «заявка/скамейка» vs «11 на поле» |
| Карьера тренера/игрока | Данные игрока переживают матч и существуют отдельно от `CharacterBody3D` |
| Локальный сплит-скрин | «Управляемый» — атрибут игрока, а не один глобальный `controlled_player` |
| Сетевой матч | Один шов создания для репликации (`MultiplayerSpawner` любит одну точку и стабильные пути) |

## Не-цели (явно отложено)

Швы, которые вводит этот заход (данные-конфиг, фабрика-шов, `Team`-узлы, компонентные
мозги), оставляют перечисленное инкрементальным — но **ничего из этого сейчас не
строим**:

- персистентность/сейвы карьеры;
- репликация / неткод (`MultiplayerSpawner`, authority, синхронизация);
- сама логика замен и движок тактики;
- авторинг формаций (спавн 11 по схеме 4-4-2 и т.п.) — сейчас позиции задаются
  явными конфигами, не системой формаций;
- система атрибутов/статов игрока;
- сплит-скрин-ввод (несколько человек на одном ПК);
- `RemoteBrain` (сетевой мозг);
- общий **intent modifier stack** (приоритетный стек стиринг-слоёв) — Фаза 3 делает лишь
  его вырожденный одноэлементный случай (слот приём-ассиста); полный стек призывается
  11×11-дисциплиной / избеганием / `REMOTE` (см. «Будущее» в Фазе 3).

## Общая форма (итог обсуждения)

Три развилки уже решены:

1. **Уровень амбиции — B**: фабрика + реестр + лёгкий `Team` (кит/сторона) + enum роли
   (`GK/DEF/MID/FWD`). Не C: формации/атрибуты преждевременны (YAGNI до реального 11×11).
2. **Хранение ростера — гибрид**: `Team`-объект — авторитетный источник ростера/ролей/
   кита/стороны; **группы Godot** (`team_1`/`team_2` + `fallen`/`fk_spawned`) остаются
   **физическим индексом** для Area3D-оверлапов/тэклов/подбора. Фабрика — единственное
   место, где эти двое ставятся согласованно, поэтому рассинхрон структурно невозможен.
3. **`Team` — узел в дереве** (netcode-дружелюбная форма: позже `MultiplayerSpawner`
   вешается на поддерево команды, пути стабильны, authority — на команду). Игроки — дети
   `Team`-узла.
4. **Примитив фабрики — сцена `player.tscn`** (idiom неткода; убирает копипаст сборки
   капсулы/коллайдера; особый узел `$PlayerHome` исчезает).

Заход выполняется **тремя последовательными фазами в одном рефакторе**, каждая —
чистый рефактор (нулевой видимый геймплей-эффект), каждая оставляет игру запускаемой и
headless-тесты зелёными.

## Конвенция связей (сигналы vs вызовы)

Godot рекомендует сигналы, но с оговоркой самой документации — **«signal up, call down»**:
сигналы вверх по дереву (ребёнок сообщает, не зная слушателя), прямые вызовы вниз (родитель
командует). Не «везде сигналы». Правила этого рефактора:

- **Сигналы — для дискретных событий, вверх по дереву.** `PlayerVisual.action_contact/
  action_finished` (уже канон), `Brain.action_requested`/`charge_fired(...)` (мозг → executor),
  `charge_started/canceled`, `Team.player_added/removed`. Слушатель может быть неизвестен
  эмитенту (реплей/статистика подпишутся бесплатно потом).
- **Опрос геттеров — для непрерывных состояний, каждый тик.** `movement_intent`,
  направление прицела, текущий charge `ratio` — читаются в `_physics_process` (call down).
  Сигнал на каждый physics-тик = шум, мусорные аллокации и, главное, **потеря явного порядка**
  (петля с опросом читается сверху вниз, сигнальный каскад — нет). Правило: сигнал = *событие*,
  опрос = *состояние*.
- **Внутренности резолюции — прямые вызовы.** Цепочка `select_target → lead/scatter → launch`
  внутри `ActionExecutor` остаётся линейным кодом, а не сигнальной цепочкой (иначе теряется
  читаемая последовательность).
- **Все `connect` — только в `PlayerFactory`.** Единственная точка проводки = противоядие от
  сигнальных спагетти: вся связность видна в одном месте (и её забывчивое отсутствие — ровно
  баг стенки штрафного — становится структурно невозможным).

## Фаза 1 — фабрика + ростер

### `PlayerConfig` (`scripts/match/player_config.gd`, `RefCounted`)

Вход фабрики; эмбрион будущего `SquadMember`. Сейчас — тонкий дата-холдер, `FootballConstants`
не читает (значения передаются вызывающим):

```
enum Role { GK, DEF, MID, FWD }
enum Control { AI, HUMAN, REMOTE }   # REMOTE — заглушка на будущее

team_group: StringName    # &"team_1" (наша) / &"team_2" (соперник) — совместимо с физикой
role: Role
kit_color: Color
spawn_pos: Vector3
control_mode: Control
ai_script: Script         # мозг, когда control_mode == AI (keeper_ai / simple_ai / teammate_ai)
display_name: String
```

### `scenes/player.tscn`

Корень `CharacterBody3D` (**в Фазе 1 без скрипта** — скрипт мозга навешивается через
`set_script`, см. ниже; Фаза 2 заменит это на стабильный `player.gd`). Дети — в
**фиксированном порядке**:

1. `PlayerVisual` (инстанс `scenes/player_visual.tscn`);
2. `PlayerMotor`;
3. `CollisionShape3D` (капсула `height=1.5`, `radius=0.3`, `position.y=0.25`).

Фиксированный порядок в сцене снимает рантайм-футган «`PlayerVisual` должен
существовать раньше `PlayerMotor`, иначе `PlayerMotor._ready` не найдёт его при
однократном скане сиблингов» (см. CLAUDE.md, *Locomotion*).

**Вратарь** — тот же `player.tscn` + доп. узлы, которые фабрика досоздаёт по
`role == GK` (нельзя вшить в общую сцену, иначе полевые игроки таскали бы лишнее):
`SaveArea` (`Area3D`, сфера `KEEPER_REACH`, mask=1), `HoldPoint` (`Node3D`), и
`PlayerVisual.set_locomotion_style(LOCO_STYLE_KEEPER)`.

### Идентичность без скрипта

Так как в Фазе 1 `set_script(ai)` заменяет скрипт корня, идентичность (команда/роль)
хранится в **группах**, которые переживают `set_script`:

- команда — существующие `team_1`/`team_2`;
- роль — **роль-группа** (`role_gk`/`role_def`/`role_mid`/`role_fwd`).

Роль-группы полезны и после Фазы 2 (физике/`Team.by_role` они не мешают), поэтому это
**не выброшенная работа**, а постоянный физический индекс роли. `set_meta`-хак не нужен.

### `PlayerFactory` (`scripts/match/player_factory.gd`, статические функции)

Единственный шов создания:

```
static func spawn(config: PlayerConfig, team: Team) -> CharacterBody3D
```

Делает по порядку: `preload("res://scenes/player.tscn").instantiate()` → имя/поза →
кит через `PlayerVisual.apply_appearance` → слои коллизий (`PLAYER_COLLISION_MASK` /
`… | BOUNDARY_COLLISION_LAYER`) → для `GK` досоздаёт `SaveArea`/`HoldPoint` → регистрация
`team.add_player(body, config.role)` (внутри: `add_child` под `Team`-узел, группы
`team_x` + `role_x`, добавление в упорядоченный список) → коннект
`visual.action_contact/action_finished` на менеджер (как у штатных игроков — иначе
deferred-impulse пас уходит по фолбэку) → `set_script(config.ai_script)` (если AI) →
проставление `ball`/`home_goal`/`controlled_player`/`speed`.

`team` знает `manager` и `ball`, поэтому дополнительных параметров не нужно.

### `Team` (`scripts/match/team.gd`, `class_name Team extends Node`)

Узел в дереве, игроки — его дети. Две штуки под менеджером: `TeamHome` (наша),
`TeamAway` (соперник).

```
team_group: StringName
attack_z_sign: float     # -1 наша (атакуем -Z), +1 соперник
kit_color: Color
id: StringName
manager: Node
ball: Node

add_player(body, role) / remove_player(body)
players() -> Array[CharacterBody3D]   # упорядоченный
by_role(role) -> Array
keeper() -> CharacterBody3D           # первый role_gk или null
outfield() -> Array
```

Источник истины для геймплея. Группы — по-прежнему для физики.

### Роутинг 46 обращений по имени → запросы к `Team`

Категории и на что меняются:

- `_reset_ball` — итерирует `TeamHome.players()` + `TeamAway.players()`, ставит по
  их `spawn_pos` (сохранённой в теле/конфиге) или по будущей формации, вместо жёстких
  3 именованных строк.
- `_sync_ai_controllers` — итерирует обе команды.
- `player_away.target_node` — через `TeamAway`/`TeamHome`-запросы.
- `_give_ai_to_player_home`, `controlled_player = player_home` — наш человек становится
  обычным продуктом фабрики (конфиг `control_mode = HUMAN`); `controlled_player`
  инициализируется этим телом.
- `_team_arrays(group, except)` — уже работает по группам; выравнивается на `Team`.

### Особый случай `$PlayerHome`

Узел `$PlayerHome` (+ его `Mesh`) **удаляется** из `match.tscn`. Наш человек спавнится
фабрикой, как все. Это убирает единственную асимметрию «сценовый узел vs `.new()`».

### DEBUG-флаги

`DEBUG_DISABLE_TEAMMATE` / `DEBUG_DISABLE_OPPONENT` / `DEBUG_MARK_TEAMMATE` продолжают
работать — фабрика просто спавнит меньше тел / болванки идут тем же путём.

## Фаза 2 — ИИ-мозги как компоненты

Убирает `set_script(ai)` на корне тела: корень получает **стабильный скрипт**, а «мозг»
становится дочерним компонентом — как `PlayerMotor`/`PlayerVisual`.

### `player.gd` (стабильный корень `player.tscn`)

`class_name Player extends CharacterBody3D`. Держит **реальные поля идентичности и
геймплей-ссылки** (вместо групп-как-единственного-носителя и ручного проставления после
`set_script`): `team_group`, `role`, `ball`, `home_goal`, `controlled_player`,
`display_name`. Группы `team_x`/`role_x` остаются как физический индекс (дублируют поле
роли намеренно — физике нужны группы, геймплею удобны поля).

### Brain-интерфейс

Мозг — дочерний `Node`, выдающий **намерение движения** (и ничего не двигающий сам):

```
# базовый контракт (утиная типизация или базовый class_name Brain extends Node)
func think(delta) -> void          # считает намерение
func movement_intent() -> Vector3  # желаемое направление в мире (как сегодня set_move_intent)
func speed_scale() -> float
```

Петля тела/менеджера: у активного мозга спрашиваем intent и кормим им `PlayerMotor`
(тот же путь `set_move_intent`, что и сегодня). Commit-действия ИИ (запрос тэкла,
`wants_to_tackle`; удар/пас ИИ) остаются как сейчас — через флаги/менеджер.

### Конверсия ИИ-скриптов

`simple_ai.gd` / `teammate_ai.gd` / `keeper_ai.gd` переписываются с
`extends CharacterBody3D` на `extends Node` (или `extends Brain`), читающие тело-
родителя (`_body := get_parent()`): каждое `self.global_position` → `_body.global_position`,
поля/сигналы/group-проверки — через `_body`. Их внешнее поведение сохраняется 1:1.

**Вратарь — самый рисковый узел**: save-loop, нырок через `move_and_collide`,
ловля/приклейка мяча (`ball.catch`), дистрибуция. Конверсия сохраняет всю его логику;
`move_and_collide`/доступ к `SaveArea`/`HoldPoint` идут через `_body`. Прогонять
`check_keeper_logic` + `check_keeper_clear` + `check_kick_grace` после каждого шага.

### `control_mode`

- `AI` — активен `AIBrain` (конкретный скрипт из `config.ai_script`).
- `HUMAN` — **активного мозга нет; телом рулит `match_manager`** напрямую (как в Фазе 1).
  Это временный «лес» до Фазы 3.
- `REMOTE` — отложено (`RemoteBrain` в будущем).

Фабрика в Фазе 2 навешивает мозг как компонент вместо `set_script`. Смена «стенка →
обычный ИИ» (`_convert_bodies` в штрафном) становится **добавлением/включением
компонента**, а не `set_script` + ручной re-wire.

### Тесты Фазы 2

- Все прежние остаются зелёными (особенно keeper-набор и `check_free_kick_flow`).
- Новый `check_player_brain.gd`: у тела с `AIBrain` есть `movement_intent`; включение/
  выключение мозга; `HUMAN`-тело не имеет активного мозга.

## Фаза 3 — человек как компонент-мозг (за гейтом)

Симметризует управление: `HUMAN` перестаёт быть спецслучаем в `match_manager` и
становится мозгом, как ИИ. Это — конечное состояние под сплит-скрин и неткод (пока
человек — единственный спецслучай, именно эта асимметрия дерётся с ними).

**Самая сложная и наименее механическая фаза** — трогает feel-critical ввод
(→ дриблинг/удар/пас), чистый рефактор с нулевым видимым эффектом ровно там, где регресс
игрок заметит первым. Поэтому — **за гейтом** (см. «Порядок и гейты») и с возможным
быстрым под-дизайном при входе в неё.

### Два внутренних шага (последовательно, каждый — 1:1 по поведению)

**Шаг 3a — извлечение `ActionExecutor` (чисто механически).** Общий commit/резолюция-путь
(select_target → lead/scatter → launch-вектор → триггер анимации → ожидание
`action_contact` → `ball.kick/launch` → приём-ассист → передача `controlled_player`)
выносится из `match_manager` в отдельный объект `ActionExecutor`
(`scripts/match/action_executor.gd`). Перенос кода, поведение 1:1, все тесты зелёные.
Мотив: (1) Фаза 3 всё равно **определяет интерфейс** этого пути (action-requests на входе,
импульсы мяча на выходе) — извлекать потом = трогать код дважды; (2) executor с чистым
интерфейсом **headless-тестируем напрямую** (скормили фейковый `action_requested` —
проверили `ball.launch`), чего с методами внутри ~1000-строчного менеджера сейчас нет;
(3) менеджер худеет (перегруженный файл — сигнал по CLAUDE.md). Ключевое: путь остаётся
**один и общий с ИИ** — в каком файле он лежит, вторично. `ActionExecutor` — сегодняшнее
решение; если однажды заслужит дальнейшего дробления, это уже отдельный заход.

**Шаг 3b — `HumanBrain` + подключение сигналами.** `HumanBrain` (`extends Brain`) =
адаптер «устройство-ввод → намерение + запросы действий», симметричный ИИ-мозгу.

### Шов (граница ввод ↔ резолюция)

Та же линия, что и для движения: **мозг интерпретирует ввод — `ActionExecutor` резолвит.**

- **`HumanBrain` держит у себя:**
  - непрерывные состояния (опрашиваются геттером раз в тик, как `movement_intent`):
    `movement_intent`/`speed_scale`, направление прицела, и **текущий charge ratio**;
  - **заряд-как-таймер целиком** — превращение удержания кнопки в `ratio` живёт здесь
    (девайс-независимый выход: клавиша-таймер и аналоговый триггер дают `ratio` по-разному).
    ИИ не «заряжает» — он решает силу напрямую, поэтому это по определению ввод-специфично;
  - дискретные события наружу — **сигналами** (`charge_started` / `charge_fired(action, ratio)`
    / `charge_canceled`, `tackle_requested`, …).
- **`ActionExecutor` держит у себя** общий commit-путь (шаг 3a) — по `action_requested`
  из мозга. Трогает **общий мяч**, шарится с ИИ. Форкать его в `HumanBrain` **нельзя** —
  это ре-создало бы класс багов «человек и ИИ бьют по-разному» (эмпирика этой сессии:
  баги стенки штрафного были ровно форкнутым, мимо-`action_contact`, commit-путём).
- **Менеджер** остаётся владельцем per-frame петли (опрос intent мозга → `PlayerMotor`),
  UI заряда (power-bar/телеграф **читают** состояние из мозга, не опрашивают «а не начал ли
  ты?»), и роутинга сигналов мозга в `ActionExecutor` (коннект ставит фабрика).

Почему заряд обязан быть per-brain, а не одним `_charge_action` в менеджере: это тот же
синглтон-недуг, что и `player_home`. Два человека на сплит-скрине заряжают одновременно —
одна match-wide state-машина заряда ломается ровно так же, как ломались по-именные игроки.
А по сети поедет «пас, ratio 0.7», не «кнопка зажата 0.43с» — значит `ratio` обязан
считаться там, где живёт ввод; будущий `RemoteBrain` эмитит тот же `charge_fired` из пакета,
и `ActionExecutor` потребляет его неотличимо от человека.

### Следствия

- `controlled_player` = «тело с активным `HumanBrain`». Сплит-скрин (будущее) = несколько
  `HumanBrain`. Схема «HUMAN = менеджер рулит напрямую» из фаз 1–2 — лес, заменяется.
- `REMOTE` = `RemoteBrain` — по-прежнему отложено (эмитит те же сигналы из сетевого пакета).

### Приём-ассист и оверрайд intent мозга

Основную границу (ввод ↔ резолюция) фиксирует раздел «Шов» выше. Остаётся один нюанс:
**приём-ассист** и подобная матч-логика **перекрывает** intent мозга (ассистированный забег
приёмника поверх стика; тот же силуэт — магнетизм подбора `PICKUP_ASSIST_*` и брейк-эвей-
погоня в `_handle_player_input`, где стик лишь подруливает heading). Это не чистый «мозг
выдал — motor взял»: матч-логика модифицирует движение управляемого тела на таком кадре.

**Решение на Фазу 3 (вариант A — вырожденный одноэлементный случай будущего стека):**

- После опроса intent мозга и перед подачей в `PlayerMotor` менеджер применяет **один
  именованный слот-модификатор движения** (`_movement_override` или т.п.). Он владеет
  матч-знанием (входящий пас, предсказание мяча, свободный мяч) — **мозг про оверрайд не
  знает и остаётся тупым**. Слот применяется одинаково к человеку и (будущему) ИИ-приёмнику.
- Состояние приёма делаем **per-receiver, а не match-wide**: нынешние `_receive_active`/
  `_receiver`/`_receive_timer` — тот же синглтон-недуг, что `_charge_action`/`player_home`,
  и так же сломаются на сплит-скрине (два приёмника разом). Кладём его на тело/мозг приёмника.
- Существующие ad-hoc оверрайды (магнетизм подбора, брейк-эвей-погоня) по возможности
  сводим в тот же слот — но это причёсывание, не блокер фазы.

### Будущее: intent modifier stack (НЕ строим сейчас)

Слот из варианта A — **вырожденный одноэлементный случай** общего приоритетного стека
модификаторов движения (паттерн *steering behaviors* / context steering): базовый intent
мозга + N контекстных слоёв, часть — мягкий бленд (взвешенный пул), часть — жёсткий оверрайд,
разрешаются по приоритету. Призывается **не сейчас, а конкретными вехами дорожной карты**:

- **11×11 — позиционная дисциплина** (20 полевых, каждый вне мяча подтягивается к слоту
  формации поверх решения ИИ — мягкий пул);
- **локальное избегание** (обруливание тел поверх навигационного intent);
- **сет-пис-стейджинг** (стенка/забеги как слой позиционирования вместо ad-hoc
  `set_control_locked`);
- **give-and-go / скриптовые забеги** как слой;
- **`REMOTE` — сетевая реконсиляция** (подтягивание локально-предсказанного тела к серверной
  позиции — оверрайд-слой над предсказанием).

**Граница стека:** только **мягкий стиринг** (посчитал направление/цель → бленд или замена).
Жёсткое физикой-владеемое движение — `fallen`/нокдаун, слайд-тэкл через `move_and_collide`,
заморозка на голе — в стек **не входит**: это вопрос «кто владеет телом на кадре» (обход
мотора / прямое владение позицией), а не «какое направление». Впихивать их туда «высоким
приоритетом» — дырявая абстракция.

### Тесты Фазы 3

- Все прежние зелёные (особенно `check_free_kick_flow`/`check_penalty_flow` — общий
  commit-путь через `ActionExecutor` должен сохраниться 1:1).
- Новый `check_action_executor.gd` (шаг 3a): фейковый `action_requested` на входе →
  проверка `ball.kick/launch` на выходе, headless, в изоляции от менеджера/Input.
- Новый `check_human_brain.gd` (шаг 3b, насколько headless позволяет без Input):
  `HumanBrain` выдаёт `movement_intent` и эмитит `charge_fired(action, ratio)` из
  подставленного ввода; `ActionExecutor` их резолвит.
- Интерактивный feel (дриблинг/удар/пас/спринт/приём) — **обязательный человеческий
  плейтест**, headless его не покрывает.

## Порядок и гейты

1. **Фаза 1** (фабрика/ростер) — целиком, до зелёных тестов и плейтеста «играется как
   раньше».
2. **Фаза 2** (ИИ-мозги) — целиком, до зелёных тестов и плейтеста.
3. **Гейт**: перед Фазой 3 — плейтест-подтверждение фаз 1–2 + под-дизайн границы.
4. **Фаза 3** (человек-мозг).

Почему тремя фазами, а не одним слитным диффом: все три — чистый рефактор с нулевым
видимым эффектом; единственная страховка — «играется так же». Слитый дифф переплёл бы
регресс в нырке вратаря с регрессом в запросах ростера и во вводе человека — бисект стал
бы мучением. Фаза-1-первой даёт, что к моменту brain-изации точка навешивания мозга ровно
одна (фабрика), а не 7.

## Риски

- **Вратарь (Фаза 2)** — самый интеллектуально плотный код; конверсия body→component
  рискованна. Митигировать: пошагово, с прогоном keeper-тестов после каждого шага.
- **Feel человека (Фаза 3)** — регресс заметен игроку первым; митигировать гейтом +
  плейтестом + сохранением общего commit-пути в `ActionExecutor` 1:1 (мозг только
  запрашивает, резолюцию не форкает).
- **Скрытая зависимость от порядка детей** — снимается фиксированным порядком в
  `player.tscn` (это улучшение, не риск).
- **Рассинхрон `Team` ↔ группы** — структурно исключён: обе стороны ставит только
  фабрика.

## Сводная тестовая стратегия

- Регрессионная сетка = все существующие `tests/check_*.gd` должны оставаться зелёными
  на каждом шаге всех трёх фаз.
- Новые headless: `check_player_factory.gd`, `check_team_roster.gd` (Фаза 1);
  `check_player_brain.gd` (Фаза 2); `check_action_executor.gd` (шаг 3a),
  `check_human_brain.gd` (шаг 3b) (Фаза 3).
- Плейтест человеком — после каждой фазы (headless не ловит feel/рендер): «играется как
  раньше» — движение, дриблинг, удар/пас, тэкл, вратарь, штрафной/пенальти.
