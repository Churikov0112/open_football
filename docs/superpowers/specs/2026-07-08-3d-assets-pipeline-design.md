# 3D-ассеты: переход от процедурной графики к реальным моделям и анимациям

## Обзор

Сейчас OpenFootball — полностью процедурный: меши, текстуры, разметка поля генерируются в
коде, игроки визуализируются цветными капсулами. Цель — заменить визуальный слой на
**настоящие риггованные анимированные модели** (полу-реалистичный стиль, как в референсе
`C:\Users\User\Desktop\OpenSoccer`), **не ломая существующий геймплей**.

Проект **публичный/open-source**, поэтому допустимы только чистые лицензии
(CC0 / CC-BY / Mixamo). Декомпилированные ассеты OpenSoccer использовать **нельзя** — только
как локальный референс по таймингу/пропорциям, не коммитить и не распространять.

Документ описывает стратегию источников ассетов и целевую архитектуру. Это дизайн «на
будущее» — реализация пойдёт отдельным планом (writing-plans), поэтапно.

## Ограничения и принятые решения

| Ограничение | Решение |
|---|---|
| Проект open-source | Только CC0 / CC-BY / Mixamo. Ассеты OpenSoccer вне пайплайна |
| Полу-реалистичный стиль | Игроки — Mixamo (риг + мокап). Чистых CC0-реалистичных футболистов почти нет |
| Пользователь не моделирует | Mixamo (параметрический выбор), CC0-библиотеки, headless-скрипты Blender |
| Есть рабочий процедурный геймплей | Не переписывать логику. Менять только слой презентации |
| Готовность к будущему 11v11 | Единый переиспользуемый `PlayerVisual` на всех игроков |

## Стратегия источников ассетов

Игроки и реквизит решаются **раздельно** — это разные задачи.

### Игроки (анимированные) — Mixamo

- **Персонаж:** базовая модель Mixamo либо свой меш через авто-риггер Mixamo.
- **Анимации:** мокап-библиотека Mixamo (idle, walk, run, sprint, turn) + доработка
  футбольной специфики (kick, slide, header, keeper dive) — часть адаптируется из
  генеричных клипов.
- **Формат:** Mixamo отдаёт FBX → прогон в `.glb` → импорт в Godot 4.
- **Лицензия:** Mixamo royalty-free, годится для коммерции и open-source. **Серая зона** —
  распространение *сырых* файлов Mixamo как отдельной библиотеки. **Митигация:** в репозиторий
  коммитим только Godot-импортированный `.glb` (игровая форма), не сырые FBX; происхождение
  фиксируем в `NOTICE`/`ASSET_CREDITS.md`.

### Реквизит (статичный) — CC0-библиотеки

Мяч, ворота, флаги, элементы стадиона, декор.

- **Источники:** Kenney (CC0), Quaternius (CC0), Poly Haven (CC0).
- **AI-генерация (Meshy / Tripo / Rodin)** — допустима **только для статичного реквизита**,
  не для игроков (плохая топология под скиннинг + мутные лицензии бесплатных тарифов).
  По возможности избегать в open-source из-за неясных прав; предпочитать CC0.
- Текущую процедурную геометрию (поле, разметка) можно оставить как есть — она уже
  генерируется в коде и лицензионно чистая.

## Архитектура: разделение геймплей / презентация

### Проблема текущей структуры

Узел игрока смешивает две ответственности (`match_manager.gd:_setup_away_player`):

```
PlayerAway (CharacterBody3D)   ← ГЕЙМПЛЕЙ: позиция, движение
├── MeshInstance3D (капсула)   ← ПРЕЗЕНТАЦИЯ: как выглядит
├── CollisionShape3D           ← ГЕЙМПЛЕЙ: физика
└── script = simple_ai.gd      ← ГЕЙМПЛЕЙ: мозги (move_toward, подкат, удар)
```

### Целевая структура

Геймплей-слой **не трогаем**. Заменяем капсулу на риггованный визуал:

```
PlayerAway (CharacterBody3D)        ← НЕ ТРОНУТО
├── PlayerVisual (инстанс сцены)    ← НОВОЕ, вместо капсулы
│   ├── Skeleton3D
│   ├── MeshInstance3D (меш Mixamo)
│   ├── AnimationPlayer             ← клипы (idle/run/sprint/kick/slide…)
│   └── AnimationTree → StateMachine
│       + script = player_visual.gd ← склейка
├── CollisionShape3D                ← НЕ ТРОНУТО
└── script = simple_ai.gd           ← НЕ ТРОНУТО
```

### Гибридный интерфейс (ключевое решение)

OpenSoccer тоже управляет AnimationTree от состояния геймплея, но делает это **внутри
монолитного `Player.gd` (~1000 строк)** — анимация вперемешку с AI/мячом/движением
(`Player.gd:676` `myAState.travel("sprint")`, `:813` `RunSpeed/scale = vl*1.33`). Это даёт
высокую точность, но плохо поддерживается — та же болезнь, что у нашего `match_manager.gd`
(820 строк).

Берём развязку, но **не «нюхаем скорость» пассивно** — геймплей **явно пушит** состояние
презентации через узкий интерфейс `PlayerVisual`:

```gdscript
# player_visual.gd — публичный API, вызывается из gameplay-скриптов:
func set_locomotion(velocity: Vector3) -> void   # → блендит idle/walk/run/sprint
func trigger(action: String) -> void             # разовые: "kick", "header"
func set_flag(flag: String, on: bool) -> void    # длящиеся: "sliding", "fallen"
```

Контракт:
- **Геймплей** не знает про имена анимаций, узлы, AnimationTree — только зовёт API.
- **Презентация** не читает и не меняет логику — только реагирует на вызовы.
- Точность как в OpenSoccer (визуал знает момент удара, наклон, слайд), но без монолита.

Маппинг состояний геймплея на анимации:

| Источник (геймплей уже знает) | API | Анимация |
|---|---|---|
| `velocity ≈ 0` | `set_locomotion` | `idle` |
| средняя/высокая скорость | `set_locomotion` | `run` / `sprint` (blend по длине) |
| группа `fallen` | `set_flag("fallen", true)` | падение / вставание |
| идёт слайд-подкат | `set_flag("sliding", true)` | `slide` |
| вызван `_kick_ball()` | `trigger("kick")` | `kick` |

### Интеграция замены

В `match_manager.gd` блок создания капсулы (`_setup_away_player` строки ~341–349, аналогично
`_setup_teammate`, `PlayerHome`) заменяется на инстансинг `PlayerVisual.tscn`. Точки вызова
API добавляются в `simple_ai.gd` / `teammate_ai.gd` / input-обработку и в существующую
машину подката. **Фолбэк:** если модель не грузится, `PlayerVisual` показывает капсулу-
заглушку — геймплей продолжает работать.

## Godot-интеграция (технические детали)

### Пайплайн импорта Mixamo → Godot

1. В Mixamo: выбрать модель, скачать её со скином (T-поза) + анимации отдельно. Локомоцию
   (idle/run/sprint) — «in place» (движение делает геймплей-код). Коммит-действия
   (slide/fall/getup) часто **без** флага In Place — это нормально, root motion там полезен
   (см. «Движение и реализм»); клипы, у которых In Place недоступен, приводим к нужному виду
   при сборке.
2. **Прогон FBX → `.glb`** (Godot дружелюбнее к glTF). Варианты:
   - вручную через Blender (импорт FBX → экспорт glb), **или**
   - **headless-скрипт Blender** (`blender --background --python merge_mixamo.py`), который
     объединяет модель + все анимации в один `.glb` с одним AnimationPlayer. Скрипт пишу я,
     если Blender установлен.
3. Положить `.glb` в `assets/characters/`, открыть редактор один раз для импорта.
4. Проверить импорт-настройки в Import-доке (масштаб, скелет).

### Известные грабли Mixamo → Godot

| Грабля | Обход |
|---|---|
| Масштаб ×100 (сантиметры) | Import scale `0.01` в `.import` |
| Несколько анимаций = несколько файлов | Объединить в один AnimationPlayer (Blender-скрипт или вручную) |
| Root motion сдвигает модель | Гибрид (см. «Движение и реализм»): локомоция — «in place», код двигает тело; коммит-действия (slide/fall) — наоборот, root motion **гонит** тело. Клипы без флага In Place де-рутим при сборке или гасим через `root_motion_track` |
| Имена костей Mixamo | Godot 4 humanoid retarget / bone map при необходимости |
| Ориентация модели | Развернуть в `PlayerVisual.tscn`, чтобы «вперёд» = −Z по движению |

### Движение и реализм (как в FIFA/PES — и что берём мы)

Как AAA-футбол добивается реализма движений — четыре столпа, и все взаимозависимы:

1. **Root motion как фундамент** — анимация (мокап) двигает игрока, а не «код двигает
   капсулу, анимация сверху». Отсюда правильный перенос веса, инерция, отсутствие
   проскальзывания стоп.
2. **Motion Matching** — база из тысяч кадров мокапа; каждый кадр система ищет позу+траекторию,
   лучше всего совпадающую с желаемой (из ввода/ИИ), и подмешивается к ней. Реализм оттого,
   что всегда играется реальный мокап, а не собранное руками blend-дерево.
3. **Foot planting / IK** — инверсная кинематика прибивает стопы к земле, гасит остаточное
   скольжение, фиксирует опорную ногу на разворотах/остановках.
4. **Смесь с физикой (active ragdoll)** — подкаты/столкновения/падения перетекают в физику
   (каждое уникально, а не «консервный» клип) + animation warping доводит стопу точно по мячу.

**Важно:** root motion в AAA неотделим от motion matching + IK + физики. Взять только root
motion — получишь «игрок едет по рельсам анимации, управление вязкое». А у нас в CLAUDE.md
прямо записано arcade rules → полный AAA-путь не для этой стадии.

**Наше решение — гибрид** (не «всё in-place» и не «всё root motion»):

| Класс движения | Кто двигает тело | Скольжение стоп лечим |
|---|---|---|
| Локомоция (idle/run/sprint) | **код** (`move_toward` по позиции — как сейчас) | синхронизацией скорости клипа с реальной (`RunSpeed/scale`), позже — foot IK |
| Коммит-действия (slide/fall/getup, dive, празднования) | **root motion** — анимация гонит `CharacterBody3D` через `root_motion_track` → дельта | не нужно (тело едет вместе с анимацией) |
| Разовые на месте (kick/pass/header) | код (тело почти не едет) | не актуально |

Логика: в коммит-действии игрок и так «отдаёт управление» на время клипа, поэтому пусть его
двигает анимация — это выглядит **лучше** нашего ручного `move_and_collide` в подкате и не
ломает аркадную отзывчивость бега.

**«По-взрослому» (дальняя перспектива, бэклог):** motion matching + полноценный foot IK
(`SkeletonIK3D`) + physics/ragdoll-blending на столкновениях. В Godot нет motion matching из
коробки — это отдельный крупный проект (своя реализация или плагин). Заводим, только когда
геймплей устоится и захочется дожать реализм; на этап 3 **не** тащим.

### AnimationTree

Простой `AnimationNodeStateMachine`: `idle → walk → run → sprint` (переходы по скорости) +
one-shot ветки для `kick` / `header` поверх (`AnimationNodeOneShot`), + флаги `slide`/`fallen`
как отдельные состояния. Локомоция-ветка получает `RunSpeed/scale` от реальной скорости
(anti-slide); состояния коммит-действий читают `root_motion_track`. Хардкодить сложный граф в
`.tscn` вручную больно, поэтому начинаем с минимального (idle/run/sprint) и растим.

## Внешность и различение команд

Две отдельные задачи: **цвет формы команды** (все синие / все красные) и **вариативность
игроков** (кожа, волосы, причёски). Копировать меши для этого не нужно — всё делается
материалами и attach-ами.

### Цвет формы (кит) — по возрастанию качества

| Способ | Как | Когда |
|---|---|---|
| Тинт материала целиком | Override `albedo_color` на инстансе, красит всё тело | **Пилот** (выбран): команды = синий/красный, лучше капсул |
| Свап текстуры кита | Две текстуры (синий/красный) на материал рубашки | Когда есть меш с рубашкой как отдельным материалом/UV |
| Шейдер + маска кита | Ч/б маска «где рубашка» + юниформ цвета → красит только рубашку | Целевой масштабируемый: одна модель → любой цвет |

**Пилот-решение:** Mixamo-персонаж + тинт всего тела в цвет команды. Не «настоящий кит»
(случайная одежда Mixamo, без номеров/спонсора), но визуально разделяет команды. Настоящие
киты (маска рубашки, номера) — позже, требуют футбольного меша с kit-UV, которого Mixamo не
даёт.

### Вариативность игроков (кожа / волосы / причёски) — дальняя перспектива

- **Кожа** — тинт/юниформ материала кожи на инстансе.
- **Цвет волос** — тинт материала волос.
- **Причёски** — модульные меши: лысая база + сменный меш волос, attach к кости головы.

Из одной общей базы генерится разнообразный состав: на игрока — скин + меш причёски + цвет
волос + цвет кита. **Один humanoid-скелет → один набор анимаций работает на всех вариантах;
кастомизация — только материалы + attach, никогда не переанимация.**

### Интеграция в `PlayerVisual`

Внешность задаётся один раз при спавне, отдельно от покадровой анимации:

```gdscript
func apply_appearance(cfg: AppearanceConfig) -> void
#   cfg = { kit_color, skin_tone, hair_mesh_id, hair_color }
```

Пилот использует только `kit_color` (тинт всего тела). Остальные поля — задел на будущее.

### Влияние на выбор базовой модели

Требование вариативности разворачивает долгосрочный выбор базы к **параметрическим людям**:
фиксированные персонажи Mixamo плохо параметризуются (готовые «личности»), а
**MakeHuman/MB-Lab** дают скин-тон/причёски/тип тела ползунками + чище лицензия. При этом
**Mixamo остаётся источником анимаций** (ретаргет на MakeHuman-риг). Целевая связка:
MakeHuman (база) + Mixamo (анимации) + шейдер-маска китов + модульные причёски. На пилоте это
**не** трогаем — стартуем на Mixamo + тинт.

## Риски и открытые вопросы

- **Лицензия Mixamo для публичного репо** — серая зона. Митигация: только `.glb` в репо +
  `NOTICE`. Если станет блокером — запасной путь: полностью CC0 Blender-пайплайн
  (MakeHuman/MB-Lab + Rigify + CC0-мокап).
- **Дефицит футбольных анимаций в Mixamo** — kick/slide/header/keeper dive скудны, часть
  придётся адаптировать вручную. Оценить на этапе 3 (сбор клипов).
- **Клипы без флага In Place** — у slide/fall/getup флага часто нет → несут root motion.
  Решено (см. «Движение и реализм»): для коммит-действий это ок (root motion гонит тело); для
  локомоции без In Place — де-рутить при сборке (`merge_mixamo.py`) или гасить
  `root_motion_track`. Ось «горизонтали» после `automatic_bone_orientation` неочевидна —
  чистку root motion проверять на конкретном клипе.
- **Производительность на 11v11** — 22 скелета + анимации. Проверять на этапе 5 (LOD,
  animation culling вне камеры).
- **Установлен ли Blender** — определяет, могу ли я автоматизировать FBX→glb. Проверить перед
  реализацией.
- **Скольжение стоп в локомоции** — при «in place»-беге скорость клипа надо синхронизировать
  со скоростью геймплея, иначе ноги скользят. Решено: `RunSpeed/scale` в AnimationTree (как в
  OpenSoccer), позже — foot IK на этапе «по-взрослому».
- **Настоящие киты требуют футбольного меша с kit-UV** — Mixamo его не даёт. На пилоте
  обходим тинтом всего тела; для номеров/масок нужен спец-меш (сорсить/делать позже).
- **MakeHuman не гиперреалистичен** — из коробки «обобщённый реалистичный человек» (полу-
  реализм, простые текстуры, слегка манекенный вид), подходит под целевой стиль, но лица
  бывают безликими. Оценивать при переходе на этап 6.
