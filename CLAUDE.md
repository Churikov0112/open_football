# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OpenFootball — a football (soccer) simulation game in Godot 4.7 / GDScript. Arcade rules, FIFA-scale pitch. Windows-only for now. Currently a small-scale prototype (human + AI teammate vs. one AI opponent), not yet 11v11.

**Art is now hybrid, no longer "procedural everything."** The pitch, field markings, goals, grass, and ball are still generated in code, but **players are real rigged Mixamo models** (skeletal idle/run animations) wrapped in a `PlayerVisual` node — the old colored capsules are gone. See *Presentation layer & asset pipeline* below.

## Commands

- **Validate (headless, no window, menu-load only):**
  `& "C:\Users\User\AppData\Local\Godot\Godot_v4.7-stable_win64_console.exe" --path "C:\Users\User\Desktop\projects\OpenFootball" --headless --quit`
- **Validate the match scene (headless, no window):**
  `& "C:\Users\User\AppData\Local\Godot\Godot_v4.7-stable_win64_console.exe" --path "C:\Users\User\Desktop\projects\OpenFootball" --headless --quit-after 2 res://scenes/match.tscn`
- **Run the game / open editor:** same exe without the `--headless` flags.

**Both headless commands above are needed, not just one — they catch different things.** Plain `--headless --quit` boots `main_menu.tscn` (the project's actual main scene) and never clicks Start, so it parses every globally-registered `class_name` script and autoload but **never loads `match.tscn`** — meaning `match_manager.gd`, `teammate_ai.gd`, and `simple_ai.gd` are never parsed by this command at all (verified empirically: injecting a syntax error into `match_manager.gd` and running plain `--quit` produced zero error output). The second command (`--quit-after 2 res://scenes/match.tscn`) directly instantiates `match.tscn`, so it's the one that actually exercises those three files (and `keeper_ai.gd`). Known pre-existing baseline for the second command: a handful of error *categories* — `ERROR: Condition "!is_inside_tree()" is true.` (setup-order), the `ACTION_CLIPS` kick/pass duplicate-registration quirk (`states.has(p_name)` + two transition-duplicate errors, see *Presentation layer* below), and `ERROR: Cannot get class 'WorldEnvironment3D'.`. **Counts grew** once the keeper was added (it's a second `PlayerVisual` in the match scene, so the duplicate-registration errors roughly doubled) — so diff by error *category/text*, not exact counts. When validating a change that touches match-only scripts, diff your error output against this baseline rather than expecting zero errors.

There are **no tests, no lint, and no CI** beyond the two headless commands above and the `tests/check_*.gd` scripts (see *Headless check scripts* below) — verify gameplay feel by actually running the game, since most logic is physics/timing-dependent and won't surface in a headless load.

## Architecture

**Entry flow:** `main_menu.tscn` (main scene) → Start button loads `match.tscn`. Do **not** treat `match.tscn` as a standalone entry point.

**One brain — `scripts/match/match_manager.gd`** (extends Node3D, root of `match.tscn`). This ~1000-line file owns nearly everything: input setup, camera tracking, procedural field markings/goals/grass/boundaries, controlled-player switching, kick/pass (with charge + deferred impulse system), and the entire slide-tackle state machine. When in doubt, the logic is here.

**Nodes are wired up in code, not in the scene.** In `_ready()`, `match_manager` builds two `Team` roster nodes and spawns every player — human, teammate, opponent, keeper — through `PlayerFactory.spawn(config, team)` (see *Player spawn factory & roster* below), which attaches AI as a **child `Brain` component** (`scripts/ai/brain.gd`, `class_name Brain extends Node`) rather than `set_script()`-ing the body root. The body root itself is a stable `scripts/player/player.gd` (`class_name Player extends CharacterBody3D`, `player.tscn`'s root script) with a `brain()` lookup. The `Ball` still gets its script attached via `set_script()`/`preload()` — unaffected by this. So `.tscn` files are minimal — grep the manager's `_setup_*` functions (and `PlayerFactory.spawn` itself) to find where a node actually gets its behavior. Every field player gets a `scenes/player_visual.tscn` instance as a child (baked into `scenes/player.tscn`, the factory's spawn primitive) for its rigged model + team-color tint (see next section).

**AI Brain components (children of the body, not `set_script` on it):**
- `scripts/ai/simple_ai.gd` (`extends Brain`) — opponent (team_2, **red**): chases ball/target, dribbles toward goal, shoots, can request tackles.
- `scripts/ai/teammate_ai.gd` (`extends Brain`) — used for **both** the teammate **and** `PlayerHome` when it's not the human-controlled player (team_1, **blue**). Positions for a pass / chases ball. (The teammate is currently spawned — `DEBUG_DISABLE_TEAMMATE=false`.)
- `scripts/ai/keeper_ai.gd` (`extends Brain`) — the AI goalkeeper in the Home goal (`_setup_keeper`), driving its `PlayerMotor` + a keeper-styled `PlayerVisual` on the body. Save loop + ball-in-hands + distribution; math in `scripts/match/keeper_logic.gd` (`class_name KeeperLogic`). See *Goalkeeper* below.
- Every `Brain` subclass reads its own body via `_body := get_parent()` (cached in `Brain._ready()`) — never `self` for the body's own transform/physics/groups. Field brains drive movement by calling the base class's `_drive(dir, scale)`/`_stop()`, which forward into `PlayerMotor.find_on(_body)`.
- **`MatchManager._ai_of(body) -> Node`** is the single indirection the manager uses to reach an AI's fields/methods (`wants_to_tackle`, `target_node`, `mark_target`, `begin_receiving`, `begin_give_and_go`, `controlled_player`, `speed`, …): returns `body.brain()` if the body has one, else the body itself. Use it at every new AI call-site — a direct `body.some_ai_field` access bypasses the component and either throws (direct dot-assignment) or silently no-ops (`.set()`/`.get()`/`has_method`-guarded calls).
- **The keeper is special-cased**: `match_manager._keeper` stays the **body** (used for freeze/keep-active exclusion and ball-contact identity checks — `n == _keeper`), while `match_manager._keeper_brain` (`= _keeper.brain()`) is used for the keeper's API/state (`goal_line_z`, `on_ball_contact()`, `set_penalty_mode()`, `begin_penalty_dive()`, `set_freekick_anchor()`, `clear_freekick_anchor()`, `_state`). `penalty_controller.gd`/`free_kick_controller.gd` mirror the same split.
- Free-kick wall/mate bodies (`free_kick_controller.gd`'s `_convert_bodies`) convert from inert to live AI by **adding a Brain child** (`ai_script.new()` → `add_child`), not `set_script`.
- `scripts/ball/ball_controller.gd` — ball physics + dribbling.
- `scripts/camera/match_camera.gd` — camera.
- `scripts/player/player_controller.gd` — exists but note `PlayerHome` is driven by `match_manager` input + `teammate_ai`, so check what's actually attached before assuming this runs.
- `scripts/player/player_visual.gd` (`class_name PlayerVisual`) — the presentation layer attached to `scenes/player_visual.tscn`. Not an AI/gameplay script; see next section.
- `scripts/player/player_motor.gd` (`class_name PlayerMotor`) — the locomotion component. Added as a **third child** of every field player's `CharacterBody3D` (alongside `PlayerVisual` and the collision shape), in that order — `PlayerVisual` must exist first, since `PlayerMotor._ready()` finds it by scanning siblings once. Owns all movement physics; see *Locomotion* below.

**Constants:** `scripts/data/football_constants.gd` is autoloaded as `FootballConstants` (global). Central place for field dimensions, ball/player/AI/tackle/locomotion (`LOCO_*`) tuning. **Caveat:** `match_manager.gd` also hardcodes `KICK_CHARGE_MAX_TIME = 0.5` locally and kick range `2.0` inline — when tuning, grep both locations. (The real aimed shot is now in — continuous aim, ground/chip/curl variants via `ShotSystem`; see *Status notes*. `SHOT_*` tuning lives in `football_constants.gd`.) (Player top speed comes from `FootballConstants.LOCO_TOP_SPEED` via `PlayerMotor`.)

## Locomotion (`PlayerMotor`)

**Player movement is velocity + inertia via `move_and_slide()`, not direct position manipulation.** `scripts/player/player_motor.gd` (`class_name PlayerMotor`) is a component node — every field player's `CharacterBody3D` gets one as a child, and it owns 100% of that body's movement physics. Callers (human input in `match_manager.gd`, both AI scripts) never touch `global_position`/`rotation` for movement anymore — they only call `motor.set_move_intent(dir, speed_scale)` with a desired world-space direction, once per frame. The motor internally: integrates velocity toward the desired speed (`LOCO_ACCEL` accelerating, `LOCO_DECEL` decelerating — asymmetric, so releasing input glides rather than snapping to a stop), smooth-turns the body's yaw toward the velocity direction (`LOCO_TURN_ROT`, gated below `LOCO_TURN_MIN_SPEED` so it doesn't spin on the spot), computes a **smoothed** lean/bank angle from lateral acceleration and feeds it to `PlayerVisual.set_lean()` (smoothed via `PlayerMotor.smooth_scalar()` at `LOCO_BANK_SMOOTH` — the raw per-frame value is jumpy because WASD input direction snaps instantly, not analog), calls `move_and_slide()`, then pins `global_position.y` to the spawn height every frame (the field is flat) **except while `fallen`** (so a slide-tackle knockback's vertical pop isn't instantly flattened).
- `set_control_locked(on)` — used during commit-actions (pass/kick) and the tackler's own slide: when locked (or the body is in group `fallen`), velocity snaps to **zero immediately** (not a gradual decel) so the body doesn't keep drifting on residual velocity while something else (a hand-authored animation lock, or the tackle's own `move_and_collide()`) is supposed to own the motion that frame.
- Sprint (**hold Shift**) is just a higher `speed_scale` passed into `set_move_intent` by the human-input path in `match_manager.gd` — AI does not sprint.
- `PlayerMotor.find_on(node)` (static) is the canonical "find my sibling motor" lookup — used by both AI scripts and `match_manager._player_motor()`; don't re-scan `get_children()` by hand.
- **Collision layers — three deliberately separate groups.** Default layer 1 holds the pitch and the ball (kept there so goal/tackle-`Area3D` detection, which checks `body == ball`, isn't disturbed). Field players are on `FootballConstants.PLAYER_COLLISION_MASK` (bit 2) with a `collision_mask` of `PLAYER_COLLISION_MASK | BOUNDARY_COLLISION_LAYER` — **not** layer 1 — so `move_and_slide()` makes them push off each other and off the boundary walls. The boundary walls (`_setup_boundaries()`) are on their own `FootballConstants.BOUNDARY_COLLISION_LAYER` (bit 3) precisely so they're invisible to the ball's *layer* but the ball still masks them in to physically bounce off them.
- **Ball↔player collision is FLIGHT-gated** (see *Ball model & dribbling* below). The player mask never includes the ball's layer (players walk freely). The ball's `collision_mask` base is `1 | BOUNDARY_COLLISION_LAYER` (no players); `ball_controller._set_player_collision(true)` adds the player bit **only while the ball is in `FLIGHT`** (after a kick/pass) so a shot/pass physically collides with players (block/intercept) — and removes it on trap/loose/flight-end so a dribbled or picked-up ball is transparent to capsules. This is the deliberate fix for the `78990c8` class of bug (a player mask that includes the ball's layer, or an always-on ball↔capsule collision, shoves the dribbled/loose ball off the player's own capsule → close-control stutter + spawn shove). If you add a new physics body, decide deliberately which group it sees.

## Ball model & dribbling (`ball_controller.gd`) — Phase 0, OpenSoccer-derived

This replaces the old velocity-matching / spring dribbling described in OPENCODE.md. Migrated on the `feat/kick` branch; **CLAUDE.md here is the source of truth**.

- **State machine:** `enum BallState { OPEN, TRAPPED, FLIGHT, CAUGHT }` (`ball.state`). `OPEN` = loose, `TRAPPED` = dribbled by `ball.dribbler` (a.k.a. `ball.player()`), `FLIGHT` = struck (kick/pass/curl), `CAUGHT` = **in the keeper's hands** — `ball.catch(holder, hold_node)` pins it every frame to `hold_node` (a hand-bone `BoneAttachment3D`), `is_caught()` reports it, released by `launch()/kick()/set_dribbler()` (see *Goalkeeper* above). Possession API is the legacy `set_dribbler()/release_dribble()/dribbler` kept as thin wrappers over the state machine (AI scripts read `ball.dribbler` unchanged); `player()` is the neutral getter. `set_dribbler(node, force=false)` — `force` skips the release/kicker cooldowns (used by the pass receiver and the keeper's placing-ball hand-off).
- **Impulse APIs:** `kick(dir, power)` (normalized dir × power), `launch(velocity, flat=false)` (pre-computed velocity; `flat=true` pins `vy=0` for a ground pass/roll), `launch_curl(velocity, curl, flat=false)` (Magnus). All set `FLIGHT`, apply a **deferred** impulse (`_pending_impulse`, applied at the **start** of `_integrate_forces` — see the standstill-shot fix under *Goalkeeper*), and open a `KICK_GRACE_MSEC` self-collision exception so a point-blank strike isn't blocked by its own striker. `parry(direction, damp)` is the keeper's directed deflection (vs. `block_in_flight()`'s dead stop).
- **Dribbling is continuous *lead-follow*, NOT velocity-matching or discrete pushes.** In `_integrate_forces` (TRAPPED branch): the ball is steered to a point ahead of the dribbler at a distance that **grows with player speed** (`DRIBBLE_LEAD_BASE + speed*DRIBBLE_LEAD_PER_SPEED`) — tight at the feet when slow, far ahead when sprinting. Ball velocity = player velocity + spring toward that point (`DRIBBLE_CONTROL_GAIN`), lerp-smoothed (`DRIBBLE_CONTROL_LERP`) for a living lag. Direction of the lead point = `_dribble_intent` (the human's stick, via `set_dribble_intent(dir, push_extra)`) or the dribbler's facing (AI). Sprint adds lead (`DRIBBLE_SPRINT_PUSH_EXTRA`) **and** a smooth random imprecision (`DRIBBLE_SPRINT_WOBBLE_*`) — speed traded for accuracy.
- **Break-away + chase:** when the ball gets farther than `DRIBBLE_CHASE_DIST` (sprint overshoot / deflection), it free-rolls with `DRIBBLE_ROLL_DRAG` and `should_chase()` flips true; the human-input path in `match_manager._handle_player_input` then **auto-runs the controlled player to the ball** (stick can still nudge the heading by `DRIBBLE_CHASE_STEER` to go around a defender). Back within `DRIBBLE_CATCH_DIST` → control resumes (hysteresis). Possession is **not** lost from your own push/turn — only via external factors (tackle/intercept); the distance release (`DRIBBLE_KEEP_DIST = 15`) is a far-out safety net.
- **`set_dribble_suppressed(on)`** — while charging/committing a pass or shot, the dribble is suppressed (ball waits at the feet) so the action is a single clean touch, not "dribble-push + pass". Also suppressed when the human releases the stick (player runs to the ball and stops instead of dribbling on inertia).
- **Loose-ball pickup magnetism:** off the ball, the controlled player's movement is nudged toward a nearby slow loose ball (`PICKUP_ASSIST_RADIUS/STRENGTH`) so you don't have to aim exactly.
- **Pass reception:** the intended pass receiver traps the ball at **any speed**, bypassing the trap speed-gate and the 500 ms release cooldown (`set_dribbler(receiver, force=true)`), so firm or short/quick passes don't sail past the teammate. General pickup still requires a slow ball (`BALL_TRAP_MAX_SPEED = 9`).
- **Flight-gated collision + block:** the ball collides with players only in `FLIGHT` (see *Collision layers* above); `continuous_cd = true` stops fast shots tunnelling. On a flight contact with a player, `match_manager._on_ball_collision` → `ball.block_in_flight()` (damp ×0.25, clear curl, drop to `OPEN`, collision off) — no elastic bounce, no possession handoff. Flight ends when speed < `FLIGHT_END_SPEED` (2.0, deliberately far below the trap gate so a fast ball stays blockable).
- **Magnus / curl:** `launch_curl(velocity, curl)` sets `_curl`; `_integrate_forces` applies a per-frame side+lift impulse (`MAGNUS_FORCE`, decaying by `MAGNUS_DECAY`) while in flight. **Infrastructure only** — no gameplay action calls `launch_curl` yet (the curl shot is Phase 1); `kick()/launch()` clear `_curl`.
- **Ground bounce is MANUAL, not solver restitution.** The ball's `PhysicsMaterial.bounce` is set to **`0.0`** in `_ready()` on purpose: the active floor is a materialless `WorldBoundaryShape3D` plane (see `match_manager._setup_floor`), and the solver's restitution against it — fighting the custom `_integrate_forces` that fully rewrites `linear_velocity` every frame — killed the vertical to zero, so a lob/chip "landed in a puddle." Instead, `_integrate_forces` reflects the bounce itself (OPEN/FLIGHT branch): it tracks `_prev_vy` (the vertical velocity handed to the solver last frame); when the ball is on the deck (`origin.y ≤ BALL_RADIUS + BALL_GROUND_EPS`) and was descending last frame (`-_prev_vy > BALL_BOUNCE_MIN_SPEED`) while the solver has just zeroed the current vy, it kicks vy back up by `descent × BALL_BOUNCE` and scales horizontal by `BALL_BOUNCE_FRICTION` so the ball **keeps rolling forward with decay** instead of dead-stopping. Each bounce is lower (restitution < 1) and horizontal bleeds off via `BALL_BOUNCE_FRICTION` + the usual per-frame `drag_factor`. Skipped while `_flat_flight` (a ground pass/roll is pinned to the grass anyway). The `descent > BALL_BOUNCE_MIN_SPEED` gate is what stops infinite micro-bounce jitter — a slow ball just settles.
- **Test:** `tests/check_ball_state.gd` (headless) covers the state transitions + `launch_curl`. (Bounce feel — height/decay — is physics-timing dependent and needs a human running the game; headless doesn't step the landing.)
- **Constants** live in `football_constants.gd` under DRIBBLING / BALL / SHOOTING sections. **`DRIBBLE_FORWARD_DIST`, `DRIBBLE_HEIGHT`, all `SPRING_*` are legacy/unused now** — ignore them. Ground-bounce tuning (BALL section): `BALL_BOUNCE` (0.6, restitution/height), `BALL_BOUNCE_FRICTION` (0.9, horizontal kept per bounce → roll-on distance), `BALL_BOUNCE_MIN_SPEED` (1.0, settle threshold), `BALL_GROUND_EPS` (0.03).
- **TEMPORARY test scaffolding (revert before finishing Phase 0):** `FootballConstants.DEBUG_DISABLE_OPPONENT = true` makes the AI opponent stand still (gated in `simple_ai._physics_process`) and spawns two walls of standing dummy opponents (`_spawn_wall_dummies`) for shot/block testing. The placeholder kick is also tuned stronger/flatter (`KICK_POWER_MIN/MAX = 18/34`, low `dir.y`) — the real aimed shot is Phase 1.

## Slide tackle & fall system

All in `match_manager.gd`, driven by two independent state enums: `TackleState` (`NORMAL`/`SLIDING`/`RECOVERING`) and `FallState` (`NONE`/`KNOCKDOWN`/`ROLL_1`/`ROLL_2`/`GETUP`). **Both `_tackle_state` and `_tackle_player` are single match-wide fields, not per-player** — when checking "is a tackle happening," always compare `controlled_player == _tackle_player` too, not just `_tackle_state != NORMAL`, or you'll block/affect players who have nothing to do with the tackle in progress (bit us in `_handle_player_input`).

- **Starting a slide** (`_start_tackle(player, target=null)`, called by human input via `_try_tackle()` or by AI via `_poll_ai_tackles()` polling each `team_2` node's `wants_to_tackle` flag — via `_ai_of(node)`, since the flag lives on `simple_ai`'s `Brain`, not the body): locks the tackler's `PlayerMotor`, plays the `tackle` one-shot, and aims `_tackle_dir` at `target` (defaults to `ball`) **with simple lead prediction** — `predicted_pos = target.global_position + target_velocity * (distance/SLIDE_TACKLE_SPEED)` — since the ball lead-follows its dribbler (see *Ball model & dribbling*), this leads a moving target instead of aiming at a stale position and sliding through empty space once the ~0.4s slide is over. No iterative closing-time solve, just one first-order estimate.
- **During the slide** (`_tackle_slide()`), the tackler's body physically moves via manual `move_and_collide()` (not `move_and_slide()` — the one deliberate exception to normal locomotion) while its own `PlayerMotor` stays control-locked so the two motion systems don't fight.
- **Two separate, deliberately different-radius hit checks**, because one radius can't serve both jobs without either whiffing the ball or knocking players down from a visible gap:
  - **Ball reach** — the wide `TackleArea` (`Area3D`, radius `SLIDE_TACKLE_AREA_RADIUS = 1.5`), `body_entered` → `_on_tackle_body_entered()`. Only reacts to `body == ball` now (clean tackle: pops the ball via `ball.kick()`, ends the slide). Its `collision_mask` must explicitly include `FootballConstants.PLAYER_COLLISION_MASK` (bit 2) as well as the ball's default layer 1 — Area3D's default mask is layer-1-only, so without that bit it silently never sees player bodies at all (an easy, silent way to make hit detection dead on arrival).
  - **Player knockdown** — a *much* tighter check, `_check_tackle_player_hit()`, polled every slide frame against `_tackle_area.get_overlapping_bodies()` but gated at `SLIDE_TACKLE_HIT_RADIUS = 0.9` (≈ sum of both capsule radii + a small margin) so a fall only triggers on visible capsule contact, not from ~1.5m away. Genuine `move_and_collide()` physical contact with an opposing player (checked first, in `_tackle_slide()`) also knocks them down directly, unconditionally — that path is exact contact by construction.
  - Both knockdown paths call `_on_tackle_hit_player(body, normal)` → `_begin_fall(body, normal)`.
- **Not yet a foul.** `_on_tackle_hit_player()` sets `_tackle_clean = true` unconditionally — no free kick is awarded for knocking someone down. `_tackle_foul_position` / `_tackle_fouled_player` and the free-kick branch in `_tackle_recover()` are wired up but currently unreachable; needs a "ball won first vs. body hit first" rule (see `docs/football_reference.md` §9) before it's meaningful to re-enable.
- **Victim fall chain** (`_begin_fall()` → `_process_fall()`): `KNOCKDOWN` (plays `fallen_idle`, knocked-back over `KNOCKDOWN_TIME`) → `ROLL_1`/`ROLL_2` (`roll_left`/`roll_right`, picked by which side they were hit from) → `GETUP` (`standing_up`) → `_finish_fall()` (removes `fallen` group, unlocks motor). **This is animation-driven, not physics.** An earlier physics-ragdoll approach (`scripts/player/ragdoll_skeleton.gd`, `PhysicalBone3D`) was built and then deliberately ripped out because it didn't play nice with the scaled Mixamo import — that file and its tests (`check_ragdoll_build.gd`, `check_ragdoll_real_skeleton.gd`) still exist and still pass, but **nothing in the active game calls them**; don't treat their presence as evidence ragdoll is live. While `fallen`, `PlayerMotor` doesn't touch vertical position (see *Locomotion* above) so the knockback's vertical pop isn't instantly flattened.
- **Tuning** (`football_constants.gd`): `SLIDE_TACKLE_SPEED = 9.0` (deliberately above the opponent AI's real run speed — see `simple_ai.gd`'s `speed` export, currently `8.0` — and above the human's own non-sprint top speed, so either side can close a gap; the human's sprint at `12.0` still lets them outrun a chasing AI tackle), `SLIDE_TACKLE_RANGE = 4.0`, `SLIDE_TACKLE_RECOVERY_TIME = 1.3` (slide + recovery together land close to the `tackle` clip's ~1.8s length so the animation and the commit-window roughly agree), `AI_TACKLE_RANGE = 2.0` / `AI_TACKLE_COOLDOWN = 2.0` (AI's own decision-to-attempt distance/cooldown — kept short since lead-prediction error grows with distance). `SLIDE_TACKLE_INPLACE` (currently `false`) is a diagnostic-only flag that skips `move_and_collide()` during the slide (tackler stays stationary while the clip plays) — useful for isolating whether a visual issue is in the animation or the physical slide; leave it `false` for normal play.
- **`tools/merge_mixamo.py`'s `IN_PLACE_CLIPS`** freezes root-motion translation on specific *Blender-local* bone axes for `tackle`/`roll_left`/`roll_right` so the baked-in mocap translation doesn't double up with the manual `move_and_collide()` above. Getting the axis choice wrong is easy and doesn't look like an axis bug at first — it looks exactly like "the player floats/hovers in the air." Blender's `automatic_bone_orientation` reorients each bone's local axes away from world axes, and glTF export further permutes which local index ends up in which exported track component — so "index 2 = vertical" (the assumption baked into the old code/comments) was wrong twice over. If you ever touch `IN_PLACE_CLIPS`, verify empirically (sample the built glb's actual `Position3D` track values across the clip, e.g. via `Skeleton3D.get_bone_pose()` in a throwaway headless script) rather than trusting axis-index assumptions from the source rig.

## Passing

Five pass types plus the shot share one charge system: the charge-as-timer lives in `match_manager.gd`, the resolution (`fire_shot`/`fire_pass`) in `scripts/match/action_executor.gd` (`ActionExecutor`, see *Conventions that will trip you up* below). The math lives in `scripts/match/pass_system.gd` (`class_name PassSystem extends Object`) — **pure static functions, never read `FootballConstants`** (tuning is always passed in as parameters) — so they're headless-testable without an autoload; `tests/check_pass_system_math.gd` is the project's only automated test for the pass system.

**Controls** (see *InputMap* below for the full remap): while our team's controlled player is near/dribbling the ball —
| Action | Keyboard | Gamepad | Fires |
|---|---|---|---|
| Shot | `D` (hold to charge, release fires) | `X` button | `ball.kick()` via the existing commit-action path |
| Short ground pass | `X` | `A` button | `ChargeAction.PASS_SHORT` |
| Through ball (ground) | `W` | `Y` button | `ChargeAction.PASS_THROUGH` (leads a moving target) |
| Lob | `A` | `B` button | `ChargeAction.PASS_LOB` (ballistic arc) |
| Wall pass (give-and-go) | `Q`+`X` | `LB`+`A` | `ChargeAction.PASS_WALL` (short pass + passer runs for a return) |
| Through-air | `Q`+`W` | `LB`+`Y` | `ChargeAction.PASS_THROUGH_AIR` (leads + arcs) |
| Sprint | hold `Shift` | right trigger (analog) | higher `speed_scale` into `set_move_intent` (human only) |
| Context swap | `Q` | `LB` | swaps `controlled_player` **only when our team doesn't have the ball** (`_we_possess()`); with the ball, `Q`/`LB` is the pass-combo modifier instead — see `combo_modifier` in `_setup_inputs()` |

`combo_modifier` (`Q`/`LB`) is genuinely contextual, checked live every frame in `_physics_process()`: `not _we_possess()` → player swap; held while pressing `pass_short`/`pass_through` → the WALL/THROUGH_AIR variant instead of the plain one. There is no dedicated fifth button — the modifier doubles the three pass buttons into five pass types.

**Charge system** — `enum ChargeAction { NONE, SHOT, PASS_SHORT, PASS_THROUGH, PASS_LOB, PASS_WALL, PASS_THROUGH_AIR }` (replaces the old kick-only `_kick_charging` bool). One shared `power_bar` charge serves the shot and all 5 pass types, still entirely in `match_manager.gd` (charge-as-timer is input-specific — Фаза 3a only extracted the resolution, see *Conventions that will trip you up* below): `_start_charge(action, player)` on button-down, `_fire_charge()` on release or at max charge time, `_cancel_charge()` on early cancellation. Charge timing: `KICK_CHARGE_MAX_TIME` (still the local 0.5s constant, shot only) vs. `FootballConstants.PASS_CHARGE_MAX_TIME` (0.6s, all passes) — `_process()` picks the right max per `_charge_action`. `_fire_charge()` dispatches into `ActionExecutor`: `SHOT` → `_action_executor.fire_shot(...)` (power lerped `KICK_POWER_MIN..MAX`); anything else → `_action_executor.fire_pass(action, player, charge_ratio)`, which builds a `PassParams` via its own `_pass_params()`. Charge ratio's effect now differs by pass shape: for the two air types (`PASS_LOB`/`PASS_THROUGH_AIR`) it still lerps `PASS_POWER_CHARGE_MIN..MAX` as an arc-height multiplier; for ground types (`PASS_SHORT`/`PASS_THROUGH`/`PASS_WALL`) `_pass_params()` no longer sets a power at all — `fire_pass()` instead feeds `charge_ratio` straight into `PassSystem.ground_pass_speed()` once the real target distance is known, deriving speed from distance/time rather than a fixed multiplier (see *`PassSystem`'s functions* below for why).

**`PassParams`** (`scripts/match/pass_params.gd`, `class_name PassParams extends RefCounted`) is a plain data holder, not a constant-reading factory (kept autoload-free deliberately, for the headless test) — fields `power`, `peak_height`, `extra_lead`, `is_air`, `is_wall`, plus `enum PassType { SHORT_GROUND, THROUGH_GROUND, LOB, WALL, THROUGH_AIR }` (the enum exists for documentation/clarity; the params fields, not the type tag, drive behavior).

**`PassSystem`'s 8 functions**, all consumed from `ActionExecutor.fire_pass()`/`_maybe_flag_interceptor()`/`match_manager._process()` (telegraph):
- `select_target(passer_pos, aim_dir, mate_positions, mate_velocities, lead_gain, dot_bias, max_range) -> int` — auto-aim: scores each teammate by `dot(direction, aim) − dot_bias * (dist/max_range)`, aim being `ball.peek_dribble_direction()` from the telegraph (`ball.get_dribble_direction()` at actual fire time — see the read-only-getter note below). Returns index into the parallel arrays or `-1`.
- `lead_point(target_pos, target_vel, passer_pos, ball_speed, extra_lead) -> Vector3` — where to aim a "through" pass: travel-time-based lead off the target's current velocity, plus `extra_lead` meters further along that velocity direction. A stationary target (`vel≈0`) collapses to `target_pos` (extra_lead has nothing to lead along). `ball_speed` here is only `FootballConstants.PASS_LEAD_SPEED_ESTIMATE` (a rough constant), since the *real* launch speed isn't known until `ground_pass_speed` runs below — this is a deliberate approximation, not a bug.
- `launch_ground(from, to, power) -> Vector3` — flat velocity of magnitude `power` toward `to`. `power` is virtually always the output of `ground_pass_speed` below now, not a fixed per-type constant.
- `ground_pass_speed(distance, charge_ratio, min_time, max_time, min_speed, max_speed) -> float` — **the pass always reaches its target regardless of charge; charge only controls how fast it arrives.** Speed is derived, not absolute: `travel_time = lerp(max_time, min_time, charge_ratio)` (full charge → short travel time → fast/firm; empty charge → long travel time → slow/soft), then `speed = clamp(distance / travel_time, min_speed, max_speed)`. At a fixed charge, doubling the distance doubles the speed (same travel-time budget covers more ground faster) — this is what makes a 40m pass and a 10m pass both "arrive," just at different speeds. Added after the first playtest found fixed-power ground passes felt too weak over distance.
- `launch_lob(from, to, peak_height, gravity) -> Vector3` — ballistic arc landing at `to` with the given apex height (`vy = sqrt(2*g*h)`, flight time `T = 2*vy/g`, horizontal = flat distance / `T`). Assumes launch and landing at the same height (flat field). Already distance-safe by construction (horizontal speed = distance / a charge-derived flight time), unlike the old fixed ground power — no fix was needed here.
- `interception_time(pass_from, pass_to, ball_speed, opp_pos, opp_speed, corridor_half_width, corridor_spread) -> float` — deterministic corridor-projection geometry: projects the opponent onto the pass line, checks whether they're inside a corridor that widens with distance (`half_width + along*spread`) and can reach that point no later than the ball. Returns the intercept time or `INF` if unreachable — no randomness, no knowledge of `AI_INTERCEPT_CHANCE` (that's layered on by the caller).
- `scatter_degrees(spread_base, assist, distance, distance_ref) -> float` / `apply_scatter(flat_dir, spread_deg, rng) -> Vector3` — accuracy randomization. `scatter_degrees` grows with distance (clamped `0.2..1.5×` of `distance_ref`) and shrinks with `assist` (`0..1`, project currently ships `PASS_ASSIST = 0.75`). `apply_scatter` rotates the flat aim direction by a random angle in `±spread_deg` — **always via an explicit `RandomNumberGenerator` parameter** (`ActionExecutor._pass_rng`, moved off the manager in Фаза 3a), never global `randf()`, so tests can seed it.

**`ball.peek_dribble_direction() -> Vector3`** (`ball_controller.gd`) — a **read-only** twin of `get_dribble_direction()`. The latter has a side effect: it mutates `_dribbler_prev_pos`, the same field `_integrate_forces()` reads/writes every physics tick to compute dribble-following velocity. `_process()`'s telegraph marker calls the aim-direction getter every RENDER frame while charging — if it used the mutating getter, that per-frame call would race the physics tick and understate the dribbler's measured velocity, making the ball visibly lag behind the player during any pass charge (found and fixed after the whole-branch review, not caught by any single task's review). `peek_dribble_direction()` uses only the dribbler's current facing (no position-delta tracking) and is safe to call every frame. `ActionExecutor.fire_pass()`/`match_manager._start_charge()`/`_fire_charge()` still use the original mutating `get_dribble_direction()` — fine there, it's a one-shot call at a discrete moment, not a per-frame race.

**`ball.launch(velocity: Vector3) -> void`** (`ball_controller.gd`) — a mass-compensated impulse alternative to `kick(dir, power)`, for passes with a pre-computed launch vector (ground or ballistic). Lobs read on landing via the **manual ground-bounce** in `_integrate_forces` (see *Ground bounce* above — the `PhysicsMaterial.bounce` is `0.0`; the solver's restitution against the materialless floor was killing the vertical, so the bounce is reflected in code instead). In `ActionExecutor.on_action_contact()`, the existing `_action_power < 0.0` value is the sentinel that distinguishes a launch-pass from a kick (`ball.launch(_pending_launch)` vs. `ball.kick(_action_dir, _action_power)`) — keep that convention if you add a third impulse path.

**Telegraph marker** — while charging any pass (not the shot), a second yellow `MeshInstance3D` (`_target_indicator`, separate from the cyan controlled-player cone) tracks `PassSystem.select_target`'s current pick live, every `_process()` frame, so the human sees who they're about to pass to before releasing — it re-evaluates continuously as the player steers the aim stick, not just once at charge-start.

**Receive-assist** — while a human-controlled receiver's pass is inbound (`_receive_active` / `_receiver` / `_receive_timer`, still fields on `match_manager` — set via `begin_pass_receive()`, which `ActionExecutor.fire_pass()` calls when the receiver is/becomes `controlled_player`), `_handle_player_input()` **unconditionally** steers their movement input toward the ball's predicted position (`ball.global_position + ball.linear_velocity * PASS_RECEIVE_PREDICT_WINDOW`), overriding whatever the stick is doing. **There is no "steer away = deliberate dummy run" carve-out** — an earlier version respected a stick pointing away from the ball as intentional, but in practice the human's stick is almost always still aimed for the *previous* controlled player right after a handoff (they haven't had a chance to re-aim for the new one), so that carve-out mostly just made receivers run in the wrong direction. Fixed after the first playtest; if a genuine deliberate-dummy-run feature is wanted later, it needs a different signal than raw stick position at handoff (e.g. a sustained away-hold over several frames). The phase ends on catch, timeout (`PASS_RECEIVE_MAX_TIME`), losing control, or the receiver becoming invalid — checked every `_physics_process()`.

**Give-and-go (wall pass)** — a `PASS_WALL` charge (combo + short-pass button) sets `params.is_wall = true`; on fire, if a receiver was found, the passer's `begin_give_and_go(receiver_pos)` (on `teammate_ai.gd`, since the passer is AI-controlled once possession/`controlled_player` hands off to the receiver) adds them to group `giving_run` and sprints them into space (opposite side from the receiver) for `PASS_WALL_WINDOW` (3s), hoping for a return pass. **This sprint is the one deliberate exception to "AI doesn't sprint"** in this project (see *Locomotion* above). The wall-pass also bypasses the ball's own kick cooldown for the return via `ActionExecutor._clear_wall_pass_cooldown()` — a non-`await`ed coroutine (so it doesn't stall `fire_pass()` itself) that calls `ball.clear_last_kicker()` after 0.4s, letting the passer reacquire the ball before their own `_kick_cooldown_msec` would otherwise have expired. `giving_run` membership is cleared in `_finish_fall()` as a safety net (in case a wall-passer gets knocked down mid-run) as well as by its own timeout/catch/role-change check in `teammate_ai.gd`'s `_physics_process()`.

**Teammate receiving role** — `teammate_ai.gd` has `enum Role { SUPPORT, RECEIVING, CHASING }` plus `begin_receiving(pass_dir, lead)` / `end_receiving()` / `_move_to_receive()`: an AI-teammate "run onto the pass" mechanism. **Currently unreachable** in this 1-human + 1-AI-teammate prototype — `ActionExecutor.fire_pass()` always hands `controlled_player` to whoever receives a pass, so it's the human-side receive-assist above (not `Role.RECEIVING`) that actually delivers the "run onto the pass" feel today. `Role.RECEIVING` is live infrastructure for when the roster grows past 2 outfield players on our side. Separately, `_position_for_pass`'s support-run target was fixed to use `-Z` (this team attacks toward `-Z`) — it previously used `+Z`, which put the AI teammate behind the ball carrier instead of ahead.

**Honest interception** — `ActionExecutor._maybe_flag_interceptor(from, to, launch_vel)` runs `PassSystem.interception_time` (deterministic corridor geometry) against every `team_2` node at the moment a pass is fired; if some opponent could geometrically reach the corridor in time, a `_pass_rng.randf() > AI_INTERCEPT_CHANCE` roll decides whether they actually react (a miss chance, so it's not omniscient/instant), and if they do, `simple_ai.gd`'s `begin_intercept(point)` makes them run to the corridor intersection point after a reaction delay (`AI_INTERCEPT_REACT`, 0.3s) rather than teleporting or reacting instantly. **Reads the opponent's real speed off the node** (`opp_nodes[i].get(&"speed")`, i.e. `simple_ai.gd`'s `@export var speed`, default 8.0) — not `FootballConstants.AI_SPEED` (5.0), which is stale/unused legacy left over from before `PlayerMotor`; using the constant would make every feasibility check wrong.

**New constants** (`football_constants.gd`, "PASSING" section) — ground-pass speed (distance-derived, NOT a fixed power — see `PassSystem.ground_pass_speed` above): `PASS_GROUND_MIN_TRAVEL_TIME` (0.5s, full charge), `PASS_GROUND_MAX_TRAVEL_TIME` (1.4s, empty charge), `PASS_GROUND_MIN_SPEED`/`MAX_SPEED` (4.0/28.0 m/s safety clamps), `PASS_LEAD_SPEED_ESTIMATE` (12.0 m/s — a rough constant fed to `lead_point` before the real speed is known, NOT the actual launch speed). Air-pass arc height: `PASS_LOB_PEAK_HEIGHT` (3.0m), `PASS_THROUGH_AIR_PEAK_HEIGHT` (2.5m). Charge: `PASS_CHARGE_MAX_TIME` (0.6s), `PASS_POWER_CHARGE_MIN`/`MAX` (0.7/1.6× multiplier, air-pass height only). Auto-aim: `PASS_LEAD_GAIN` (0.25s), `PASS_THROUGH_EXTRA_LEAD` (4.0m — bumped from 2.0m after playtest feedback that through-balls didn't lead far enough ahead of the runner), `PASS_DOT_BIAS` (0.15), `PASS_MAX_RANGE` (45m). Interception corridor: `PASS_CORRIDOR_HALF_WIDTH` (1.2m), `PASS_CORRIDOR_SPREAD` (0.06 per meter). Accuracy: `PASS_SPREAD_BASE` (12°), `PASS_SPREAD_DIST_REF` (25m), `PASS_ASSIST` (0.75). Receive-assist: `PASS_RECEIVE_PREDICT_WINDOW` (0.08s — halved from 0.16s after playtest feedback that the receiver's assisted run overshot too far ahead of the ball's actual position), `PASS_RECEIVE_MAX_TIME` (2.0s). Give-and-go: `PASS_WALL_WINDOW` (3.0s), `PASS_WALL_RUN_FORWARD` (10.0m), `PASS_WALL_RUN_LATERAL` (6.0m). Opponent interception: `AI_INTERCEPT_REACT` (0.3s), `AI_INTERCEPT_CHANCE` (0.8).

## Goal net (procedural, physically-simulated)

**What it is.** Each goal is no longer a flat rectangle of posts — it's a volumetric box (front posts+crossbar **and** back posts+crossbar at depth `NET_DEPTH` behind the line) wrapped in a procedural cloth net that physically wobbles when the ball hits it. On a goal the ball flies into the net volume, settles, the net wobbles, and after a `NET_CELEBRATION_TIME` (5s) celebration everything resets. Modeled on OpenSoccer's `Nettest.gd` (Verlet spring-mass) but procedurally generated and headless-testable.

**Two-part split, mirroring the gameplay/presentation seam elsewhere:**
- **`scripts/match/net_sim.gd` (`class_name NetSim extends Object`)** — pure static math, **never reads `FootballConstants`** (all tuning passed in as params), so it's headless-testable like `PassSystem`/`PlayerMotor`. Two functions:
  - `build_box_net(width, height, depth, w_div, h_div, d_div, slack=1.0) -> Dictionary` — generates the 5-face box net (back/top/2 sides; bottom open) as **4 independent grid panels** (not one welded cloth — a deliberate simplification; each panel's outer ring is pinned to the frame, only interiors move). Returns parallel arrays `pos`/`rest`/`prev`/`normal` (`PackedVector3Array`), `pinned` (`PackedByteArray`), `edges` (`PackedInt32Array` index pairs), `rest_len` (`PackedFloat32Array`). `slack < 1.0` scales `rest_len` below the built spacing so the net has spare material to drape (rest *positions* stay taut — only target edge lengths shrink).
  - `integrate(net, ball_pos, ball_speed, p, dt) -> void` — one physics step, mutates `net["pos"]`/`net["prev"]` in place. Forces: gravity, shape-return toward rest positions, and a **velocity-gated** ball push (`max(0, ball_speed − ball_min_speed)` along the node normal — a *resting* ball produces zero push, so a ball sitting in the net doesn't perpetually wobble it). Then a **soft Position-Based-Dynamics constraint pass** (Jakobsen): `constraint_iterations` relaxation passes projecting each edge back toward `rest_len`, each correction scaled by `constraint_stiffness` (0..1). That constraint pass — not the legacy spring force — is the inextensibility model (cells don't stretch like rubber), and `constraint_stiffness` is the free↔rigid dial (1.0 = rigid wall, lower = lively wobble with bounded stretch). `p` is a plain dict; **its keys must exactly match what `GoalNet` builds** (`gravity`/`damping`/`stiffness`/`shape_return`/`ball_radius`/`ball_vel_scale`/`ball_force`/`ball_min_speed`/`constraint_iterations`/`constraint_stiffness`) — a missing key nil-indexes.
- **`scripts/match/goal_net.gd` (`extends MeshInstance3D`)** — one instance per goal, added under the goal group in `_setup_goals()`. Built in **local space** (mouth at local z=0, depth toward local +z); per-side world orientation is set externally via `rotation.y` (`PI` for Home, `0` for Away — matches the `ds` depth-sign of the back frame and colliders). API: `initialize(ball)`, `start_sim()`, `stop_sim()`. Renders the net as lines via `ImmediateMesh` (rebuilt each simulated frame). **Simulation is OFF by default** (`set_physics_process(false)`); only `start_sim()` (a goal) turns it on, `stop_sim()` resets nodes to `rest` and redraws the static shape. No idle/wind sway.

**Ball stop.** 4 thin `StaticBody3D` collider walls (back/top/2 sides; bottom + front mouth open), built via `_make_net_collider()`, on `BOUNDARY_COLLISION_LAYER` with a low-bounce/high-friction `PhysicsMaterial`, so the ball decelerates and settles inside the net volume instead of sailing to the boundary wall. The ball always masks `BOUNDARY_COLLISION_LAYER`, so the stop works regardless of `BallState`; the ball's `continuous_cd` prevents tunnelling through the thin walls. **Caveat:** field players *also* mask `BOUNDARY_COLLISION_LAYER`, so a player running into the net volume during the celebration is physically blocked by these walls (low-impact, self-heals on reset — give the stoppers a ball-only layer if it ever reads badly in play).

**Goal flow** (`_setup_goals()` `body_entered` closure + `_celebrate_then_reset()`): ball crosses the line → `_celebrating` guard (a single match-wide bool — blocks re-trigger while the ball settles, and protects *both* goals from a second score during the celebration), score++, `start_sim()` on the scored-into net (`_goal_nets[g.side]`), `_set_ai_frozen(true)` (below), then a **fire-and-forget** coroutine (`await get_tree().create_timer(NET_CELEBRATION_TIME).timeout`, called **without** `await` from the closure — same pattern as `_clear_wall_pass_cooldown`) waits 5s, then `_reset_ball()` + `stop_sim()` + clears the guard + `_set_ai_frozen(false)`. The human-controlled player, camera, and input keep running during the celebration (deliberate) — only **AI players stop** (see next).

**`_set_ai_frozen(on)`** — every `team_1`/`team_2` body except `controlled_player` (so every AI: opponents, teammate, keeper, and any free-kick-spawned/converted bodies) gets its own script's `_physics_process` disabled and its `PlayerMotor` control-locked (velocity snaps to 0, ignoring residual intent) on goal; both are restored when the celebration ends. Currently just a hard stop into idle — a placeholder for a future real celebration animation.

**Tuning** (`football_constants.gd`, `GOAL NET` section) — all iterated via playtest:
- Geometry: `NET_DEPTH` (1.5m), `NET_WIDTH_DIV`/`NET_HEIGHT_DIV`/`NET_DEPTH_DIV` (24/12/5 — finer than the initial 8/6/3, which looked angular).
- Feel knobs, in order of impact: **`NET_STIFFNESS`** (0.2 — the primary free↔rigid dial; lower = wobblier with more give, 1.0 = rigid wall), `NET_DAMPING` (0.98 — higher = wobbles longer), `NET_SLACK` (0.9 — lower = more drape/looser hang), `NET_SHAPE_RETURN` (3.0 — lower = wobble/drape lives longer), `NET_CONSTRAINT_ITERATIONS` (2 — higher = stiffer/less stretch).
- Other: `NET_GRAVITY` (9.8); `NET_SPRING_STIFFNESS` (400 — the legacy soft-spring force, now largely redundant/inert alongside the PBD constraints, kept but not the load-bearing mechanism); ball-push `NET_BALL_RADIUS`/`NET_BALL_VEL_SCALE` (0.4)/`NET_BALL_FORCE`/`NET_BALL_MIN_SPEED` (1.5); stopper `NET_BOUNCE`/`NET_FRICTION`; `NET_SIM_STEP` (0.016); `NET_CELEBRATION_TIME` (5.0s).
- **Test:** `tests/check_net_sim.gd` (headless) covers topology, integration (gravity sag, pinned immobility, velocity-gated push, resting-ball no-push, inextensibility under load, soft-vs-stiff give, slack scaling).

## Goalkeeper (`scripts/ai/keeper_ai.gd` + `scripts/match/keeper_logic.gd`)

**What it is.** One AI keeper, spawned into the Home goal by `match_manager._setup_keeper()` (so it defends the goal the human attacks). It holds the line, reacts to shots (catch on the spot / dive to a corner / tip over the bar), holds the ball in its hands, then distributes. Same gameplay/presentation split as everywhere: a `CharacterBody3D` + `PlayerMotor` + `PlayerVisual`, driven by `keeper_ai.gd`; **all geometry/timing math is pure functions in `keeper_logic.gd`** (`class_name KeeperLogic extends Object`, **never reads FootballConstants** — tuning passed in, headless-testable like `PassSystem`/`NetSim`).

**State machine** (`enum State`): `POSITION` (hold line, face the shooter, react) → `DIVE` (corner save) / `CATCHING` (central catch or `miss_top`) → `HOLD` (ball in hands) → distribution. Distribution has **three built variants, only one wired at a time** (the others kept as building blocks for the real game AI): `THROWING` (overhand throw — **currently active**), the placing-ball scenario (`PLACING`→`CARRY`→`FIELD_PASS`), and the low roll (`DISTRIBUTE`/`keeper_pass`) plus the drop-kick clear (`_do_clear`). `_hold()`'s exit call picks which — swap that one line to change distribution.

**Save detection & classification** (in `_position`):
- **Shot prediction** — `KeeperLogic.shot_intercept(ball_pos, ball_vel, goal_line_z, gravity, drag_xz, drag_y, dt)` integrates the trajectory **numerically with the ball's real drag** (`ball.drag_factor`/`air_resistance`) + gravity, NOT a naive `t=dz/vz` line. Critical: the ball's drag (`0.985`/frame ≈ −60% horizontal speed per second) makes real flight longer and land 0.3–0.5m lower than clean ballistics; the naive version over-estimated height and the keeper conceded on-target shots as "over the bar". Returns the ball position (no save) if it's travelling away or dies in drag before the line.
- **Gates** — reacts only to a ball `_heading_at_goal()` (own clears/throws travelling away are ignored — this kills the catch→distribute→re-catch loop), on-target within `KEEPER_ENGAGE_MARGIN` of the frame, after a `KEEPER_REACT` delay.
- **Central (lateral ≤ `KEEPER_REACH` = 0.85m)** — catch on the spot or tip over. `_should_catch_high(y)`: `y ≤ KEEPER_HIGH_CATCH_CERTAIN` (2.0) always catch; `y > KEEPER_JUMP_REACH` (2.5, just above the 2.44 crossbar) always `miss_top`; **in the 2.0–2.5 band a `KEEPER_HIGH_CATCH_CHANCE` (0.5) coin-flip, rolled once per shot** (`_high_roll`, reset on new detection). Catch clip by height (`_catch_clip_for_height`): `<0.6` scoop, `<1.3` catch, `<1.9` catch_head, else catch_top. **Anticipation:** the catch clip fires `KEEPER_CATCH_LEAD` (0.4s) before arrival (miss_top gets a longer `KEEPER_MISS_LEAD` = 0.75s — the upward jump has a longer wind-up) so the arms are up in time; the ball only actually sticks at the tight `_catch_radius_hit` (0.85m), so anticipation doesn't re-introduce the "vacuum" (keeper grabbing balls flying past).
- **Corner (lateral > reach)** — `_position` slides along the line to meet the ball if it can reach in time, else `KeeperLogic.save_decision(...)` picks `DIVE_LOW/HIGH_L/R` and `_begin_save` dives via manual `move_and_collide` **(horizontal only — the clip does the vertical jump; freezing the clip's vertical axis made the keeper "hover")**. `KeeperLogic.resolve_save` decides catch vs parry (`ball.parry`) by zone+speed.

**Ball in hands.** `ball.catch(holder, hold_node)` → `BallState.CAUGHT`, pinned every frame to `hold_node` — the **right-hand bone** via `PlayerVisual.get_hold_attachment()` (a `BoneAttachment3D` named `BallHold` on the `righthand` bone), so the ball moves with the hand through catch/hold/place/throw. A **caught ball can't score** — `_setup_goals`' goal-area closure guards `ball.is_caught()` (the hand can swing past the line while holding).

**Distribution — active = overhand throw.** `_to_overhand_throw` plays `keeper_overhand_throw` (ball stays glued to the right hand); on the animation's contact `_do_overhand_throw` launches it in an **arc** toward center: vertical from `KEEPER_THROW_PEAK` (6m), horizontal **drag-compensated** via `KeeperLogic.drag_horizontal_speed(distance, flight_time, drag, dt)` so it carries `KEEPER_THROW_DISTANCE` (25m) instead of falling short like a raw lob. Kept-but-unwired variants: **placing-ball** (`PLACING` plays `keeper_placing_ball`, ball stays on the hand as the clip lowers it to the grass → on contact hand off `CAUGHT`→`TRAPPED` via `set_dribbler(force=true)`; `CARRY` waits out the rest of the clip, THEN dribbles forward `KEEPER_PLACE_DRIBBLE_DIST` (10m) **1:1 as a field player**; `FIELD_PASS` fires a field-player ground pass via `PassSystem` on the shared `pass` clip's contact, then back to `POSITION`); the **low roll** (`keeper_pass`, released after 0.8s, `KeeperLogic.roll_speed(distance, drag, dt)` for a drag-accurate ground roll); and the **drop-kick clear** (`_do_clear`, `KEEPER_CLEAR_SPEED/LIFT`).

**Two ball-level fixes this required (`ball_controller.gd`):**
- **Pending-impulse ordering** — `_integrate_forces` applies the deferred launch impulse at the **start** of the function, before the state branches. Previously applied at the end, so a **standstill shot** (ball at rest when struck) was declared "flight ended" (`< FLIGHT_END_SPEED`) on frame 1 and dropped to `OPEN` before the impulse landed → the keeper never saw a shot. Run-up shots (ball already moving) hid the bug.
- **Anti-self-block kick grace** — on kick/launch the ball excludes the kicker from its collision for `KICK_GRACE_MSEC` (350ms) via `add_collision_exception_with`. A point-blank shot/clear/throw starts inside the striker's own capsule; without the grace the immediate contact fired `block_in_flight()` and silently killed the ball. (Also needed the standstill fix above to matter.)

**Constants** (`football_constants.gd`, `KEEPER` section): reach/thresholds (`KEEPER_REACH`, `KEEPER_JUMP_REACH`, `KEEPER_HIGH_THRESHOLD`, `KEEPER_HEAD_THRESHOLD`, `KEEPER_SCOOP_HEIGHT`, `KEEPER_HIGH_CATCH_CERTAIN`, `KEEPER_HIGH_CATCH_CHANCE`), timing (`KEEPER_REACT`, `KEEPER_CATCH_LEAD`, `KEEPER_MISS_LEAD`, `KEEPER_HOLD_TIME`), dive (`KEEPER_DIVE_*`, `KEEPER_SAVE_ERROR`, `KEEPER_ENGAGE_MARGIN`), distribution (`KEEPER_CLEAR_SPEED/LIFT`, `KEEPER_PASS_DISTANCE`, `KEEPER_PLACE_DRIBBLE_DIST`, `KEEPER_THROW_DISTANCE/PEAK`).

**Tests:** `check_keeper_logic.gd` (all `KeeperLogic` pure fns incl. drag-aware `shot_intercept`, `roll_speed`, `drag_horizontal_speed`), `check_keeper_clear.gd` (full catch→hold→distribute cycle — tracks whichever distribution is wired), `check_kick_grace.gd` (standstill self-block repro).

## Penalty (Phase A — `scripts/match/penalty_controller.gd` + `scripts/match/penalty_logic.gd`)

**What it is.** Press **P** (`penalty_debug` action) to stage a penalty into the attacked goal. Fixed 3rd-person camera behind the spot; a **yellow world-space ring** on the goal plane is the aim reticle (stick/arrows move it, hold **kick** to charge power — the ring grows with the spread); it **eases smoothly back to goal-center when the stick is released** (`PEN_RETICLE_RETURN`). Release fires a direct shot, or **`combo_modifier`+kick** (Q+D / LB+X) a chip. A **direct** shot flies to `aim + a uniform sample inside the spread disc` (bigger disc at higher power → miss more likely). For the **chip, power sets the landing distance** (short → drops in front, right → drops in, full → sails long/over the bar), so you can miss by power too. The keeper dives **blind** into a random one of 5 zones; a save only happens if the dive geometrically reaches the ball (existing dive/`resolve_save`/`KEEPER_SAVE_ERROR`) — guessing the side never guarantees a save. Direct + chip only (no curl in Phase A). Phases B (save as keeper) and C (shootout) are spec-only for now — see the spec.

**Same gameplay/pure-math split as everywhere.** `PenaltyController` (`extends Node`, added in `match_manager._ready`, `setup(...)`ed) runs the `SETUP→AIM→STRIKE` state machine; **all geometry is pure static funcs in `PenaltyLogic`** (`class_name PenaltyLogic extends Object`, **never reads `FootballConstants`**, headless-tested by `check_penalty_logic.gd`): `move_reticle`, `spread_radius`, `power_speed`, `sample_in_disc` (uniform via `sqrt(u)`), `plane_point_to_world`, `random_dive_zone`, `zone_target`, `enum Zone {LOW_L,HIGH_L,LOW_R,HIGH_R,CENTER}`. Launch vectors reuse `ShotSystem.ballistic_to` (direct) / `PassSystem.launch_lob` (chip — but its horizontal is **drag-compensated** via `KeeperLogic.drag_horizontal_speed`, since clean ballistics undershoots under the ball's drag; the chip aims a charge-scaled landing distance along the reticle direction, at ground level, so power = distance). All RNG via a seedable `_pen_rng`.

**The base controller runs ONE penalty and stays out of everything else.** It emits `struck` on contact and has `release_after_strike` (default `true` — single penalty). On the kicker's `action_contact` it launches the ball, calls `keeper.begin_penalty_dive(zone)`, then (single) **hands the ball straight back to normal play** — goal/save/miss are resolved by the existing systems (`GoalArea`→`_reset_ball` for a goal = "ball to center"), NOT by the controller. There is deliberately **no RESOLVE phase / no timeout / no outcome classification** in the base controller — that lives in the future shootout layer (`release_after_strike=false`).

**`match_manager` gating.** `_penalty_active` (+ `is_penalty_active()`); while true, `_physics_process` delegates to `_penalty.update(delta)` and returns (normal input/AI/dribbling skipped), `_process` parks `CameraPivot` at `_penalty_cam_pose` (fixed penalty view, set by the controller via `set_penalty_cam_pose`), and `set_field_ai_active(false)` idles the field AI (keeper stays live — it must dive). The kicker is the current `controlled_player`; `teammate_ai`'s `controlled_player==self` guard already keeps its own AI off the kicker. **P is ignored while `_celebrating`** — a pending `_reset_ball` (goal celebration) would teleport actors mid-penalty. On SETUP the controller **locks the kicker's motor + `set_face_direction(_forward)`** so it faces the goal even if P was pressed mid-run (else the motor keeps turning the body toward the leftover run velocity), and offsets it `PEN_FOOT_LATERAL` to the plant-foot side (right foot → left).

**Keeper penalty sub-mode** (`keeper_ai.gd`): `set_penalty_mode(true)` at SETUP **hard-resets the keeper from ANY prior state** (exit dive/one-shot via `recover`, release a held ball, snap to line-center, clear save flags) — needed because P can be pressed mid-dive/distribution/off-line — then holds center in `keeper_idle`, faces the field, **reactive sideways save OFF** (so it can't read the trajectory — the guess must be blind), but the **central-catch reflex stays ON**. `begin_penalty_dive(zone)` at contact: corner zones synthesize a `dec` and reuse `_begin_save`; **`CENTER` keeps the keeper central and lets the existing height reflex** (`_should_catch_high` + `_catch_clip_for_height` scoop/catch/catch_head/catch_top, or `miss_top` above the certain band) resolve a central shot — same rules as an in-game central shot. `_penalty_hold` auto-clears the mode once the ball is caught/past the line/flying away.

**Root-motion run-up (A1).** `penalty_kick_l`/`penalty_kick_r` (left/right foot, reused later for free kicks) are the only clips with a real ~3 m run-up — deliberately **NOT** in `IN_PLACE_CLIPS` (`merge_mixamo.py`), so their root translation survives. `PlayerVisual` enables `root_motion_track` on the Hips bone (`_find_root_motion_path` reads the track path straight from the clip — the AnimationTree's `root_node` is `../Model`, so no `Model/` prefix), and `consume_root_motion()` returns the per-frame horizontal advance in **game meters** — the raw `get_root_motion_position()` is in unscaled Hips-track units (import set no `motion_scale`), so it's multiplied by **`PEN_ROOT_SCALE`** (empirically calibrated by `tools/measure_penalty_runup.gd`: raw path to contact ↔ the ~3 m real Hips displacement). The controller pre-places the kicker `PEN_RUNUP_DIST` back and applies `consume_root_motion()` along `_forward` each strike frame (motor control-locked), so body+model arrive at the ball together with no foot-slide. **If the clips are ever re-exported, re-run `measure_penalty_runup.gd` and update `PEN_ROOT_SCALE`/`PEN_RUNUP_DIST`.** Kicker foot is `PEN_DEFAULT_FOOT` (`penalty_r`); the AIM stance is plain `idle` (no `hold_pose`). `ACTION_CLIPS`/`ACTION_TIMING` gained `penalty_l`/`penalty_r` — the strike timing (`contact`/`lock`/`speed`/`post_speed`, where `post_speed` speeds up the follow-through after the ball launches) lives in `ACTION_TIMING` (player_visual.gd), not in constants.

**Two root-motion gotchas (both bit us).** (1) `root_motion_track` is set **only for the penalty clip inside `trigger()`** (and for that clip only), NOT globally in `_build_anim_tree` — a global track extracts the Hips from **every** clip, which made `keeper_idle` float in the air and the dive clips lose their vertical jump (dive verticals live in the Hips track). (2) The track is cleared **after the return crossfade finishes** (`_playback.get_fading_from_node() == StringName()`), NOT at `lock` — clearing it mid-crossfade re-applies the clip's forward Hips pose and blends it into idle, so the body visibly **slid backward** into idle. The kick→idle return itself is a real crossfade (`_make_transition(false)`, IMMEDIATE+xfade), not `AT_END` (which doesn't blend — it holds the last frame then snaps).

**Constants** (`football_constants.gd`, `PENALTY` section): `PEN_RUNUP_DIST`, `PEN_ROOT_SCALE`, `PEN_DEFAULT_FOOT`, `PEN_FOOT_LATERAL`; aim (`PEN_RETICLE_SPEED`, `PEN_RETICLE_RETURN`, `PEN_RETICLE_START_Y`, `PEN_AIM_OVERHANG`, `PEN_SPREAD_MIN_R/MAX_R`); power (`PEN_POWER_MIN_SPEED/MAX_SPEED`, `PEN_CHARGE_MAX_TIME`); chip (`PEN_CHIP_PEAK_MIN/MAX`, `PEN_CHIP_DIST_MIN/MAX` — landing distance by charge); keeper zones (`PEN_KEEPER_DIVE_LOW_Y/HIGH_Y/LATERAL`); camera (`PEN_CAM_BACK/HEIGHT/LOOK_Y`). Strike timing (`contact`/`lock`/`speed`/`post_speed`) is in `ACTION_TIMING` (player_visual.gd), not here.

**Tests:** `check_penalty_logic.gd` (pure fns), `check_penalty_flow.gd` (headless smoke: `start_single`→`_fire`→ball launched + `_penalty_active` cleared). `tools/measure_penalty_runup.gd` is the run-up/scale calibration tool. The reticle-visibility flag `_reticle_visible` (always `true` in Phase A) is the seam for the future "hide reticle" toggle (Phase B fairness). **Interactive feel (aim, camera framing, run-up look, dive variety) needs a human running the game — headless can't drive input/rendering.** Spec: `docs/superpowers/specs/2026-07-15-penalty-design.md`; plan: `docs/superpowers/plans/2026-07-15-penalty-phase-a.md`.

## Goal kick (Phase A — `scripts/match/goal_kick_controller.gd` + `scripts/match/goal_kick_logic.gd`)

**What it is.** Press **G** (`goal_kick_debug` action, test trigger only — no rules-based auto-trigger yet) to stage a goal kick. **The one striking it is the KEEPER, not the human's field player** — the human drives the keeper's aim/strike for the duration of the set piece (`controlled_player` is left untouched, so control returns to the human's own team_1 player the instant the set piece ends). The controlled-player marker (the cyan cone) is simply **hidden** for the duration — it isn't about the keeper and isn't about `controlled_player` (nobody switched), so there's nothing correct to point it at. The ball is placed at the **center of the goal-area line** (not the kicker's own position, unlike free kick/corner). Same `SETUP→AIM→STRIKE` automaton and 3rd-person fixed camera as free kick/penalty/corner, but simpler: no wall, no shot-on-target option, no receiver hand-off — just two ball types, **ground pass (`pass_short`/A) or lob (`pass_lob`/B)**, charged by holding the button (distance/height scale with charge ratio, same `PassSystem.ground_pass_speed`/`launch_lob` + `KeeperLogic.drag_horizontal_speed` reuse as free kick/corner). The aim stick keeps rotating `_heading` **all the way through the run-up to contact** — not just before commit — so you can redirect the ball sideways as a late feint even after the camera has locked; the camera itself (`_cam_heading`) freezes the instant you press A/B, only the ball's launch heading keeps moving.

**Math lives in `GoalKickLogic`** (`class_name GoalKickLogic extends Object`, **never reads `FootballConstants`**, headless-tested by `check_goal_kick_logic.gd`): `spot_position(goal_line_z, into, ga_depth, ball_radius)` (center of the goal-area line), `runup_placement(spot, forward, runup_dist, foot_lateral, foot, body_y)` (keeper stands behind the spot facing up-field), `push_out_of_penalty_area(pos, goal_line_z, into, pa_depth, pa_half_width, margin)` (the opponent encroachment rule below), `push_out_of_goal_area(pos, goal_line_z, into, ga_depth, ga_half_width, margin)` (the everyone-out-of-the-box rule below — unlike `push_out_of_penalty_area`, `margin` here widens the check zone itself on BOTH axes, not just how far past the line the exit point lands). Everything else is reused as-is: `FreeKickLogic.rotate_heading` (aim), `PassSystem.ground_pass_speed`/`launch_ground`/`launch_lob`, `KeeperLogic.drag_horizontal_speed`.

**Two separate, deliberately different-scope clearing rules, same reasoning as the slide-tackle's two hit radii — one rule can't serve both jobs.** (1) **Opponent box** (`_clear_opponent_box`, `GK_ENCROACH_MARGIN`): symmetric by kicking side, not hardcoded to a team — `GoalKickController.start(kicker, goal_line_z)` reads the kicker's own group (`team_1`/`team_2`) and treats **the other group** as the opponents to clear, pushing every opponent inside the full 16.5m penalty area out past the line via `push_out_of_penalty_area`. This is why the test trigger works correctly even though it's the **team_2** keeper kicking (clearing **team_1**, i.e. the human's own players) — the same code will clear the opposite side unmodified once an AI opponent gets its own goal-kick behavior; there's no team_1/team_2 literal in the clearing logic itself. (2) **Goal-area buffer** (`_clear_goal_area_buffer`, `GK_CLEAR_MARGIN` = 5m): applies to **every field player of both groups, including the kicking team's own teammates** — nobody but the keeper may stand in the goal area or within 5m of it in any direction, via `push_out_of_goal_area`. This is strictly narrower in reach (10.5m from the line) than rule (1) for opponents (16.5m), so for opponents it's already redundant; what it actually adds is clearing the kicking team's **own** players away from right next to their keeper, which rule (1) never touched.

**Keeper goes passive for the duration** (`keeper_ai.gd`): `set_goalkick_mode(true)` at SETUP does a `set_penalty_mode`-style hard reset (exit any dive/one-shot via `recover()`, release a held ball, clear save-state flags, force `State.POSITION`) and then **early-returns out of `_physics_process` entirely** — no reactive save/positioning logic runs at all while the controller owns the body via root-motion + locked motor, unlike the penalty/free-kick keeper sub-modes which keep some reflex live. It also switches to `PlayerVisual.LOCO_STYLE_NORMAL` (plain idle), not the keeper's alert/ready stance — for this set piece the keeper is acting as a field kicker (run-up + strike, same as the other set pieces' kickers), so the goalkeeper stance would look wrong here. The action-contact handler (`_on_visual_contact`) also early-returns in this mode — needed because the keeper normally self-connects `action_contact` for its own distribution clips (`connect_action_signals=false` on the keeper's `PlayerConfig`, see *Player spawn factory* below), so without the guard both the keeper's own pass-roll logic and `GoalKickController`'s launch would fire off the same contact signal. `set_goalkick_mode(false)` at release just returns to `State.POSITION` — normal reactive logic (including the alert-stance switch back) resumes next physics tick.

**`match_manager` gating** mirrors free kick/corner exactly: `_goal_kick_active` (+ `is_goal_kick_active()`/`set_goal_kick_active()`), `_physics_process` delegates to `_goal_kick.update(delta)` and returns while active, `_process` parks `CameraPivot` at `_goal_kick_cam_pose`, charge-bar ownership is excluded from the manager's own charge gate. **G is ignored while `_celebrating`**, same reasoning as the other set pieces (a pending `_reset_ball` would fight the goal-kick teleport). The trigger passes `_keeper` as the kicker (not `controlled_player`) — this set piece is always keeper-driven regardless of who the human currently controls.

**Constants** (`football_constants.gd`, `GOAL KICK` section): `GK_RUNUP_DIST`, `GK_DEFAULT_FOOT`, `GK_FOOT_LATERAL`; aim (`GK_AIM_SPEED`, `GK_AIM_ARC` — single arc governs both pre-commit aim and the post-commit in-flight redirect, no separate "feint" constant); charge (`GK_CHARGE_MAX_TIME`); ground pass (`GK_GROUND_MIN_DIST`/`MAX_DIST`); lob (`GK_LOB_MIN_DIST`/`MAX_DIST`, `GK_LOB_PEAK_MIN`/`MAX`); clearing (`GK_ENCROACH_MARGIN` — opponent full-box push, 1m; `GK_CLEAR_MARGIN` — everyone-out-of-goal-area buffer, 5m); camera (`GK_CAM_BACK`/`HEIGHT`/`LOOK_Y`). Kicker foot defaults to `GK_DEFAULT_FOOT` and switches live during AIM via `foot_left`/`foot_right` (`_set_foot` re-runs `_place_kicker`) — same `penalty_l`/`penalty_r` clips and `foot_left`/`foot_right` actions as free kick/penalty/corner.

**Tests:** `check_goal_kick_logic.gd` (pure fns: spot placement, run-up placement, both push-out functions inside/outside their zones, including the goal-area buffer's width-only and depth-only padding cases). `check_goalkick_keeper_mode.gd` (keeper enters passive mode, its own `_physics_process` doesn't move the body while active, mode clears on demand). `check_goal_kick_flow.gd` (headless smoke: `start`→`_fire_charge`→ball launched + `_goal_kick_active` cleared — note the ball can legitimately travel the pitch length, bounce off the far end, and get caught by the same keeper within the test's multi-second window once released; that's expected physics, not a flow bug). `check_goal_kick_own_team_clear.gd` (a team_2 outfielder placed right next to the team_2 keeper gets pushed out to exactly `GOAL_AREA_DEPTH + GK_CLEAR_MARGIN` — proof the buffer rule doesn't exempt the kicking team's own players). **Interactive feel (aim redirect, camera framing, run-up, encroachment look) needs a human running the game — headless can't drive input/rendering.** Spec: `docs/superpowers/specs/2026-07-21-goal-kick-design.md`; plan: `docs/superpowers/plans/2026-07-21-goal-kick.md`.

## Presentation layer & asset pipeline

**Gameplay and presentation are separated on purpose.** The `CharacterBody3D` + its AI/input script + `CollisionShape3D` are the *gameplay* (position, physics, tackle, groups) and are untouched by the visual work. The *visual* is a `scenes/player_visual.tscn` instance added as a child. Never bake animation/model logic into the gameplay scripts.

**`PlayerVisual` (`scripts/player/player_visual.gd`)** — the node script on `player_visual.tscn`, which instances `assets/models/footballer.glb` as a child named `Model`.
- Builds an `AnimationTree` **in code**: a state machine with **idle / run / sprint** locomotion states (each run/sprint state is its own `AnimationNodeAnimation` → `AnimationNodeTimeScale` sub-tree, not a shared blend space) plus one-shot action states layered in. No hand-authored tree resource.
- **Two flavors of one-shot state**, both auto-registered only if the clip exists in the glb: `ACTION_CLIPS` (kick/pass/penalty/throw_in — semantic name → clip name, auto-return to `LOCOMOTION` at clip end via `trigger(action)`; **header clips were removed 2026-07-12** — the header/skidка feature was cut, see Status notes) and `ONESHOT_CLIPS` (`tackle`, `fallen_idle`, `roll_left`, `roll_right`, `standing_up` — the slide-tackle/fall chain, travel-only via `play_oneshot(clip)`, no auto-return; `match_manager.gd`'s fall state machine drives the chain and calls `recover()` at the end — plus the keeper save clips `keeper_body_block_l/r`, `keeper_diving_save_l/r`, `keeper_catch`, `keeper_catch_top`, `keeper_catch_head`, `keeper_scoop`, `keeper_miss_top`, `keeper_idle_ball`, driven by `keeper_ai.gd`). The keeper distribution/place/throw clips (`keeper_drop_kick`, `keeper_pass`, `keeper_placing_ball`, `keeper_overhand_throw`, and a `keeper_field_pass` timing alias on the shared `pass` clip) are `ACTION_CLIPS` with per-clip `ACTION_TIMING` — the ball is released/handed-off on the `action_contact` signal (see *Goalkeeper* above). `ONESHOT_CLIPS` members are also **fully cross-connected** to each other (not just star-wired through `LOCOMOTION`) — without that, `travel()` between two of them with no direct edge pathfinds through the hub and visibly flashes `idle` mid-transition (bit us between the last roll and `standing_up`).
- **Known quirk (harmless):** `ACTION_CLIPS` maps both `"kick"` and `"pass"` to the same clip name `"pass"` (kick's dedicated clip isn't wired in yet — see Status notes). The registration loop keys nodes/transitions by the *resolved clip name*, not the action key, and doesn't dedupe against `_states` the way the `ONESHOT_CLIPS` loop right after it does — so every `PlayerVisual._ready()` logs real (but non-fatal — the duplicate add is a silent no-op) Godot engine errors (`Condition "states.has(p_name)" is true` + two transition-duplicate errors). Visible in any headless run touching `PlayerVisual` (e.g. `check_player_visual_fall.gd`). Not yet fixed.
- **Locomotion speed is fed in by `PlayerMotor`** via `set_locomotion(velocity: Vector3)` every physics frame — `PlayerVisual` no longer measures its own speed off `global_position` delta (that was the old direct-position-movement era). State selection is by speed thresholds (`LOCO_RUN_ANIM_SPEED`, `LOCO_SPRINT_ANIM_SPEED`); within run/sprint, the clip's `TimeScale` is driven by `run_timescale(speed, top_speed, fudge) = (speed/top_speed)*fudge` (`LOCO_RUN_SCALE_FUDGE`) so the animation's stride matches actual movement speed — the anti-foot-slide fix. If `footballer.glb` has no `sprint` clip, the sprint state silently falls back to playing the `run` clip at a higher `TimeScale`.
- Public API (the intended gameplay→visual seam): `set_locomotion(velocity: Vector3)`, `set_lean(deg: float)` (rolls the `Model` node for body-banking — expects an already-smoothed value; `PlayerVisual` itself does not smooth), `apply_appearance(cfg: Dictionary)` (reads `cfg["kit_color"]` → whole-body albedo tint), `trigger(action)` (plays one-shot `pass` clip for both kick and pass — kick's own animation clip is planned), `play_oneshot(clip)` / `recover()` (the fall/tackle chain — see *Slide tackle & fall system* below), `set_flag(flag, on)`. Timing: `ACTION_TIMING` dict per action (`contact` = when `action_contact` fires, `lock` = when `action_finished` fires). `trigger()` no longer a stub.
- **Fallback:** if the model or its `idle`/`run` animations are missing, it spawns a plain capsule and warns — gameplay keeps working.
- Exports for visual fit: `model_y_offset` (`-0.5`, drop feet to ground since the body sits at `y=0.5`) and `model_yaw_deg` (`180`, Mixamo models face `+Z` but game-forward is `−Z`).
- **glTF gotcha:** imported animations arrive **unlooped** (`loop_mode = NONE`) and freeze after one cycle; `_build_anim_tree` sets `loop_mode = LOOP_LINEAR` on idle/run/sprint at runtime.

**Team color** is a whole-body `albedo_color` tint via `apply_appearance` (pilot-grade, not a real kit yet): team_1 = blue `Color(0.1,0.1,0.9)`, team_2 = red `Color(0.9,0.1,0.1)`.

## Player spawn factory & roster (Phase 1) + component brains (Phase 2)

Players are spawned through **one seam** — `PlayerFactory.spawn(config, team)` (`scripts/match/player_factory.gd`, static, `class_name PlayerFactory extends Object`) — which instantiates `scenes/player.tscn` (root `Player`, `scripts/player/player.gd`, `class_name Player extends CharacterBody3D` — a stable identity holder with `team_group`/`role`/`brain()`; children `PlayerVisual` → `PlayerMotor` → `CollisionShape3D`, fixed order — `PlayerMotor._ready()` finds `PlayerVisual` by scanning siblings once, so the order matters), tints the kit via `PlayerVisual.apply_appearance`, sets collision layers, registers the body into a `Team` node (`scripts/match/team.gd`, `class_name Team extends Node3D` — a `CharacterBody3D` needs a `Node3D` parent for correct transform propagation) as its child — group membership (`team_1`/`team_2` + `role_gk`/`role_def`/`role_mid`/`role_fwd`) and a `role` meta key are set by `Team.add_player`, not the factory directly — connects `PlayerVisual.action_contact/action_finished` to the manager (**skipped for the keeper** — `keeper_ai.gd` self-connects its own visual, see *Goalkeeper*), and attaches AI as a **child `Brain` component** (`scripts/ai/brain.gd`, `class_name Brain extends Node`, `ai_script.new()` → `add_child`) — **Phase 2, replacing the earlier `set_script`-on-the-body scheme**. Input to the factory is `PlayerConfig` (`scripts/match/player_config.gd`, `RefCounted`) — a thin data holder (`team_group`, `role`, `kit_color`, `spawn_pos`, `control_mode`, `ai_script`, `display_name`, `connect_action_signals`, `locomotion_style`, `extra_fields`) that, like `PassParams`/`FreeKickLogic`, never reads `FootballConstants` itself.

**Component brains (Phase 2).** `Brain` (`_body := get_parent()`, cached in `_ready()`) is the base class for `simple_ai.gd`/`teammate_ai.gd`/`keeper_ai.gd` — all three now `extends Brain`, not `extends CharacterBody3D`. Field brains drive movement through the base class's `_drive(dir, scale)`/`_stop()` (→ `PlayerMotor.find_on(_body).set_move_intent(...)`); every reference to the AI's own transform/physics/groups goes through `_body` (`_body.global_position`, `_body.is_in_group(...)`, `_body.move_and_collide(...)` for the keeper's dive) — never bare `self`/`global_position`, which would silently refer to the `Brain` `Node`, not the body. `MatchManager._ai_of(body) -> Node` is the manager-side bridge: returns `body.brain()` if present, else the body itself — every manager call-site that reaches into an AI's fields/methods (`wants_to_tackle`, `target_node`, `mark_target`, `controlled_player`, `speed`, `begin_intercept`, `begin_receiving`, `begin_give_and_go`) goes through it. The keeper is special-cased: `match_manager._keeper` / `penalty_controller._keeper` / `free_kick_controller._keeper` stay the **body** (freeze/keep-active exclusion, `n == _keeper` checks, ball-contact identity), while a parallel `_keeper_brain` field (`= _keeper.brain()`) carries the keeper's API/state (`goal_line_z`, `on_ball_contact()`, `set_penalty_mode()`, `begin_penalty_dive()`, `set_freekick_anchor()`, `clear_freekick_anchor()`, `_state`). **Gotcha (bit us during the conversion):** a body-typed variable's *static* type is `CharacterBody3D`, which has no `brain()` member — `var kb := k.brain()` fails to compile ("cannot infer the type") even though `k.brain()` resolves fine at runtime; declare the receiving variable explicitly (`var kb: Node = k.brain()`) instead of `:=`.

`Team` is the **authoritative gameplay roster** — `players()` (ordered, prunes freed bodies), `by_role(role)`, `keeper()`, `outfield()` (all non-GK) — while Godot groups remain the **physics index** (Area3D overlaps, tackle hit-checks, pickup loops). The factory is the only place that sets both, so the two structures can't drift apart. Two `Team` nodes live under the manager: `_team_home` (`team_group = &"team_1"`) and `_team_away` (`team_group = &"team_2"`), each carrying `manager`/`ball` so the factory doesn't need them passed separately.

**Spawn-ordering gotcha:** the factory sets `body.position` **before** `Team.add_player` (i.e. before the body enters the tree), on purpose. If you set `global_position` *after* `add_child`, every fresh body's physics body registers at the origin `(0,0,0)` and only the node moves — so a player whose spawn spot *is* the origin (the human at center) briefly overlaps the still-at-origin physics bodies of the other just-spawned players, and its `move_and_slide()` depenetrates it away (it teleports onto another body and rides on top at `Y+1.5`). Keep position-before-`add_child`.

**The old named singletons are GONE.** `player_home`/`player_teammate`/`player_away` no longer exist — query `_team_home`/`_team_away`/groups instead (e.g. `_away_outfielder()` — first non-keeper `_team_away` body — replaces the old `player_away` reads in the opponent's `target_node` and `DEBUG_MARK_TEAMMATE` wiring). `_human_player` is the one remaining meaningful singleton: the body the human controls by default (`controlled_player` starts there). `_reset_ball()` repositions every roster body from its factory-set `home_pos` meta (`_team_home.players() + _team_away.outfield()` — **the keeper is deliberately excluded**, same as before this refactor: it holds its line via `keeper_ai`'s own logic, not a hard reset). `scenes/match.tscn`'s old `$PlayerHome` scene node is gone too — the human player is now a factory product like everyone else.

**Keeper-specific nodes** (`SaveArea`, `HoldPoint`) aren't part of the shared `player.tscn` (field players don't need them) — `_setup_keeper()` creates and attaches them to the factory's returned body *after* the `spawn()` call, then sets the keeper's brain fields (`kb.goal_line_z`/`kb.save_area`/`kb.hold_point`/`kb.manager`) on `k.brain()`, not on the body. Free-kick wall/mate bodies (`free_kick_controller.gd`'s `_make_wall_body`/`_make_mate_body`) also go through the factory, with `ai_script = null` until `_convert_bodies()` **adds a `Brain` child** (`simple_ai`/`teammate_ai`, via `add_child`, not `set_script`) once the free kick resolves — the `fk_spawned` group marker and cleanup-on-next-kick logic are unchanged.

**Note:** `PlayerConfig`'s control-mode enum is named `ControlMode`, not `Control` — the latter collides with Godot's built-in `Control` UI node class and breaks external scripts' ability to resolve `PlayerConfig.control_mode` (`Could not resolve external class member`).

Tests: `check_player_config.gd`, `check_team_roster.gd`, `check_player_factory.gd`, `check_player_brain.gd` (see *Headless check scripts* above). **Phase 1 (factory/roster) and Phase 2 (AI as component brains) are both done** — see this section and *AI Brain components* above for the as-built reference. **Phase 3 step 3a (`ActionExecutor`) is done** — see *Kick/pass use a deferred-impulse* under *Conventions that will trip you up* below for the as-built reference. **Step 3b (`HumanBrain`** — making the human body's control a symmetric brain too, charge-as-timer moving off the manager) is a separate, not-yet-executed plan — see `docs/superpowers/specs/2026-07-19-player-spawn-factory-design.md`, `docs/superpowers/plans/2026-07-19-player-spawn-factory-phase-1.md`, `docs/superpowers/plans/2026-07-20-player-spawn-factory-phase-2.md`, and `docs/superpowers/plans/2026-07-21-player-spawn-factory-phase-3a.md` (the executed Phase 3a plan).

## Conventions that will trip you up

- **InputMap is built programmatically** in `match_manager.gd:_setup_inputs()`, which erases and recreates every action on `_ready()`. The bindings in `project.godot` are overridden and effectively dead. **Always edit `_setup_inputs()`, never `project.godot` input.** Movement is **arrows/left stick only** — WASD letters are freed for actions: `D`/gamepad-X = shot (hold to charge, release fires), `X`/`A` = short pass, `W`/`Y` = through ball, `A`/`B` = lob, `Q`/`LB` = context-sensitive (pass-combo modifier with the ball, player-swap without it — see *Passing* above), `Shift`/right-trigger (analog) = sprint (human only, no stamina), `Esc`/`Start` = pause, `1`/`3` = DEBUG camera toggle (broadcast/third-person — see *Field coordinate system* below). The old WASD-move / `E`-pass / unconditional-`Q`-swap scheme is gone.
- **Player movement is `velocity` + `move_and_slide()` via `PlayerMotor`** (see *Locomotion* above) — direct position manipulation is gone for regular locomotion. The slide tackle is the one remaining exception: it still moves the tackler with a manual `move_and_collide()` call in `match_manager.gd`, while the tackler's `PlayerMotor` is control-locked for the duration so the two motion systems don't fight.
- **Dribbling is continuous lead-follow** (ball held ahead, distance grows with speed; break-away → chase). See the *Ball model & dribbling* section above for the full model — this supersedes the old velocity-matching/spring description (and `SPRING_*`/`DRIBBLE_FORWARD_DIST` constants are now legacy/unused). Ignore OPENCODE.md's spring description.
- **Kick/pass use a deferred-impulse (commit-action) system**, not direct `ball.kick()`. The resolution lives in `scripts/match/action_executor.gd` (`class_name ActionExecutor extends Node`, Фаза 3a — extracted from `match_manager` as a companion node, same pattern as `PenaltyController`/`FreeKickController`, `setup(manager, ball)`-ed in `_ready`): `_action_executor.fire_shot()` / `.fire_pass()` (all 5 pass types, see *Passing* above) set `_action_player`/`_action_power`/`_kick_action_active=true` (now fields on the executor, not the manager), trigger the animation, and **wait** for `PlayerVisual.action_contact` — the factory still wires that signal straight to `match_manager._on_action_contact`/`_on_action_finished`, which are now thin one-line forwarders into `_action_executor.on_action_contact()`/`.on_action_finished()` — before calling `ball.kick()` (shot) or `ball.launch()` (pass — distinguished by the `_action_power < 0.0` sentinel). The manager reads the executor's commit state via two getters, `_action_executor.action_player()` / `.is_kick_action_active()`, instead of the old bare fields; `_fire_charge()`/`_try_fire_queue()` (still in the manager — charge-as-timer + the one-touch queue are input-specific, moving to `HumanBrain` in the future Фаза 3b) dispatch into `_action_executor.fire_shot()`/`.fire_pass()`. The executor calls back into the manager for shared helpers it doesn't own (`_aim_dir`, `_ai_of`, `_player_visual`, `_player_motor`, `_sync_ai_controllers`, `begin_pass_receive`, `controlled_player`, `_attack_dir_z`, `field_length`) — a `var x := _manager.some_method()` fails to compile ("cannot infer the type") because `_manager` is typed `Node`, which doesn't statically declare those methods (the same gotcha as `Player.brain()` in Фаза 2); use an explicit type (`var x: PlayerVisual = _manager._player_visual(...)`) instead of `:=`. No `set_control_locked()` during kick/pass — the `_kick_action_active` flag skips the motor-lock early-return in `_handle_player_input` instead, so movement/sprint/other-action inputs keep working while a kick/pass animation plays. Test: `tests/check_action_executor.gd`.
- **Shot = hold `D`/gamepad-X** for charge (up to `KICK_CHARGE_MAX_TIME` = 0.5s), release fires with power lerped 12–25. Passes share the same `power_bar` charge bar but a shorter max time (`FootballConstants.PASS_CHARGE_MAX_TIME` = 0.6s) — see *Passing* above for the five pass types. PowerBar (green→red gradient) visible during any charge. Auto-fires at max charge.
- **Movement is camera-relative** — input is transformed through `camera_pivot.global_transform.basis`, so "forward" means "away from the camera," not world-Z.
- **Controlled player** auto-switches to whichever team_1 player is dribbling; `Q`/`LB` switches manually **only while our team doesn't have the ball** (`_we_possess()` — with the ball, the same button is the pass-combo modifier instead; see *Passing* above), with a `_manual_swap_cooldown` to stop the auto-switch from immediately reverting it. A cyan cone indicator marks the controlled player; a yellow one (during pass charge only) marks the auto-aim's current target.
- **Team membership drives everything** via groups `team_1` (ours) / `team_2` (opponent); tackled players get a temporary `fallen` group. Use `_same_team()` and group checks, not node identity.

## Field coordinate system (FIFA-scale)

- Center at `(0,0,0)`. **Z = length (105m)**, **X = width (68m)**, Y = height. Half-extents: Z ±52.5, X ±34.
- **Goals are only ever on the Z axis** — Home at Z = −52.5, Away at Z = +52.5. Never place goals along X or Y.
- Our team attacks toward **−Z** (Home → Away).
- Camera is a fixed sideline/broadcast view: pivot parked at X = −40, follows the ball's Z, `look_at` the ball's Z on the centerline. **DEBUG toggle:** press `1` for this broadcast view (default) or `3` for a third-person view following `controlled_player` (positioned behind + above via `CAMERA_TP_DISTANCE/HEIGHT`, looking `CAMERA_TP_LOOK_AHEAD` ahead along the player's facing, smoothed by `CAMERA_TP_FOLLOW`) — added purely to make manual playtesting easier; penalty/free-kick still always use their own dedicated cameras regardless of this toggle. See `match_manager._process()` and the `CAMERA_TP_*` constants in `football_constants.gd`.
