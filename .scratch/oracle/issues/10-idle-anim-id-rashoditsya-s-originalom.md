# 10 — `GetIdleMovementAnimID` в порте выбирает не тот клип, что оригинал

Status: ready-for-human
Type: bug

**Найдено оракулом** при приёмке тикета 03 (первое сведение трасс, 2026-08-04). Ретроспективная
находка по фазам 1–3: код написан и принят человеком, ошибку не поймали ни компилятор, ни 25
headless-тестов, ни глаз.

**Симптом.** На **нулевом тике**, до всякой динамики, обе стороны стоят на своём idle-клипе кадра 0 —
и клипы разные:

```
эталон  P,0,26,1,movement/idle/000_idlelevel1,1128,movement,1,0,-1,0,0,0,9.473575,1.655500,...
порт    P,0,0, 1,autogen [v0 b0] => [v0 b0 a0]_mirror,512,movement,1,0,-1,1,0,0,9.473575,1.655500,...
```

Позиция, угол, кадр, `enum_velocity`, `quadrant_id` и оба смаггла совпадают до знака: стартовое
состояние поднялось верно. Расходятся ровно три поля, и все три — следствие одного выбора:
`anim_name`, `anim_id` и `foot` (у клипа эталона исходящая нога левая, у клипа порта правая).

**Манифесты при этом совпадают побайтово** — 1452 клипа, тот же порядок, те же имена, ноги и длины.
Значит дело не в загрузке коллекции и не в нумерации: `anim_id` 1128 и 512 указывают на разные
клипы в **одинаковых** коллекциях. Это ошибка в логике отбора, а не в данных.

**Причина по коду.** Правила разные.

Оригинал (`humanoidbase.cpp:875-947`) делает полноценный отбор: `CrudeSelection` по
`functionType = Movement`, `incomingVelocity = Idle`, `outgoingVelocity = Idle`, затем цепочка
`std::stable_sort` — сперва по близости числовой переменной `idlelevel` к 1
(`SetNumericVariableSimilarityPredicate("idlelevel", 1)`), потом по схожести входящего направления
тела с `(0, -1, 0)`, и дальше по остальным предикатам.

Порт (`AnimCollection.cs:130-138`) берёт первый попавшийся:

```csharp
for (int i = 0; i < _animations.Count; i++)
{
    var a = _animations[i];
    if (a.GetAnimType() == "movement" && a.GetIncomingVelocity() < 1.8f && a.GetOutgoingVelocity() < 1.8f)
    {
        _idleMovementAnimId = i; // фолбэк humanoidbase.cpp:1416
        break;
    }
}
```

Комментарий в порте ссылается на `humanoidbase.cpp:1416` — но там `GetIdleMovementAnimID()` только
**вызывается** как фолбэк, а сама функция живёт на `:875`. То есть портирована ссылка на место
вызова, а не тело. Первым в коллекции идёт автоген (`GenerateAutoAnims` стоит до файлового цикла),
поэтому порт и получает `autogen [v0 b0] => [v0 b0 a0]_mirror` с индексом 512 вместо файлового
`movement/idle/000_idlelevel1`.

**Почему это важно, а не косметика.** `GetIdleMovementAnimID()` — не только стартовый клип:
`humanoidbase.cpp:1416` подставляет его как **аварийный фолбэк отбора**, когда подходящего клипа не
нашлось (после странных столкновений, падений, невозможных углов тела). Каждое такое срабатывание
уводит порт на другой клип, с другой ногой и другим движением корня.

**Починено 2026-08-05.**

- [x] `GetIdleMovementAnimID` портирован телом: `CrudeSelection` (movement + incoming/outgoing
      velocity = Idle) и вся сорт-цепочка `humanoidbase.cpp:875-926` — `idlelevel`→1, входящее
      направление тела `(0,−1,0)`, входящая скорость Idle, затем `BodyDirectionSimilarity` по lookat
      в 10 м перед игроком и `MovementSimilarity`. Тело — в `AnimSelector` (там живут предикаты и
      `StableSort`), точка входа — `HumanoidBase.GetIdleMovementAnimID()`
- [x] На нулевом тике `anim_name`, `anim_id` и `foot` порта совпадают с эталоном:
      `movement/idle/000_idlelevel1`, id 1128, нога 0. **Совпадение держится 24 тика** — до тика 24
      все дискретные поля идут тик в тик, дальше расхождение уже другое (тикет 12)
- [x] Проверено, что фолбэк-ветка отбора зовёт то же самое: все четыре точки вызова оригинала
      (`humanoidbase.cpp:949`, `:1416`, `humanoid.cpp:1363`, `:1659`) теперь зовут одну и ту же
      функцию, как в оригинале
- [x] `dotnet build` чист (0 ошибок, 0 предупреждений), обе headless-валидации без новых категорий,
      набор `check_gpf_*` и `check_trace_diff` — `CHECK PASS`

**Blocked by:** None.

## Настоящая причина оказалась глубже «ссылки вместо тела»

Функция не просто выбирала не тот клип — она стояла **не на том объекте**. В оригинале это метод
`HumanoidBase`, и последние два сорта его цепочки читают `spatialState` (lookat считается от позиции и
угла игрока, `corneringBias` — от его скорости). То есть idle-клип **не свойство коллекции**, а функция
позы игрока, и кэшировать его при загрузке нельзя в принципе.

Поэтому починка — не подмена одной строки: `AnimCollection._idleMovementAnimId` и
`AnimCollection.GetIdleMovementAnimID()` **удалены**, а все пять мест, где порт их читал, переведены на
метод гуманоида.

## Вскрылась ошибка в спеке оракула, без починки которой пункт про нулевой тик недостижим

Спека велит порту ставить мяч из `B`-строки **с нулевым моментом** («сценарий фазы 5 мяча не касается,
и его движение на дифф не влияет»). Это неверно: сорт-цепочка отбора читает `Ball::Predict(200)` и по
порогу 16 м выбирает `desiredIdleLevel` (`humanoid.cpp:1565-1566`). На `walk_line` эталон видит 16.48 м
(мяч катится) и берёт уровень 1, а порт с замороженным мячом — 15.985 м и уровень 0, то есть **другой
idle-клип на нулевом же тике**. Момент мяча теперь берётся из той же `B`-строки; в трассе он уже был.

Перекладывать позицию мяча из трассы **каждый тик** сознательно не стали: это выключило бы физику мяча
порта, которую фаза 8 обязана мерить. Мяч стартует состоянием эталона и дальше живёт своей физикой.

Побочное следствие, которое стоит знать: **правило нулевого тика требует, чтобы мяч был дальше 16 м**.
Оно сверяет текущий клип с `GetIdleMovementAnimID()`, а ближе 16 м два отбора дают разные клипы, и
условие не наступает никогда — ровно так упал `check_gpf_trace.gd`, у которого мяч в фикстуре стоял в
6 м. У `walk_line` запас тонкий: 16.48 против порога 16.
