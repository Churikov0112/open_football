# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OpenFootball — a football (soccer) simulation game in Godot 4.7 / GDScript. Arcade rules, FIFA-scale pitch. Windows-only for now. Currently a small-scale prototype (human + AI teammate vs. one AI opponent), not yet 11v11.

**Art is now hybrid, no longer "procedural everything."** The pitch, field markings, goals, grass, and ball are still generated in code, but **players are real rigged Mixamo models** (skeletal idle/run animations) wrapped in a `PlayerVisual` node — the old colored capsules are gone. See *Presentation layer & asset pipeline* below.

## Commands

- **Validate (headless, no window, menu-load only):**
  `& "C:\Users\User\AppData\Local\Godot\Godot_v4.7-stable_win64_console.exe" --path "C:\Users\User\Desktop\projects\OpenFootball" --headless --quit`
- **Validate the match scene (headless, no window):**
  `& "C:\Users\User\AppData\Local\Godot\Godot_v4.7-stable_win64_console.exe" --path "C:\Users\User\Desktop\projects\OpenFootball" --headless --quit-after 2 res://scenes/match.tscn`
- **Run the game / open editor:** same exe without the `--headless` flags.

**Both headless commands above are needed, not just one — they catch different things.** Plain `--headless --quit` boots `main_menu.tscn` (the project's actual main scene) and never clicks Start, so it parses every globally-registered `class_name` script and autoload but **never loads `match.tscn`** — meaning `match_manager.gd`, `teammate_ai.gd`, and `simple_ai.gd` are never parsed by this command at all (verified empirically: injecting a syntax error into `match_manager.gd` and running plain `--quit` produced zero error output). The second command (`--quit-after 2 res://scenes/match.tscn`) directly instantiates `match.tscn`, so it's the one that actually exercises those three files. Known pre-existing baseline for the second command (unrelated to any specific feature — present before the pass-system branch): exactly 4 error categories, ~33× `ERROR: Condition "!is_inside_tree()" is true.`, ~6× `ERROR: Condition "transitions[i].from == p_from && transitions[i].to == p_to" is true.`, ~3× `ERROR: Condition "states.has(p_name)" is true.` (the harmless `ACTION_CLIPS` kick/pass duplicate-registration quirk, see *Presentation layer* below), ~1× `ERROR: Cannot get class 'WorldEnvironment3D'.`. When validating a change that touches match-only scripts, diff your error output against this baseline rather than expecting zero errors.

There are **no tests, no lint, and no CI** beyond the two headless commands above and the `tests/check_*.gd` scripts (see *Headless check scripts* below) — verify gameplay feel by actually running the game, since most logic is physics/timing-dependent and won't surface in a headless load.

## Architecture

**Entry flow:** `main_menu.tscn` (main scene) → Start button loads `match.tscn`. Do **not** treat `match.tscn` as a standalone entry point.

**One brain — `scripts/match/match_manager.gd`** (extends Node3D, root of `match.tscn`). This ~1000-line file owns nearly everything: input setup, camera tracking, procedural field markings/goals/grass/boundaries, controlled-player switching, kick/pass (with charge + deferred impulse system), and the entire slide-tackle state machine. When in doubt, the logic is here.

**Nodes are wired up in code, not in the scene.** In `_ready()`, `match_manager` procedurally spawns the away player and teammate as bare `CharacterBody3D`s, then `set_script()`s AI onto them. Even `PlayerHome` and the `Ball` get their scripts attached at runtime via `set_script()`/`preload()`. So `.tscn` files are minimal — grep the manager's `_setup_*` / `_give_*` functions to find where a node actually gets its behavior. Each field player (`PlayerAway`, `PlayerTeammate`, `PlayerHome`) also gets a `scenes/player_visual.tscn` instance added as a child for its rigged model + team-color tint (see next section).

**Scripts attached at runtime:**
- `scripts/ai/simple_ai.gd` — opponent (team_2, **red**): chases ball/target, dribbles toward goal, shoots, can request tackles.
- `scripts/ai/teammate_ai.gd` — used for **both** the teammate **and** `PlayerHome` when it's not the human-controlled player (team_1, **blue**). Positions for a pass / chases ball.
- `scripts/ball/ball_controller.gd` — ball physics + dribbling.
- `scripts/camera/match_camera.gd` — camera.
- `scripts/player/player_controller.gd` — exists but note `PlayerHome` is driven by `match_manager` input + `teammate_ai`, so check what's actually attached before assuming this runs.
- `scripts/player/player_visual.gd` (`class_name PlayerVisual`) — the presentation layer attached to `scenes/player_visual.tscn`. Not an AI/gameplay script; see next section.
- `scripts/player/player_motor.gd` (`class_name PlayerMotor`) — the locomotion component. Added as a **third child** of every field player's `CharacterBody3D` (alongside `PlayerVisual` and the collision shape), in that order — `PlayerVisual` must exist first, since `PlayerMotor._ready()` finds it by scanning siblings once. Owns all movement physics; see *Locomotion* below.

**Constants:** `scripts/data/football_constants.gd` is autoloaded as `FootballConstants` (global). Central place for field dimensions, ball/player/AI/tackle/locomotion (`LOCO_*`) tuning. **Caveat:** `match_manager.gd` also hardcodes `KICK_CHARGE_MAX_TIME = 0.5`, `KICK_POWER_MIN`, `KICK_POWER_MAX` locally and kick range `2.0` inline — when tuning, grep both locations. (Kick power is currently a **temporary** stronger/flatter placeholder — `18/34` — for wall testing; the real aimed shot is Phase 1.) (Player top speed comes from `FootballConstants.LOCO_TOP_SPEED` via `PlayerMotor`.)

## Locomotion (`PlayerMotor`)

**Player movement is velocity + inertia via `move_and_slide()`, not direct position manipulation.** `scripts/player/player_motor.gd` (`class_name PlayerMotor`) is a component node — every field player's `CharacterBody3D` gets one as a child, and it owns 100% of that body's movement physics. Callers (human input in `match_manager.gd`, both AI scripts) never touch `global_position`/`rotation` for movement anymore — they only call `motor.set_move_intent(dir, speed_scale)` with a desired world-space direction, once per frame. The motor internally: integrates velocity toward the desired speed (`LOCO_ACCEL` accelerating, `LOCO_DECEL` decelerating — asymmetric, so releasing input glides rather than snapping to a stop), smooth-turns the body's yaw toward the velocity direction (`LOCO_TURN_ROT`, gated below `LOCO_TURN_MIN_SPEED` so it doesn't spin on the spot), computes a **smoothed** lean/bank angle from lateral acceleration and feeds it to `PlayerVisual.set_lean()` (smoothed via `PlayerMotor.smooth_scalar()` at `LOCO_BANK_SMOOTH` — the raw per-frame value is jumpy because WASD input direction snaps instantly, not analog), calls `move_and_slide()`, then pins `global_position.y` to the spawn height every frame (the field is flat) **except while `fallen`** (so a slide-tackle knockback's vertical pop isn't instantly flattened).
- `set_control_locked(on)` — used during commit-actions (pass/kick) and the tackler's own slide: when locked (or the body is in group `fallen`), velocity snaps to **zero immediately** (not a gradual decel) so the body doesn't keep drifting on residual velocity while something else (a hand-authored animation lock, or the tackle's own `move_and_collide()`) is supposed to own the motion that frame.
- Sprint (**hold Shift**) is just a higher `speed_scale` passed into `set_move_intent` by the human-input path in `match_manager.gd` — AI does not sprint.
- `PlayerMotor.find_on(node)` (static) is the canonical "find my sibling motor" lookup — used by both AI scripts and `match_manager._player_motor()`; don't re-scan `get_children()` by hand.
- **Collision layers — three deliberately separate groups.** Default layer 1 holds the pitch and the ball (kept there so goal/tackle-`Area3D` detection, which checks `body == ball`, isn't disturbed). Field players are on `FootballConstants.PLAYER_COLLISION_MASK` (bit 2) with a `collision_mask` of `PLAYER_COLLISION_MASK | BOUNDARY_COLLISION_LAYER` — **not** layer 1 — so `move_and_slide()` makes them push off each other and off the boundary walls. The boundary walls (`_setup_boundaries()`) are on their own `FootballConstants.BOUNDARY_COLLISION_LAYER` (bit 3) precisely so they're invisible to the ball's *layer* but the ball still masks them in to physically bounce off them.
- **Ball↔player collision is FLIGHT-gated** (see *Ball model & dribbling* below). The player mask never includes the ball's layer (players walk freely). The ball's `collision_mask` base is `1 | BOUNDARY_COLLISION_LAYER` (no players); `ball_controller._set_player_collision(true)` adds the player bit **only while the ball is in `FLIGHT`** (after a kick/pass) so a shot/pass physically collides with players (block/intercept) — and removes it on trap/loose/flight-end so a dribbled or picked-up ball is transparent to capsules. This is the deliberate fix for the `78990c8` class of bug (a player mask that includes the ball's layer, or an always-on ball↔capsule collision, shoves the dribbled/loose ball off the player's own capsule → close-control stutter + spawn shove). If you add a new physics body, decide deliberately which group it sees.

## Ball model & dribbling (`ball_controller.gd`) — Phase 0, OpenSoccer-derived

This replaces the old velocity-matching / spring dribbling described in OPENCODE.md. Migrated on the `feat/kick` branch; **CLAUDE.md here is the source of truth**.

- **State machine:** `enum BallState { OPEN, TRAPPED, FLIGHT, CAUGHT }` (`ball.state`). `OPEN` = loose, `TRAPPED` = dribbled by `ball.dribbler` (a.k.a. `ball.player()`), `FLIGHT` = struck (kick/pass/curl), `CAUGHT` = reserved (keeper, unused). Possession API is the legacy `set_dribbler()/release_dribble()/dribbler` kept as thin wrappers over the state machine (AI scripts read `ball.dribbler` unchanged); `player()` is the neutral getter. `set_dribbler(node, force=false)` — `force` skips the release/kicker cooldowns (used by the pass receiver, below).
- **Dribbling is continuous *lead-follow*, NOT velocity-matching or discrete pushes.** In `_integrate_forces` (TRAPPED branch): the ball is steered to a point ahead of the dribbler at a distance that **grows with player speed** (`DRIBBLE_LEAD_BASE + speed*DRIBBLE_LEAD_PER_SPEED`) — tight at the feet when slow, far ahead when sprinting. Ball velocity = player velocity + spring toward that point (`DRIBBLE_CONTROL_GAIN`), lerp-smoothed (`DRIBBLE_CONTROL_LERP`) for a living lag. Direction of the lead point = `_dribble_intent` (the human's stick, via `set_dribble_intent(dir, push_extra)`) or the dribbler's facing (AI). Sprint adds lead (`DRIBBLE_SPRINT_PUSH_EXTRA`) **and** a smooth random imprecision (`DRIBBLE_SPRINT_WOBBLE_*`) — speed traded for accuracy.
- **Break-away + chase:** when the ball gets farther than `DRIBBLE_CHASE_DIST` (sprint overshoot / deflection), it free-rolls with `DRIBBLE_ROLL_DRAG` and `should_chase()` flips true; the human-input path in `match_manager._handle_player_input` then **auto-runs the controlled player to the ball** (stick can still nudge the heading by `DRIBBLE_CHASE_STEER` to go around a defender). Back within `DRIBBLE_CATCH_DIST` → control resumes (hysteresis). Possession is **not** lost from your own push/turn — only via external factors (tackle/intercept); the distance release (`DRIBBLE_KEEP_DIST = 15`) is a far-out safety net.
- **`set_dribble_suppressed(on)`** — while charging/committing a pass or shot, the dribble is suppressed (ball waits at the feet) so the action is a single clean touch, not "dribble-push + pass". Also suppressed when the human releases the stick (player runs to the ball and stops instead of dribbling on inertia).
- **Loose-ball pickup magnetism:** off the ball, the controlled player's movement is nudged toward a nearby slow loose ball (`PICKUP_ASSIST_RADIUS/STRENGTH`) so you don't have to aim exactly.
- **Pass reception:** the intended pass receiver traps the ball at **any speed**, bypassing the trap speed-gate and the 500 ms release cooldown (`set_dribbler(receiver, force=true)`), so firm or short/quick passes don't sail past the teammate. General pickup still requires a slow ball (`BALL_TRAP_MAX_SPEED = 9`).
- **Flight-gated collision + block:** the ball collides with players only in `FLIGHT` (see *Collision layers* above); `continuous_cd = true` stops fast shots tunnelling. On a flight contact with a player, `match_manager._on_ball_collision` → `ball.block_in_flight()` (damp ×0.25, clear curl, drop to `OPEN`, collision off) — no elastic bounce, no possession handoff. Flight ends when speed < `FLIGHT_END_SPEED` (2.0, deliberately far below the trap gate so a fast ball stays blockable).
- **Magnus / curl:** `launch_curl(velocity, curl)` sets `_curl`; `_integrate_forces` applies a per-frame side+lift impulse (`MAGNUS_FORCE`, decaying by `MAGNUS_DECAY`) while in flight. **Infrastructure only** — no gameplay action calls `launch_curl` yet (the curl shot is Phase 1); `kick()/launch()` clear `_curl`.
- **Test:** `tests/check_ball_state.gd` (headless) covers the state transitions + `launch_curl`.
- **Constants** live in `football_constants.gd` under DRIBBLING / BALL / SHOOTING sections. **`DRIBBLE_FORWARD_DIST`, `DRIBBLE_HEIGHT`, all `SPRING_*` are legacy/unused now** — ignore them.
- **TEMPORARY test scaffolding (revert before finishing Phase 0):** `FootballConstants.DEBUG_DISABLE_OPPONENT = true` makes the AI opponent stand still (gated in `simple_ai._physics_process`) and spawns two walls of standing dummy opponents (`_spawn_wall_dummies`) for shot/block testing. The placeholder kick is also tuned stronger/flatter (`KICK_POWER_MIN/MAX = 18/34`, low `dir.y`) — the real aimed shot is Phase 1.

## Slide tackle & fall system

All in `match_manager.gd`, driven by two independent state enums: `TackleState` (`NORMAL`/`SLIDING`/`RECOVERING`) and `FallState` (`NONE`/`KNOCKDOWN`/`ROLL_1`/`ROLL_2`/`GETUP`). **Both `_tackle_state` and `_tackle_player` are single match-wide fields, not per-player** — when checking "is a tackle happening," always compare `controlled_player == _tackle_player` too, not just `_tackle_state != NORMAL`, or you'll block/affect players who have nothing to do with the tackle in progress (bit us in `_handle_player_input`).

- **Starting a slide** (`_start_tackle(player, target=null)`, called by human input via `_try_tackle()` or by AI via `_poll_ai_tackles()` polling each `team_2` node's `wants_to_tackle` flag): locks the tackler's `PlayerMotor`, plays the `tackle` one-shot, and aims `_tackle_dir` at `target` (defaults to `ball`) **with simple lead prediction** — `predicted_pos = target.global_position + target_velocity * (distance/SLIDE_TACKLE_SPEED)` — since the ball lead-follows its dribbler (see *Ball model & dribbling*), this leads a moving target instead of aiming at a stale position and sliding through empty space once the ~0.4s slide is over. No iterative closing-time solve, just one first-order estimate.
- **During the slide** (`_tackle_slide()`), the tackler's body physically moves via manual `move_and_collide()` (not `move_and_slide()` — the one deliberate exception to normal locomotion) while its own `PlayerMotor` stays control-locked so the two motion systems don't fight.
- **Two separate, deliberately different-radius hit checks**, because one radius can't serve both jobs without either whiffing the ball or knocking players down from a visible gap:
  - **Ball reach** — the wide `TackleArea` (`Area3D`, radius `SLIDE_TACKLE_AREA_RADIUS = 1.5`), `body_entered` → `_on_tackle_body_entered()`. Only reacts to `body == ball` now (clean tackle: pops the ball via `ball.kick()`, ends the slide). Its `collision_mask` must explicitly include `FootballConstants.PLAYER_COLLISION_MASK` (bit 2) as well as the ball's default layer 1 — Area3D's default mask is layer-1-only, so without that bit it silently never sees player bodies at all (an easy, silent way to make hit detection dead on arrival).
  - **Player knockdown** — a *much* tighter check, `_check_tackle_player_hit()`, polled every slide frame against `_tackle_area.get_overlapping_bodies()` but gated at `SLIDE_TACKLE_HIT_RADIUS = 0.9` (≈ sum of both capsule radii + a small margin) so a fall only triggers on visible capsule contact, not from ~1.5m away. Genuine `move_and_collide()` physical contact with an opposing player (checked first, in `_tackle_slide()`) also knocks them down directly, unconditionally — that path is exact contact by construction.
  - Both knockdown paths call `_on_tackle_hit_player(body, normal)` → `_begin_fall(body, normal)`.
- **Not yet a foul.** `_on_tackle_hit_player()` sets `_tackle_clean = true` unconditionally — no free kick is awarded for knocking someone down. `_tackle_foul_position` / `_tackle_fouled_player` and the free-kick branch in `_tackle_recover()` are wired up but currently unreachable; needs a "ball won first vs. body hit first" rule (see `docs/football_reference.md` §9) before it's meaningful to re-enable.
- **Victim fall chain** (`_begin_fall()` → `_process_fall()`): `KNOCKDOWN` (plays `fallen_idle`, knocked-back over `KNOCKDOWN_TIME`) → `ROLL_1`/`ROLL_2` (`roll_left`/`roll_right`, picked by which side they were hit from) → `GETUP` (`standing_up`) → `_finish_fall()` (removes `fallen` group, unlocks motor). **This is animation-driven, not physics.** An earlier physics-ragdoll approach (`scripts/player/ragdoll_skeleton.gd`, `PhysicalBone3D`) was built and then deliberately ripped out because it didn't play nice with the scaled Mixamo import — that file and its tests (`check_ragdoll_build.gd`, `check_ragdoll_real_skeleton.gd`) still exist and still pass, but **nothing in the active game calls them**; don't treat their presence as evidence ragdoll is live. While `fallen`, `PlayerMotor` doesn't touch vertical position (see *Locomotion* above) so the knockback's vertical pop isn't instantly flattened.
- **Tuning** (`football_constants.gd`): `SLIDE_TACKLE_SPEED = 9.0` (deliberately above the opponent AI's real run speed — see `simple_ai.gd`'s `speed` export, currently `8.0` — and above the human's own non-sprint top speed, so either side can close a gap; the human's sprint at `12.0` still lets them outrun a chasing AI tackle), `SLIDE_TACKLE_RANGE = 4.0`, `SLIDE_TACKLE_RECOVERY_TIME = 1.3` (slide + recovery together land close to the `tackle` clip's ~1.8s length so the animation and the commit-window roughly agree), `AI_TACKLE_RANGE = 2.0` / `AI_TACKLE_COOLDOWN = 2.0` (AI's own decision-to-attempt distance/cooldown — kept short since lead-prediction error grows with distance). `SLIDE_TACKLE_INPLACE` (currently `false`) is a diagnostic-only flag that skips `move_and_collide()` during the slide (tackler stays stationary while the clip plays) — useful for isolating whether a visual issue is in the animation or the physical slide; leave it `false` for normal play.
- **`tools/merge_mixamo.py`'s `IN_PLACE_CLIPS`** freezes root-motion translation on specific *Blender-local* bone axes for `tackle`/`roll_left`/`roll_right` so the baked-in mocap translation doesn't double up with the manual `move_and_collide()` above. Getting the axis choice wrong is easy and doesn't look like an axis bug at first — it looks exactly like "the player floats/hovers in the air." Blender's `automatic_bone_orientation` reorients each bone's local axes away from world axes, and glTF export further permutes which local index ends up in which exported track component — so "index 2 = vertical" (the assumption baked into the old code/comments) was wrong twice over. If you ever touch `IN_PLACE_CLIPS`, verify empirically (sample the built glb's actual `Position3D` track values across the clip, e.g. via `Skeleton3D.get_bone_pose()` in a throwaway headless script) rather than trusting axis-index assumptions from the source rig.

## Passing

Five pass types plus the shot share one charge system, all fired from `match_manager.gd`. The math lives in `scripts/match/pass_system.gd` (`class_name PassSystem extends Object`) — **pure static functions, never read `FootballConstants`** (tuning is always passed in as parameters) — so they're headless-testable without an autoload; `tests/check_pass_system_math.gd` is the project's only automated test for the pass system.

**Controls** (see *InputMap* below for the full remap): while our team's controlled player is near/dribbling the ball —
| Action | Keyboard | Gamepad | Fires |
|---|---|---|---|
| Shot | `D` (hold to charge, release fires) | `X` button | `ball.kick()` via the existing commit-action path |
| Short ground pass | `X` | `A` button | `ChargeAction.PASS_SHORT` |
| Through ball (ground) | `W` | `Y` button | `ChargeAction.PASS_THROUGH` (leads a moving target) |
| Lob | `A` | `B` button | `ChargeAction.PASS_LOB` (ballistic arc) |
| Wall pass (give-and-go) | `Q`+`X` | `LB`+`A` | `ChargeAction.PASS_WALL` (short pass + passer runs for a return) |
| Through-air | `Q`+`W` | `LB`+`Y` | `ChargeAction.PASS_THROUGH_AIR` (leads + arcs) |
| Sprint | hold `Shift` | right trigger (analog) | higher `speed_scale` into `set_move_intent` (human only) |
| Context swap | `Q` | `LB` | swaps `controlled_player` **only when our team doesn't have the ball** (`_we_possess()`); with the ball, `Q`/`LB` is the pass-combo modifier instead — see `combo_modifier` in `_setup_inputs()` |

`combo_modifier` (`Q`/`LB`) is genuinely contextual, checked live every frame in `_physics_process()`: `not _we_possess()` → player swap; held while pressing `pass_short`/`pass_through` → the WALL/THROUGH_AIR variant instead of the plain one. There is no dedicated fifth button — the modifier doubles the three pass buttons into five pass types.

**Charge system** — `enum ChargeAction { NONE, SHOT, PASS_SHORT, PASS_THROUGH, PASS_LOB, PASS_WALL, PASS_THROUGH_AIR }` (replaces the old kick-only `_kick_charging` bool). One shared `power_bar` charge serves the shot and all 5 pass types: `_start_charge(action, player)` on button-down, `_fire_charge()` on release or at max charge time, `_cancel_charge()` on early cancellation. Charge timing: `KICK_CHARGE_MAX_TIME` (still the local 0.5s constant, shot only) vs. `FootballConstants.PASS_CHARGE_MAX_TIME` (0.6s, all passes) — `_process()` picks the right max per `_charge_action`. `_fire_charge()` dispatches: `SHOT` → the pre-existing kick path (power lerped `KICK_POWER_MIN..MAX`); anything else → `_fire_pass(action, player, charge_ratio)`, which builds a `PassParams` via `_pass_params()`. Charge ratio's effect now differs by pass shape: for the two air types (`PASS_LOB`/`PASS_THROUGH_AIR`) it still lerps `PASS_POWER_CHARGE_MIN..MAX` as an arc-height multiplier; for ground types (`PASS_SHORT`/`PASS_THROUGH`/`PASS_WALL`) `_pass_params()` no longer sets a power at all — `_fire_pass()` instead feeds `charge_ratio` straight into `PassSystem.ground_pass_speed()` once the real target distance is known, deriving speed from distance/time rather than a fixed multiplier (see *`PassSystem`'s functions* below for why).

**`PassParams`** (`scripts/match/pass_params.gd`, `class_name PassParams extends RefCounted`) is a plain data holder, not a constant-reading factory (kept autoload-free deliberately, for the headless test) — fields `power`, `peak_height`, `extra_lead`, `is_air`, `is_wall`, plus `enum PassType { SHORT_GROUND, THROUGH_GROUND, LOB, WALL, THROUGH_AIR }` (the enum exists for documentation/clarity; the params fields, not the type tag, drive behavior).

**`PassSystem`'s 8 functions**, all consumed from `_fire_pass()`/`_maybe_flag_interceptor()`/`_process()` (telegraph):
- `select_target(passer_pos, aim_dir, mate_positions, mate_velocities, lead_gain, dot_bias, max_range) -> int` — auto-aim: scores each teammate by `dot(direction, aim) − dot_bias * (dist/max_range)`, aim being `ball.peek_dribble_direction()` from the telegraph (`ball.get_dribble_direction()` at actual fire time — see the read-only-getter note below). Returns index into the parallel arrays or `-1`.
- `lead_point(target_pos, target_vel, passer_pos, ball_speed, extra_lead) -> Vector3` — where to aim a "through" pass: travel-time-based lead off the target's current velocity, plus `extra_lead` meters further along that velocity direction. A stationary target (`vel≈0`) collapses to `target_pos` (extra_lead has nothing to lead along). `ball_speed` here is only `FootballConstants.PASS_LEAD_SPEED_ESTIMATE` (a rough constant), since the *real* launch speed isn't known until `ground_pass_speed` runs below — this is a deliberate approximation, not a bug.
- `launch_ground(from, to, power) -> Vector3` — flat velocity of magnitude `power` toward `to`. `power` is virtually always the output of `ground_pass_speed` below now, not a fixed per-type constant.
- `ground_pass_speed(distance, charge_ratio, min_time, max_time, min_speed, max_speed) -> float` — **the pass always reaches its target regardless of charge; charge only controls how fast it arrives.** Speed is derived, not absolute: `travel_time = lerp(max_time, min_time, charge_ratio)` (full charge → short travel time → fast/firm; empty charge → long travel time → slow/soft), then `speed = clamp(distance / travel_time, min_speed, max_speed)`. At a fixed charge, doubling the distance doubles the speed (same travel-time budget covers more ground faster) — this is what makes a 40m pass and a 10m pass both "arrive," just at different speeds. Added after the first playtest found fixed-power ground passes felt too weak over distance.
- `launch_lob(from, to, peak_height, gravity) -> Vector3` — ballistic arc landing at `to` with the given apex height (`vy = sqrt(2*g*h)`, flight time `T = 2*vy/g`, horizontal = flat distance / `T`). Assumes launch and landing at the same height (flat field). Already distance-safe by construction (horizontal speed = distance / a charge-derived flight time), unlike the old fixed ground power — no fix was needed here.
- `interception_time(pass_from, pass_to, ball_speed, opp_pos, opp_speed, corridor_half_width, corridor_spread) -> float` — deterministic corridor-projection geometry: projects the opponent onto the pass line, checks whether they're inside a corridor that widens with distance (`half_width + along*spread`) and can reach that point no later than the ball. Returns the intercept time or `INF` if unreachable — no randomness, no knowledge of `AI_INTERCEPT_CHANCE` (that's layered on by the caller).
- `scatter_degrees(spread_base, assist, distance, distance_ref) -> float` / `apply_scatter(flat_dir, spread_deg, rng) -> Vector3` — accuracy randomization. `scatter_degrees` grows with distance (clamped `0.2..1.5×` of `distance_ref`) and shrinks with `assist` (`0..1`, project currently ships `PASS_ASSIST = 0.75`). `apply_scatter` rotates the flat aim direction by a random angle in `±spread_deg` — **always via an explicit `RandomNumberGenerator` parameter** (`match_manager._pass_rng`), never global `randf()`, so tests can seed it.

**`ball.peek_dribble_direction() -> Vector3`** (`ball_controller.gd`) — a **read-only** twin of `get_dribble_direction()`. The latter has a side effect: it mutates `_dribbler_prev_pos`, the same field `_integrate_forces()` reads/writes every physics tick to compute dribble-following velocity. `_process()`'s telegraph marker calls the aim-direction getter every RENDER frame while charging — if it used the mutating getter, that per-frame call would race the physics tick and understate the dribbler's measured velocity, making the ball visibly lag behind the player during any pass charge (found and fixed after the whole-branch review, not caught by any single task's review). `peek_dribble_direction()` uses only the dribbler's current facing (no position-delta tracking) and is safe to call every frame. `_fire_pass()`/`_start_charge()`/`_fire_charge()` still use the original mutating `get_dribble_direction()` — fine there, it's a one-shot call at a discrete moment, not a per-frame race.

**`ball.launch(velocity: Vector3) -> void`** (`ball_controller.gd`) — a mass-compensated impulse alternative to `kick(dir, power)`, for passes with a pre-computed launch vector (ground or ballistic). The ball also got a light landing-bounce `PhysicsMaterial` (`bounce = 0.4`) so lobs read visually instead of dead-stopping on landing. In `_on_action_contact()`, the existing `_action_power < 0.0` value is the sentinel that distinguishes a launch-pass from a kick (`ball.launch(_pending_launch)` vs. `ball.kick(_action_dir, _action_power)`) — keep that convention if you add a third impulse path.

**Telegraph marker** — while charging any pass (not the shot), a second yellow `MeshInstance3D` (`_target_indicator`, separate from the cyan controlled-player cone) tracks `PassSystem.select_target`'s current pick live, every `_process()` frame, so the human sees who they're about to pass to before releasing — it re-evaluates continuously as the player steers the aim stick, not just once at charge-start.

**Receive-assist** — while a human-controlled receiver's pass is inbound (`_receive_active` / `_receiver` / `_receive_timer`, set in `_fire_pass()` when the receiver is/becomes `controlled_player`), `_handle_player_input()` **unconditionally** steers their movement input toward the ball's predicted position (`ball.global_position + ball.linear_velocity * PASS_RECEIVE_PREDICT_WINDOW`), overriding whatever the stick is doing. **There is no "steer away = deliberate dummy run" carve-out** — an earlier version respected a stick pointing away from the ball as intentional, but in practice the human's stick is almost always still aimed for the *previous* controlled player right after a handoff (they haven't had a chance to re-aim for the new one), so that carve-out mostly just made receivers run in the wrong direction. Fixed after the first playtest; if a genuine deliberate-dummy-run feature is wanted later, it needs a different signal than raw stick position at handoff (e.g. a sustained away-hold over several frames). The phase ends on catch, timeout (`PASS_RECEIVE_MAX_TIME`), losing control, or the receiver becoming invalid — checked every `_physics_process()`.

**Give-and-go (wall pass)** — a `PASS_WALL` charge (combo + short-pass button) sets `params.is_wall = true`; on fire, if a receiver was found, the passer's `begin_give_and_go(receiver_pos)` (on `teammate_ai.gd`, since the passer is AI-controlled once possession/`controlled_player` hands off to the receiver) adds them to group `giving_run` and sprints them into space (opposite side from the receiver) for `PASS_WALL_WINDOW` (3s), hoping for a return pass. **This sprint is the one deliberate exception to "AI doesn't sprint"** in this project (see *Locomotion* above). The wall-pass also bypasses the ball's own kick cooldown for the return via `_clear_wall_pass_cooldown()` — a non-`await`ed coroutine (so it doesn't stall `_fire_pass()` itself) that calls `ball.clear_last_kicker()` after 0.4s, letting the passer reacquire the ball before their own `_kick_cooldown_msec` would otherwise have expired. `giving_run` membership is cleared in `_finish_fall()` as a safety net (in case a wall-passer gets knocked down mid-run) as well as by its own timeout/catch/role-change check in `teammate_ai.gd`'s `_physics_process()`.

**Teammate receiving role** — `teammate_ai.gd` has `enum Role { SUPPORT, RECEIVING, CHASING }` plus `begin_receiving(pass_dir, lead)` / `end_receiving()` / `_move_to_receive()`: an AI-teammate "run onto the pass" mechanism. **Currently unreachable** in this 1-human + 1-AI-teammate prototype — `_fire_pass()` always hands `controlled_player` to whoever receives a pass, so it's the human-side receive-assist above (not `Role.RECEIVING`) that actually delivers the "run onto the pass" feel today. `Role.RECEIVING` is live infrastructure for when the roster grows past 2 outfield players on our side. Separately, `_position_for_pass`'s support-run target was fixed to use `-Z` (this team attacks toward `-Z`) — it previously used `+Z`, which put the AI teammate behind the ball carrier instead of ahead.

**Honest interception** — `_maybe_flag_interceptor(from, to, launch_vel)` runs `PassSystem.interception_time` (deterministic corridor geometry) against every `team_2` node at the moment a pass is fired; if some opponent could geometrically reach the corridor in time, a `_pass_rng.randf() > AI_INTERCEPT_CHANCE` roll decides whether they actually react (a miss chance, so it's not omniscient/instant), and if they do, `simple_ai.gd`'s `begin_intercept(point)` makes them run to the corridor intersection point after a reaction delay (`AI_INTERCEPT_REACT`, 0.3s) rather than teleporting or reacting instantly. **Reads the opponent's real speed off the node** (`opp_nodes[i].get(&"speed")`, i.e. `simple_ai.gd`'s `@export var speed`, default 8.0) — not `FootballConstants.AI_SPEED` (5.0), which is stale/unused legacy left over from before `PlayerMotor`; using the constant would make every feasibility check wrong.

**New constants** (`football_constants.gd`, "PASSING" section) — ground-pass speed (distance-derived, NOT a fixed power — see `PassSystem.ground_pass_speed` above): `PASS_GROUND_MIN_TRAVEL_TIME` (0.5s, full charge), `PASS_GROUND_MAX_TRAVEL_TIME` (1.4s, empty charge), `PASS_GROUND_MIN_SPEED`/`MAX_SPEED` (4.0/28.0 m/s safety clamps), `PASS_LEAD_SPEED_ESTIMATE` (12.0 m/s — a rough constant fed to `lead_point` before the real speed is known, NOT the actual launch speed). Air-pass arc height: `PASS_LOB_PEAK_HEIGHT` (3.0m), `PASS_THROUGH_AIR_PEAK_HEIGHT` (2.5m). Charge: `PASS_CHARGE_MAX_TIME` (0.6s), `PASS_POWER_CHARGE_MIN`/`MAX` (0.7/1.6× multiplier, air-pass height only). Auto-aim: `PASS_LEAD_GAIN` (0.25s), `PASS_THROUGH_EXTRA_LEAD` (4.0m — bumped from 2.0m after playtest feedback that through-balls didn't lead far enough ahead of the runner), `PASS_DOT_BIAS` (0.15), `PASS_MAX_RANGE` (45m). Interception corridor: `PASS_CORRIDOR_HALF_WIDTH` (1.2m), `PASS_CORRIDOR_SPREAD` (0.06 per meter). Accuracy: `PASS_SPREAD_BASE` (12°), `PASS_SPREAD_DIST_REF` (25m), `PASS_ASSIST` (0.75). Receive-assist: `PASS_RECEIVE_PREDICT_WINDOW` (0.08s — halved from 0.16s after playtest feedback that the receiver's assisted run overshot too far ahead of the ball's actual position), `PASS_RECEIVE_MAX_TIME` (2.0s). Give-and-go: `PASS_WALL_WINDOW` (3.0s), `PASS_WALL_RUN_FORWARD` (10.0m), `PASS_WALL_RUN_LATERAL` (6.0m). Opponent interception: `AI_INTERCEPT_REACT` (0.3s), `AI_INTERCEPT_CHANCE` (0.8).

## Presentation layer & asset pipeline

**Gameplay and presentation are separated on purpose.** The `CharacterBody3D` + its AI/input script + `CollisionShape3D` are the *gameplay* (position, physics, tackle, groups) and are untouched by the visual work. The *visual* is a `scenes/player_visual.tscn` instance added as a child. Never bake animation/model logic into the gameplay scripts.

**`PlayerVisual` (`scripts/player/player_visual.gd`)** — the node script on `player_visual.tscn`, which instances `assets/models/footballer.glb` as a child named `Model`.
- Builds an `AnimationTree` **in code**: a state machine with **idle / run / sprint** locomotion states (each run/sprint state is its own `AnimationNodeAnimation` → `AnimationNodeTimeScale` sub-tree, not a shared blend space) plus one-shot action states layered in. No hand-authored tree resource.
- **Two flavors of one-shot state**, both auto-registered only if the clip exists in the glb: `ACTION_CLIPS` (kick/pass/penalty/throw_in — semantic name → clip name, auto-return to `LOCOMOTION` at clip end via `trigger(action)`; **header clips were removed 2026-07-12** — the header/skidка feature was cut, see Status notes) and `ONESHOT_CLIPS` (`tackle`, `fallen_idle`, `roll_left`, `roll_right`, `standing_up` — the slide-tackle/fall chain, travel-only via `play_oneshot(clip)`, no auto-return; `match_manager.gd`'s fall state machine drives the chain and calls `recover()` at the end). `ONESHOT_CLIPS` members are also **fully cross-connected** to each other (not just star-wired through `LOCOMOTION`) — without that, `travel()` between two of them with no direct edge pathfinds through the hub and visibly flashes `idle` mid-transition (bit us between the last roll and `standing_up`).
- **Known quirk (harmless):** `ACTION_CLIPS` maps both `"kick"` and `"pass"` to the same clip name `"pass"` (kick's dedicated clip isn't wired in yet — see Status notes). The registration loop keys nodes/transitions by the *resolved clip name*, not the action key, and doesn't dedupe against `_states` the way the `ONESHOT_CLIPS` loop right after it does — so every `PlayerVisual._ready()` logs real (but non-fatal — the duplicate add is a silent no-op) Godot engine errors (`Condition "states.has(p_name)" is true` + two transition-duplicate errors). Visible in any headless run touching `PlayerVisual` (e.g. `check_player_visual_fall.gd`). Not yet fixed.
- **Locomotion speed is fed in by `PlayerMotor`** via `set_locomotion(velocity: Vector3)` every physics frame — `PlayerVisual` no longer measures its own speed off `global_position` delta (that was the old direct-position-movement era). State selection is by speed thresholds (`LOCO_RUN_ANIM_SPEED`, `LOCO_SPRINT_ANIM_SPEED`); within run/sprint, the clip's `TimeScale` is driven by `run_timescale(speed, top_speed, fudge) = (speed/top_speed)*fudge` (`LOCO_RUN_SCALE_FUDGE`) so the animation's stride matches actual movement speed — the anti-foot-slide fix. If `footballer.glb` has no `sprint` clip, the sprint state silently falls back to playing the `run` clip at a higher `TimeScale`.
- Public API (the intended gameplay→visual seam): `set_locomotion(velocity: Vector3)`, `set_lean(deg: float)` (rolls the `Model` node for body-banking — expects an already-smoothed value; `PlayerVisual` itself does not smooth), `apply_appearance(cfg: Dictionary)` (reads `cfg["kit_color"]` → whole-body albedo tint), `trigger(action)` (plays one-shot `pass` clip for both kick and pass — kick's own animation clip is planned), `play_oneshot(clip)` / `recover()` (the fall/tackle chain — see *Slide tackle & fall system* below), `set_flag(flag, on)`. Timing: `ACTION_TIMING` dict per action (`contact` = when `action_contact` fires, `lock` = when `action_finished` fires). `trigger()` no longer a stub.
- **Fallback:** if the model or its `idle`/`run` animations are missing, it spawns a plain capsule and warns — gameplay keeps working.
- Exports for visual fit: `model_y_offset` (`-0.5`, drop feet to ground since the body sits at `y=0.5`) and `model_yaw_deg` (`180`, Mixamo models face `+Z` but game-forward is `−Z`).
- **glTF gotcha:** imported animations arrive **unlooped** (`loop_mode = NONE`) and freeze after one cycle; `_build_anim_tree` sets `loop_mode = LOOP_LINEAR` on idle/run/sprint at runtime.

**Team color** is a whole-body `albedo_color` tint via `apply_appearance` (pilot-grade, not a real kit yet): team_1 = blue `Color(0.1,0.1,0.9)`, team_2 = red `Color(0.9,0.1,0.1)`.

## Conventions that will trip you up

- **InputMap is built programmatically** in `match_manager.gd:_setup_inputs()`, which erases and recreates every action on `_ready()`. The bindings in `project.godot` are overridden and effectively dead. **Always edit `_setup_inputs()`, never `project.godot` input.** Movement is **arrows/left stick only** — WASD letters are freed for actions: `D`/gamepad-X = shot (hold to charge, release fires), `X`/`A` = short pass, `W`/`Y` = through ball, `A`/`B` = lob, `Q`/`LB` = context-sensitive (pass-combo modifier with the ball, player-swap without it — see *Passing* above), `Shift`/right-trigger (analog) = sprint (human only, no stamina), `Esc`/`Start` = pause. The old WASD-move / `E`-pass / unconditional-`Q`-swap scheme is gone.
- **Player movement is `velocity` + `move_and_slide()` via `PlayerMotor`** (see *Locomotion* above) — direct position manipulation is gone for regular locomotion. The slide tackle is the one remaining exception: it still moves the tackler with a manual `move_and_collide()` call in `match_manager.gd`, while the tackler's `PlayerMotor` is control-locked for the duration so the two motion systems don't fight.
- **Dribbling is continuous lead-follow** (ball held ahead, distance grows with speed; break-away → chase). See the *Ball model & dribbling* section above for the full model — this supersedes the old velocity-matching/spring description (and `SPRING_*`/`DRIBBLE_FORWARD_DIST` constants are now legacy/unused). Ignore OPENCODE.md's spring description.
- **Kick/pass use a deferred-impulse (commit-action) system**, not direct `ball.kick()`. `_fire_charge()` (shot) / `_fire_pass()` (all 5 pass types, see *Passing* above) set `_action_player`/`_action_power`/`_kick_action_active=true`, trigger the animation, and **wait** for `PlayerVisual.action_contact` signal before calling `ball.kick()` (shot) or `ball.launch()` (pass — distinguished by the `_action_power < 0.0` sentinel). No `set_control_locked()` during kick/pass — the `_kick_action_active` flag skips the motor-lock early-return in `_handle_player_input` instead, so movement/sprint/other-action inputs keep working while a kick/pass animation plays.
- **Shot = hold `D`/gamepad-X** for charge (up to `KICK_CHARGE_MAX_TIME` = 0.5s), release fires with power lerped 12–25. Passes share the same `power_bar` charge bar but a shorter max time (`FootballConstants.PASS_CHARGE_MAX_TIME` = 0.6s) — see *Passing* above for the five pass types. PowerBar (green→red gradient) visible during any charge. Auto-fires at max charge.
- **Movement is camera-relative** — input is transformed through `camera_pivot.global_transform.basis`, so "forward" means "away from the camera," not world-Z.
- **Controlled player** auto-switches to whichever team_1 player is dribbling; `Q`/`LB` switches manually **only while our team doesn't have the ball** (`_we_possess()` — with the ball, the same button is the pass-combo modifier instead; see *Passing* above), with a `_manual_swap_cooldown` to stop the auto-switch from immediately reverting it. A cyan cone indicator marks the controlled player; a yellow one (during pass charge only) marks the auto-aim's current target.
- **Team membership drives everything** via groups `team_1` (ours) / `team_2` (opponent); tackled players get a temporary `fallen` group. Use `_same_team()` and group checks, not node identity.

## Field coordinate system (FIFA-scale)

- Center at `(0,0,0)`. **Z = length (105m)**, **X = width (68m)**, Y = height. Half-extents: Z ±52.5, X ±34.
- **Goals are only ever on the Z axis** — Home at Z = −52.5, Away at Z = +52.5. Never place goals along X or Y.
- Our team attacks toward **−Z** (Home → Away).
- Camera is a fixed sideline/broadcast view: pivot parked at X = −40, follows the ball's Z, `look_at` the ball's Z on the centerline.
