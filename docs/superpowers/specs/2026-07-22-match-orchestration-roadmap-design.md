# Оркестрация матча: ИИ-стандарты, судья, per-actor управление — роадмап-дизайн

**Дата:** 2026-07-22
**Статус:** согласован, готов к плану реализации.
**Тип:** архитектурный роадмап (задаёт рамку; детальные спеки на каждую фичу — отдельно, под эту рамку).

## Что это и зачем

Сейчас все шесть стандартных положений либо реализованы (пенальти, штрафной, угловой, удар
от ворот, аут), либо отсутствуют (кикофф — гол просто ресетит мяч). Все реализованные:
- запускаются **отладочными клавишами** (P/F/C/G/T), а не по реальным событиям матча;
- **управляются локальным человеком** (team_1) — включая удар от ворот: там исполнитель — тело
  вратаря, но прицел/заряд/удар ведёт человек (по G).

Цель этого документа — задать архитектурную рамку и порядок работ, чтобы:
1. научить **ИИ** исполнять все стандарты;
2. связать стандарты в **живой матч** через движок правил («судью»);
3. сделать это так, чтобы **не загнать себя в угол** перед будущими режимами: матч vs ИИ,
   ИИ-vs-ИИ, 2 игрока на одном ПК (hotseat), матч по сети.

Это **программа из нескольких спеков**, а не один. Данный документ — первый (рамка + порядок).
Каждая фича ниже получит собственный спек → план → реализацию под эту рамку.

## Ключевые решения (зафиксированы в брейнсторме)

- **Сеть влияет на архитектуру только принципом «не загнать в угол».** Сейчас netcode не
  пишем. Но выдерживаем чистый шов «источник ввода → симуляция» и авторитетное состояние матча
  у судьи, чтобы сеть встала отдельным слоем без переделки геймплея.
- **Объём правил судьи v1 = «слой A + фолы подката».** Детект геометрии мяча (аут → вбрасывание;
  за лицевую → угловой/удар от ворот; гол → кикофф) + фол подката (мяч-первым/тело-первым →
  штрафной, в штрафной площади → пенальти). **Офсайд, карточки, прочие фолы — за горизонтом**
  (судья спроектирован расширяемым под них).
- **Подход к ИИ-управлению — «шов источника намерения» (Вариант 1), НЕ полный HumanBrain-рефактор
  сейчас.** Минимальный риск, вся существующая чистая математика (`*_logic.gd`) переиспользуется
  как есть. Полный `HumanBrain` (Фаза 3b) остаётся возможным позже — этот шов ему не мешает.

## Архитектура

### Шов «источник намерения» — per-actor, интерфейсы по ролям

**Проблема:** пять существующих контроллеров внутри `update(delta)` напрямую читают
`Input.is_action_*` для прицела, зарядки силы, смены ноги, коммита и модификатора-варианта.
«Team_1, человек» зашит неявно.

**Решение:** маленькие интерфейсы, отдающие контроллеру *намерение* без знания об источнике.
Принцип один («источник намерения»), но интерфейс — **по роли актёра**: жирная база с мёртвыми
для половины актёров методами (`foot()` у вратаря, `charge_held()` у стенки) хуже, чем три
маленьких сиблинга.

```
class_name KickerIntent extends RefCounted     # бьющий (все шесть стандартов)
  aim_axis() -> Vector2          # прицел / поворот heading (стик/стрелки)
  charge_held() -> bool          # кнопка силы зажата
  commit_pressed() -> bool       # событие «зафиксировать удар», ровно один true-кадр;
                                 # для Human-реализации = отпускание кнопки заряда
  variant() -> int               # вариант удара/паса (short/lob/через модификатор)
  foot() -> int                  # enum Foot { LEFT, KEEP, RIGHT } — смена ноги
  wants_cancel() -> bool         # отмена (где применимо)

class_name KeeperIntent extends RefCounted     # вратарь (пенальти; позже — штрафной)
  dive_zone() -> int             # enum PenaltyLogic.Zone {LOW_L, HIGH_L, LOW_R, HIGH_R, CENTER};
                                 # читается каждый кадр до самого удара (выбор можно менять),
                                 # контроллер применяет ПОСЛЕДНЕЕ выбранное на action_contact.
                                 # Момента коммита у источника НЕТ — ни у Human, ни у AI
                                 # (выравнено с Фазой B пенальти-спека: источник задаёт только
                                 # направление, момент всегда за контроллером)

class_name WallIntent extends RefCounted       # стенка как группа (штрафной)
  jump_pressed() -> bool         # команда «прыгнуть», один true-кадр
```

У каждой роли — две реализации:
- **Human\*** — тонкая обёртка над текущими `Input.is_action_*`. Поведение человека не меняется
  ни на пиксель. Первый шаг — чистый рефактор *без* изменения фила («как было»).
- **AI\*** — планировщик (см. ниже). Выдаёт те же «нажатия» по таймлайну.

Позже в те же слоты встают **Remote\*** (команды по сети) и **вторые Human\*** (2 игрока, разные
device_id) — без переделки контроллеров и математики. *Ниже по тексту «HumanIntent» / «AIIntent» /
«RemoteIntent» — собирательные имена этих реализаций по источнику, не имена классов.*

**Шов — per-actor, а не per-стандарт.** У стандарта несколько независимых актёров, у каждого
свой источник управления. Пример пенальти:

| Бьющий | Вратарь | Режим |
|---|---|---|
| Human | AI | сейчас (я бью, ИИ-вратарь) |
| AI | Human | ИИ бьёт, я в воротах |
| AI | AI | ИИ vs ИИ (закладываем на будущее) |
| Human | Human | 2 игрока на ПК |

Актёры, у которых есть источник управления: **бьющий, вратарь, игроки стенки (как группа)**.
Принимающие — **не** актёры шва: после выпуска мяча игра возвращается в обычный режим, приём
ведут существующие механизмы (receive-assist, handoff `controlled_player`, `begin_receiving`) —
отдельный intent-интерфейс им не нужен. Это та же логика, что в открытой игре
(`controlled_player` = человек, остальные = ИИ), только распространённая на стандарты. Один шов везде:
- одиночная игра: локальный человек = один актёр, остальные `AIIntent`;
- **ИИ vs ИИ**: *все* актёры `AIIntent`, ни одного `HumanIntent` — встаёт следствием честного
  шва, отдельного геймплей-кода почти не требует (нужен лишь пункт меню);
- 2P / сеть: несколько `HumanIntent`/`RemoteIntent` по разным актёрам.

**Кто из актёров «становится мной»** решает диспетчер судьи по режиму матча и по тому, чья
команда исполняет: когда моя команда **защищается** на пенальти — я автоматически «становлюсь»
вратарём (`HumanIntent` на вратаря), бьющий-ИИ получает `AIIntent`; когда бьёт моя команда —
наоборот.

### Профиль презентации (парный шов)

Сейчас контроллер мешает две вещи: (1) автомат `SETUP→AIM→STRIKE` + математику и (2)
**презентацию** — паркует `CameraPivot` в фикс 3rd-person позу, показывает power bar, рисует
ретикл/маркеры, гоняет церемонию разбега. Пункт (2) осмыслен только когда стандарт исполняет
**локальный человек**.

Вводится **профиль презентации** — **двухуровневый**. Бинарное «исполняю/наблюдаю» ломается на
смешанном случае «ИИ бьёт — я вратарь»: Фаза B пенальти-спека (2026-07-15) прямо требует камеру
из-за спины ИИ-бьющего + cyan-маркер над вратарём-человеком, т.е. при ИИ-бьющем камера ещё как
трогается. Поэтому:

1. **«Участвует ли локальный человек-актёр в стандарте?»** (в любой роли — бьющий, вратарь,
   стенка). Если да — включаются камера и тайминги стандарта, независимо от того, бьёт он или
   защищается. Пример: пенальти-камера из-за спины бьющего ставится и когда бью я, и когда бьёт
   ИИ, а я — вратарь.
2. **Состав HUD — по роли локального актёра:** бьющий → ретикл, power bar, полная церемония
   разбега; вратарь → cyan-маркер управляемого, без ретикла/бара; стенка → индикатор готовности
   прыжка (кулдаун).

**«Наблюдатель»** (камера **не трогается** — остаётся броадкаст/что смотрит зритель; без HUD;
можно ужать тайминги) — только когда локального человека среди актёров **нет вовсе**: ИИ vs ИИ,
или чужой стандарт в сетевом матче, где ни один мой актёр не участвует. Тот же наблюдательский
профиль переиспользуется 1:1 — отдельного сетевого кода на визуал не надо.

Контроллер спрашивает у профиля «мне владеть камерой/баром?» вместо безусловных
`set_*_cam_pose(...)`. Автомат и `*_logic.gd` не трогаются.

### Судья / состояние матча (`MatchReferee` v1)

Новый узел-компонент под `match_manager` (как `PenaltyController` и др.). Держит автомат матча
и решает, что и кем исполняется.

**Автомат матча:**
```
LIVE (открытая игра) → событие → DEAD (рестарт назначен)
DEAD → выбранный контроллер стандарта отрабатывает → LIVE
```

**Детект событий (v1):**
- **Мяч за боковой** → вбрасывание. Исполняет команда, противоположная last-touch.
- **Мяч за лицевой** → угловой (last-touch = защищающаяся команда, т.е. та, чьи ворота стоят
  на пересечённой лицевой) или удар от ворот (last-touch = атакующая).
- **Гол** → кикофф с центра; исполняет **пропустившая команда**. Кто разводит на старте матча —
  по жребию или фиксированно, решить в спеке кикоффа (Этап 1).
- **Фол подката** (мяч-первым/тело-первым; код наполовину проведён в `match_manager` —
  `_tackle_foul_position`/`_tackle_fouled_player` уже есть, но `_tackle_clean=true` безусловно —
  переактивировать по правилу) → штрафной или пенальти. **Исполняет команда пострадавшего**
  (жертвы подката); атрибуция фол-события — `{фоливший, пострадавший, точка}`, не last-touch.
  **Пенальти — только если точка фола внутри штрафной площади, которую защищает команда
  фолившего**; фол атакующей команды в той же штрафной → обычный штрафной в пользу защиты, не
  пенальти. Направление правила: фол = контакт с телом соперника **до** касания мяча в рамках
  подката, мяч первым = чисто; точный критерий (порядок контактов, окно подката) — в детальном
  спеке судьи, см. `docs/football_reference.md` §9.

**Разрешение рестарта — две чистые функции** (в духе `*_logic.gd`, все данные — параметрами):
1. `событие + атрибуция + позиция → {тип рестарта, команда-исполнитель, точка}` — атрибуция
   для выходов мяча = last-touch (исполняет противоположная команда), для фолов =
   `{фоливший, пострадавший}` (исполняет команда пострадавшего);
2. `{тип, команда, точка} + снапшот ростера (позиции + роли обеих команд) → кто бьёт` —
   ближайший подходящий игрок нужной команды (аут — ближайший полевой; удар от ворот — вратарь;
   угловой — ближайший к флажку; штрафной/пенальти — тоже ближайший в v1, «назначенный
   пенальтист/штатный исполнитель» — будущее расширение, атрибутов ростера пока нет).
   «Ближайший» невычислим без ростера, поэтому ростер — явный параметр, а не скрытая зависимость.

Обе тестируются хедлесс.

**Диспетчер:** назначает источник намерения каждому актёру. Если исполняющая команда (или
защищающийся ключевой актёр — вратарь на пенальти, стенка на штрафном) принадлежит команде
локального игрока — диспетчер **передаёт** человеку управление этим актёром (как сейчас делает
аут: бьющий = ближайший team_1, управление ему автоматически, кем бы человек ни управлял до
свистка); Human-источник — **следствие этой передачи, а не проверка** текущего
`controlled_player`. Все остальные актёры — под `AIIntent`. Дальше диспетчер выбирает профиль
презентации и запускает нужный контроллер. Отладочные клавиши P/F/C/G/T остаются как ручной
триггер для тестов, живой матч идёт через судью.

**Зависимость №1 (флаг as-built конфликта):** сейчас границы поля — стены, от которых мяч
**отскакивает** (CLAUDE.md, *Locomotion*). Для детекта аута/лицевой мяч должен **пересечь линию**.
Ранняя задача этапа 0: **отодвинуть границы наружу** + детект пересечения плоскости линии *раньше*
отскока.

**Зависимость №2 (as-built): честного last-touch НЕ существует.** `get_last_touch` нигде не
определён — вызовы в `match_manager.gd`/`simple_ai.gd` стоят под `has_method`-гардом и молча
мертвы. Есть только `ball.last_kicker` — механизм кулдауна удара, а не атрибуции касаний: он
намеренно чистится при блоке в полёте и каждым set-piece контроллером на старте, и не обновляется
на трапе/парировании. После рикошета от защитника мяч, ушедший за лицевую, имеет
`last_kicker == null` — угловой не отличить от удара от ворот. Ранняя задача этапа 0 (близнец
задачи про границы): **честный трекинг касаний на мяче** (kick/launch/trap/block/parry/catch,
без очистки при блоке) — вход судьи.

**Судья = логика + презентация (тот же gameplay/presentation-сплит, что везде).** `MatchReferee`
выше — это **логика** (невидимый мозг, решает события/рестарты/позже карточки). Видимая
**моделька судьи на поле** — отдельная сущность (`RefereeAvatar`, презентация), нельзя смешивать с
логикой.
- **Контракт (закладываем в Этап 0):** `MatchReferee` эмитит **сигналы** как публичный выход —
  `restart_awarded(type, team, spot)` (`team` = **исполняющая** команда), `foul_called(spot, team)`
  (`team` = **фолившая**), позже `card_shown(player, color)`.
  Это и так правильно (решение развязано и от диспетчера, и от визуализации). Диспетчер и будущий
  `RefereeAvatar` — оба подписчики этого потока.
- **`RefereeAvatar` — на будущее, сейчас НЕ делаем жесты/карточки.** Near-term версия (когда до неё
  дойдут руки) = просто **бегающий по полю чёрный актёр, как игроки**: тот же пайплайн
  `PlayerFactory` + `PlayerVisual`, только чёрный тинт, без команды и без взаимодействия с мячом,
  позиционируется у игры. Жесты стандартов и показ карточек — **позже**, отдельно (карточки — вместе
  с расширением судьи до дисциплины, а она за горизонтом).

### `AIIntent` — как ИИ принимает решения (общая форма)

У всех `AIIntent` одна структура, отличается только «оценка вариантов» под конкретный стандарт:

1. **Обдумывание (обязательный элемент).** На входе в `SETUP` — рандомизированная пауза (плюс,
   где уместно, подход к мячу/расстановка), прежде чем ИИ начнёт целиться и заряжать. **Не
   мгновенный «выстрел по входу»** — ИИ «думает» как человек. Пауза сидируемая и тюнится, заодно
   даёт зрителю понять, что идёт стандарт.
2. **Оценка (один раз).** Собрать кандидатов-получателей (свои в досягаемости), оценить каждого:
   открытость коридора паса (переиспользуем `PassSystem.interception_time`), продвижение к
   воротам, дистанцию. Выбрать лучший вариант: кому/куда + тип + сила. *(Это кикерский пример;
   у вратаря «оценка» = выбор зоны дайва, у стенки = ролл прыгать/стоять — четырёхшаговый шаблон
   тот же, состав решения свой.)*
3. **Ошибка/характер.** К цели добавить разброс через сидируемый RNG (сила ИИ = масштаб
   разброса). Задел под уровни сложности.
4. **Проигрывание.** Превратить решение в таймлайн «нажатий» ролевого интерфейса
   (`aim_axis()`/`charge_held()`/`commit_pressed()` у бьющего; `dive_zone()` у вратаря;
   `jump_pressed()` у стенки), который контроллер потребляет как ввод человека. Доворот
   прицела с человеческой скоростью (не мгновенно), удержание заряда под нужную силу, затем выпуск.

**Ключевой принцип:** `AIIntent` **не** зовёт `ball.launch()` и не трогает математику. Он только
выдаёт «нажатия»; вся физика/математика идёт тем же путём `*_logic.gd` + контроллер, что у
человека. Одна кодовая база правды, ИИ и человек физически неотличимы в результате.

**Планировщик решений — тоже чистая функция** (`SetPiecePlan.choose(...)` → `{target, variant,
power, aim_error}` — форма выхода кикерская; у вратаря/стенки свой состав: зона; bool прыжка),
отдельно от «проигрывания», чтобы тестировать выбор без симуляции. По одному на стандарт, по
общему шаблону.

## Named-пробелы в поведении защиты

### Прыжок вратаря за пенальти

Инфраструктура почти вся есть (`keeper_ai.set_penalty_mode()`, `begin_penalty_dive(zone)`,
`_begin_save` через `move_and_collide` по горизонтали, клип — вертикаль). Доделать:
- Честный **прыжок в угол** с реальной геометрией дайва (высокий/низкий, лево/право), чтобы
  визуально дотягивался до мяча, когда спас засчитан (сейчас за пенальти вратарь ныряет «блайнд»
  в зону).
- Работает симметрично от источника: вратарь-актёр под AI-`KeeperIntent` (зона выбрана
  планировщиком) и под Human-`KeeperIntent` (я кручу выбор зоны стиком — лево-верх / лево-низ /
  право-низ / право-верх / стоять — **вплоть до момента удара**, выбор можно менять). В обоих
  случаях момент один: контроллер применяет последнюю выбранную зону на `action_contact`
  (выравнено с Фазой B пенальти-спека — источник задаёт только направление, не момент; ранний
  нырок невозможен, угадайка честная). CENTER = стоять на месте — работает существующий рефлекс
  по высоте. Не зависит от того, кто бьющий.

Идёт в связке с ИИ-пенальти (первая фича этапа 2).

### Прыжок стенки на штрафном

**As-built: прыжок стенки уже реализован** — `free_kick_controller._update_wall_jumps()` +
`FreeKickLogic.wall_should_jump`: детерминированный авто-прыжок по реальной траектории мяча
(пик прыжка подгадан под подлёт), вертикаль в обход Y-пиннинга решена, клип `jumping_wall`
играется как one-shot. Работа этого роадмапа — **не построить прыжок, а заменить триггер** по
источнику управления:

- **Стенка под AI-`WallIntent`** (ИИ защищается): текущий триггер читает траекторию идеально —
  заменяем на **честную угадайку**: **один общий ролл на всю стенку на весь штрафной** — 70%
  вся прыгает / 30% вся стоит (сидируемый RNG). **Тайминг при выпавшем «прыгать» остаётся
  существующим**: `wall_should_jump` решает *когда*, ролл решает только *прыгать ли вообще*.
  Обоснование замены: то же, что у слепого нырка вратаря на пенальти — защита не должна
  всечитающе реагировать на удар, у бьющего должен быть шанс пробить под стенкой. *Дефолт —
  единое поведение всей стенки; отдельные роллы по игрокам — возможное расширение, сейчас не
  включается.*
- **Стенка под Human-`WallIntent`** (штрафной бьют мне, я защищаюсь): авто-прыжок **отключён**,
  прыжок — по моей команде (`jump_pressed()`), любой кнопкой из пула **A/B/X/Y** на геймпаде.
  Окно доступности: во время **прицеливания**, **разбега** и ~1–2 с после удара (будущая
  константа `FK_WALL_JUMP_HUMAN_WINDOW`, значение — в детальный спек). После прыжка —
  приземление и **кулдаун восстановления**, затем снова можно прыгнуть (можно тест-прыгнуть до
  разбега, а на удар прыгнуть по-настоящему).

**Открытая деталь (в детальный спек штрафного, не в роадмап):** когда я защищаюсь на штрафном —
каким *одним* полевым я управляю (вратарём? защитником?), и работает ли кнопка прыжка стенки
(group-action) независимо от этого управления.

Идёт в связке с ИИ-штрафным (последняя фича этапа 2).

## Порядок реализации до 11×11

### Этап 0 — Фундамент (швы + судья)
Без него ИИ-стандарты «правильно» не сделать.
1. **Отодвинуть границы поля наружу** + детект пересечения линии (зависимость №1 судьи).
2. **Честный трекинг касаний на мяче** (kick/launch/trap/block/parry/catch, без очистки при
   блоке) — вход судьи (зависимость №2; сейчас есть только чистимый `last_kicker`).
3. **Шов «источник намерения» (per-actor, ролевые интерфейсы) + профиль презентации** — рефактор
   пяти существующих контроллеров: заменить прямые `Input.is_action_*` на `_intent.*`, вынести
   владение камерой/баром в двухуровневый профиль. Чистый рефактор, поведение человека «как было».
4. **`MatchReferee` v1** — автомат LIVE/DEAD, детект (аут/лицевая/гол/фол подката), две чистые
   функции разрешения рестарта, диспетчер (кому какой intent + презентация), сигналы.
   **Интерим-поведение до Этапов 1–2 (явно):** диспетчер работает в режиме detect+award —
   событие фиксируется и сигналится; рестарт, для которого ещё нет контроллера или
   AI-исполнителя, разрешается заглушкой: мяч поставлен на точку, владение отдано нужной
   команде, матч обратно в LIVE, без церемонии. Кикофф до Этапа 1 = существующий `_reset_ball`.

### Этап 1 — Кикофф
Шестой стандарт, самый простой (обе команды на своих половинах, соперник вне центрального круга
до касания, мяч в центре, исполнитель крутит камеру и отдаёт пас своему на своей половине).
**Пишется сразу на шве** — прямых `Input.is_action_*` в нём не появляется. Обкатка шва:
human-контроллер + `AIIntent`, интеграция с судьёй (старт матча + после гола).

### Этап 2 — ИИ-стандарты (по согласованному порядку)
5. **ИИ-пенальти + вратарь-актёр** (дайв под `AIIntent` и `HumanIntent`; 3 комбинации —
   Human×Human подключается вместе с режимом 2P, за горизонтом) — первым.
6. **ИИ-удар от ворот.**
7. **ИИ-аут.**
8. **ИИ-угловой.**
9. **ИИ-штрафной + триггер прыжка стенки** (гейт 70/30 общим роллом под ИИ с сохранением
   существующего тайминга `wall_should_jump`; кнопочный с окном/кулдауном под человеком —
   авто-прыжок при человеке отключается).

### Этап 3 — Масштаб до 11×11
Роспись формации/ролей, расстановки под каждый стандарт на 11 игроков, базовая тактическая
ИИ-логика открытой игры. **Отдельный большой спек** (открытая игра, не стандарты).

## Заложено на будущее (не реализуется сейчас, «не загонять в угол»)

- **ИИ vs ИИ** — first-class режим (матч, где обе команды — ИИ, человек смотрит). Следствие
  честного per-actor шва (все актёры `AIIntent`); отдельная работа — лишь пункт меню. Держим как
  цель, чтобы нигде не зашить «человек = team_1».
- **2 игрока на ПК (hotseat)** — несколько `HumanIntent` по device_id в тот же слот.
- **Сеть** — `RemoteIntent` в тот же слот + авторитетное состояние матча у судьи; netcode
  отдельным слоем позже.
- **Офсайд / карточки / прочие фолы** — судья спроектирован расширяемым, но в этот роадмап не
  входят.
- **`RefereeAvatar` — моделька судьи на поле.** На будущее. Логика (`MatchReferee`) уже эмитит
  сигналы под неё (Этап 0). Near-term версия — бегающий чёрный актёр как игроки (без жестов/карточек);
  жесты стандартов и карточки — ещё позже (карточки — вместе с правилами дисциплины).
- **Структура матча** — таймы, часы, смена сторон, замены, добавленное время — отдельно, вне
  этого роадмапа (вероятная привязка — Этап 3 или после него).
- **Полный `HumanBrain` (Фаза 3b)** — симметризация управления телом человека; шов Варианта 1 ему
  не мешает, можно сделать позже.

## Тестирование

Паттерн проекта (хедлесс `tests/check_*.gd`, чистые функции без автолоада):
- **Чистые функции** тестируются напрямую: `SetPiecePlan.choose(...)` (выбор цели/варианта),
  обе функции разрешения рестарта судьи (событие → тип/команда/точка; + ростер → кто бьёт).
- **`AIIntent`** тестируется как «план сгенерил разумные нажатия», а не заново физика.
- **Автоматы** (судья LIVE/DEAD, диспетчер) — хедлесс-смоук в духе `check_penalty_flow.gd`.
- **Фил** (камера, разбег, дайв, прыжок стенки, тайминги ИИ-обдумывания) — только человек за игрой,
  хедлесс не драйвит ввод/рендер.
